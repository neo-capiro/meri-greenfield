# User preferences application contract

Implementation outline: isolated source branch `codex/meri-user-preferences-task6-20261017`, base `caa7810ff19c09c8f7ea1c2524c025f36f99ccd6`.

- `document.mjs` becomes the canonical pure owner of complete user preference fields, vocabulary, defaults, shape schema, canonical timezone semantics and field errors. The existing server document module retains Node-only inert ingress, current-client membership/release checks, tenant capability policy and ProductError mapping. The service/store retain persistence, revision CAS and audit ownership.
- `schema.mjs` derives receiving envelopes from that document owner. `protocol.mjs` describes the exact two POST paths, independent owner expectation and byte limits. `receive.mjs` composes closed JSON/schema/document checks and correlation: read requires independently current Core tenant/actor; save additionally requires the captured request, next revision and identical complete document. No identity or permission is granted by receiving.
- `generate-user-preferences.mjs` derives error/status vocabulary from the product HTTP owner and user application, and generates self-contained browser JS, schema, metadata and TypeScript. Installed Rolldown/TypeScript/json-schema-to-ts may be reused offline without installs. Existing public distributions stay unchanged.
- Focused verification covers existing server behavior and tenant semantics, actual API-produced read/save/conflict/withheld errors over labelled synthetic storage/membership boundaries, hostile/closed JSON, canonical timezone/default-client formatting, owner substitution, revision/document mismatches, exact public types and deterministic read-only generated checks.

Public API: async `receiveUserPreferencesRequest(route,jsonText)` for `read|save`; async `receiveUserPreferencesResponse(route,httpStatus,jsonText,expectation)`. Read expectation is `{owner:{tenantId,actorId}}`; save expectation additionally requires `{request}` with the exact captured complete save request. Both success bodies contain `{owner,revision,preferences}`. Outputs are recursively frozen. Owner must come from independently current Core identity, never Clerk IDs or a response body.

Runtime mounting and persistence qualification remain an integration handoff. This contract does not establish deployed membership support, database schema/migration, notification delivery, global theme behavior, default-client auto-selection or deployment acceptance.

Generation uses the existing Ajv standalone pattern. Explicit `--offline` reuses already installed Rolldown 1.2.13 (MIT), TypeScript 5.9.3 (Apache-2.0), json-schema-to-ts 3.1.1 (MIT) and ts-algebra 2.0.0 (MIT). `FromSchema` infers the canonical schema and the TypeScript checker expands structural types; no DTO fields are copied. There are no installs, network calls or dependency/lockfile edits. Set `MERI_CONTRACT_BUNDLE_ROOT` to the installed frontend toolchain and `MERI_CONTRACT_TYPE_MODULES` to the existing directory containing json-schema-to-ts/ts-algebra. Ordinary `--check` selects the backend recorded in metadata, so these offline artifacts require those roots even for a default check; an esbuild-only installation cannot reproduce them. Explicit conflicting `--canonical --check` refuses. Normal generation retains the canonical esbuild/json-schema-to-typescript backend unless `--offline` is explicit.
