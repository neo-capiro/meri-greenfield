## Envelope and operation semantics

Each closed request carries operation, request/job identity, tenant/actor/client/owner, actual Objective revision/version/snapshot and all five intent fields (or an explicit manual source), context packet and coverage hashes, original deadline and an opaque delegation reference/revision. Edit/document requests also pin the exact Strategy/version/hash and complete existing dependency graph. `inputSha256` is canonical SHA256 of the whole request excluding only `inputSha256`; it is not a hash of the nested `input` alone. Hashes detect mismatches; a trusted owner must supply the expected identities and snapshots.

`strategy.draft` carries an optional existing Strategy type hint. The model proposes one of the seven existing types and rationale from evidence; Objective ask type is a separate enum. No extra mandatory user picker is added. The whole graph must have 1–60 nodes, valid kinds/subjects/statuses, supported ownership/evidence, required real start dates, valid ranges and known acyclic edges. Unknown required dates produce typed `needs-information`; nothing fabricates a date, truncates nodes/titles or drops edges.

Draft dependencies use stable source node keys. `draftDependencyIndices` validates the entire graph and maps those edges exactly to the current draft DTO's numeric indexes. It is a narrow edge converter, not an implemented backend adapter. The trusted backend must map owners through its current active member directory and re-run existing verifiers.

`strategy.edit` normalizes the existing assistant DTO (scope/node/instruction/clientMessageId/attachments). Its pinned basis represents the complete live non-archived snapshot. Attachment resolution, `serializeStrategy`, owner names, grounding and steward context remain backend-owned and must be bound by the trusted context packet. Dependencies are tagged `{kind:'existing',nodeId}` or `{kind:'new',sourceNodeKey}`. Internal graph identities preserve these namespaces even for identical lexical IDs. This supports new/new and existing/new edges; the final whole graph, including removals, must remain acyclic and at most60 nodes. Backend preallocates all accepted new IDs, then maps dependency references once inside its existing atomic owner. Node-scoped requests cannot add or edit other nodes.

`strategy.step-document` carries the existing workspace/outreach kind, Strategy type, goal and normalized node fields. A trusted `nodeSha256` in the pinned basis must equal the entire submitted node snapshot, including title/note/kind/subject/dates. The proposal result supplies nullable title/summary, sections and nullable model metadata. HTML is untrusted; sanitization, deterministic placeholders, verification, assurance and product document materialization stay with the existing backend execution owner. No autonomous document write or model-minted assurance is accepted. The current null-client short circuit stays outside this candidate; no request is dispatched for that case. Grounding and steward facts/health must be represented by an authorized immutable context packet; this candidate does not serialize or verify their legacy opaque DTOs. Never forward `ResolvedAiProvider.apiKey` into this envelope.

Model output is `ModelOutcome`: literal operation, `succeeded|needs-information|refused`, operation-specific payload (or null) and typed issues. The SDK boundary requires literal `result/success`, `is_error:false` and `structured_output`. It never parses chat text as a verified result. Failure/cancellation states belong to the trusted runtime result envelope, not model-created lifecycle authority.

Each result binds request/job/input/source/context/basis, the complete canonical RunBinding (including attempt and writer fence), result reference, original completion time, payload hash and envelope hash. `payloadSha256` hashes payload, including null; `resultSha256` hashes the entire envelope excluding only itself. Successful completion must predate the original deadline. `assertRetainedResult` additionally requires the already-trusted exact result reference/hash, so a rehashed replacement is rejected. This pure check neither proves durable immutability nor performs current authorization.

Accepted factual source refs must exist in the request's accepted evidence set; pending refs remain separately marked assumptions/coverage and cannot support factual nodes. Tenant-shared evidence must have null client; client evidence must match the request client. These structural checks cannot establish real freshness, source truth or current client-wall membership; Core/context owners must do so.
