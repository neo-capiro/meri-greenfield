# Task command application contract

Implementation outline (2026-10-16, pinned local base de17699 / reviewed PR100 tree):

- This additive `urn:meri:task-command-application:0.1.0` browser boundary owns only the two task-update HTTP receiving envelopes, bounded inert JSON, stable conversation binding and selected-proposal/result correlation. It grants no approval or execution authority.
- `commands-0.2/task-update.schema.json` owns raw, normalized command, proposal and result shapes. `commands-0.2/task-update-validation.mjs` owns normalization; the generator bundles its existing normalizer with a JSON-only snapshot adapter. The existing command metadata, approval, authority, journal and source owners remain server responsibilities.
- `schema.mjs` references canonical shapes; `protocol.mjs` describes paths and limits; `receive.mjs` composes shape and semantic checks; `semantics.mjs` correlates immutable proposals and receipts. `generate-task-commands.mjs` resolves canonical schema references and error/status vocabulary from actual HTTP owners into self-contained browser artifacts. Existing schemas, generators, distributions and wire versions are unchanged.
- Prepare expects `{arguments: TaskUpdateRaw}` and returns `{status:'approval_required',proposal}`. Execute submits exactly that proposal and returns either observed receipt/result or `{status:'indeterminate',outcome:null}`. The receiver requires independent stable tenant/actor/conversation/run context; callers check proposal expiry against a fresh clock before presenting or submitting it. Resumed attempt/fence changes are permitted only within the same stable binding.
- Tests use actual API composition over synthetic authority/SQL/source boundaries, plus hostile input, schema, command SHA, tenant/scope, datetime, selected proposal and result/receipt mismatch cases. Generation drift, browser import isolation and public TypeScript checks verify the distribution. No live service, migration or deployment evidence is claimed.

Public API: `receiveTaskCommandRequest(route,jsonText)` and `receiveTaskCommandResponse(route,httpStatus,jsonText,expectation)` are async. Prepare expectation is `{binding,request}`; execute expectation is `{binding,proposal}`. Returned objects are recursively frozen. `TaskCommandExpectedBinding` contains only `tenantId`, `actorId`, `conversationId`, `runId`; it must come from independently authenticated application context. Errors use `TaskCommandResponseError.code`. Public metadata records exact route paths, limits, HTTP error statuses and outcomes.

Generation follows the existing Ajv standalone/esbuild/json-schema-to-typescript convention. An explicit offline option reuses already installed Rolldown 1.2.13 (MIT), json-schema-to-ts 3.1.1 (MIT), ts-algebra 2.0.0 (MIT) and TypeScript 5.9.3 (Apache-2.0): `FromSchema` infers the canonical flattened schema and the TypeScript checker expands structural declarations, with no copied DTOs. There are no installs or source dependency/lockfile changes. `--offline` requires `MERI_CONTRACT_BUNDLE_ROOT` (an installed frontend toolchain) and `MERI_CONTRACT_TYPE_MODULES` (the existing modules directory containing json-schema-to-ts and ts-algebra). `--javascript-only` is a diagnostic partial build that explicitly records declarations as ungenerated; release consumption requires a full generation and typecheck.

`--check` selects the backend recorded in the generated metadata and rejects conflicting backend flags. These committed artifacts record the offline Rolldown/json-schema-to-ts backend, so both ordinary `--check` and explicit `--offline --check` require the two borrowed tool roots above; an esbuild-only installation cannot reproduce them. Missing roots fail before loading build tools or writing files. Normal generation keeps the canonical esbuild/json-schema-to-typescript default unless `--offline` is explicitly selected.
