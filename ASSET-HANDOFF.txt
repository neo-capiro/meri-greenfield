1. What this closes
-------------------
apps/artifacts/service.mjs generation already validated the TRUSTED `context.assets` and handed the
actual object bytes to the executor, but `versions.commit` retained only
version/spec/specSha256/requestSha256/inspection, so the immutable spec's own
`assetId -> ObjectReference` mapping was lost at the durability boundary. The existing private
`revisionSource` read and apps/control/intents/document-revision.mjs therefore correctly refused
every asset-bearing parent (no map to re-present, and nothing may be re-derived).

The smallest continuation of the existing storage/revision owners: the canonical immutable version
record may now carry that mapping, bounded and optional; the private source read carries it back;
the intent layer treats it as the exact original mapping; the run composition re-presents it. No new
asset platform, no duplicate journal, no browser/model asset authority, no re-render without objects.

4. Backward compatibility (oldbytes)
------------------------------------
- A record without the map is returned by `recordValue` as the identical object and hashes
  identically: `v.hash(record)` unchanged, so every existing `record_sha256`, projection_sha256,
  decisionSha256 and page/position hash is untouched and existing rows stay byte-identical. Proven by
  the map-free assertions in the new tests (exact 5-key sorted key set, hash equality, private and
  public DTO key sets) and by the REVERT-run comparison above (all pre-existing storage/revision tests
  that pass at HEAD also pass with the change).
- Old binaries are NOT assumed compatible with a map-bearing record: at HEAD both
  `version-record.mjs:recordValue` (`own(raw,['version','spec','specSha256','requestSha256','inspection'])`)
  and `postgres-versions.mjs:commit` (`own(value,[...same 6 keys...])`) reject unknown record keys, so
  an old binary reading a new map-bearing record fails ARTIFACT_VERSION_CORRUPT. Also at HEAD
  `document-revision.mjs` accepted `own(raw,[5 keys])` only, so an old intent reader refuses a source
  carrying `assets`, and `revision-composition.mjs` refused EVERY asset-bearing parent
  (`if(retained.assetIds.length)fail('UNAVAILABLE')`).
- Map-free records therefore remain fully readable and revisable by old binaries; only a record whose
  spec actually declares an asset reference is ever written with a map.

5. Rollback / activation disposition
------------------------------------
- Reads are dual-format in this binary: records with and without the map are both read, and the map is
  surfaced only on the explicit private revision-source path. Ordinary inspect/download/history/list
  DTOs are unchanged, so nothing else in the fleet observes the new field.
- Writes: a map is emitted only when the submitted request actually declares an asset reference and
  the trusted context supplies that object. A deployment therefore activates this feature by
  deploying this binary everywhere; with no asset-declaring requests there are zero map-bearing
  records and rollback to an older binary is safe. Once any map-bearing record exists, rolling BACK
  to an older binary would make that artifact unreadable (ARTIFACT_VERSION_CORRUPT at row decode), so
  roll-forward is the supported floor; the new binary always reads both shapes.
- No migration was invented: the existing SQL already stores the whole record as JSONB and no
  schema change is required. No live upgrade, database or WSL recovery was performed (A5 owns the
  central union / migration decision).
