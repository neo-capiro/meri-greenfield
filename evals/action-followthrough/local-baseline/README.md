# Six-case local action baseline

Run `node evals/action-followthrough/local-baseline/cli.mjs --run` from a checkout with the existing pinned root contract dependencies available. No new dependency or install is introduced. `--help` or no arguments prints usage; invalid arguments exit2. Import/help/invalid paths do not construct a demo. Success exits0, any failed case exits1. The CLI sets the existing fixture's explicit source-root selector to this checkout.

`runLocalPilotBaseline({mode:'synthetic-local',createDemo?})` uses the accepted `createLocalActionDemo` by default. Optional factory injection is a trusted local test seam. Direct library users set `MERI_REVIEW_SOURCE_ROOT` to this checkout before the fixture is loaded. The public receiver admits every actual HTTP response before semantic scoring; raw response text is capped at262,144 bytes. Each case has the canonical six-second lifetime, fresh fixture stores/session, and independently attempted close and a separate one-second canonical cleanup lifetime around close, post-close HTTP/body/receiver ports. Post-close401/no-additional-effect checks must pass. The enclosing qualification command is captured with the existing240-second owned-process watchdog.

P01 queries the stored Issue/Changed/Matters/Recommend facts. P02 preserves unknown enumeration/freshness and unsupported absence. P03 creates only the editable title/no-date draft. P04 prepares an approval-required proposal. P05 calls execute on that exact pending proposal and requires409. P06 revokes its fresh session before query and requires401/no source read. Host preludes are deterministic; prompts are not sent to a model or interpreted as routing evidence. All six forbid approval issuance and task effects.

The returned receipt keeps all six IDs, status/checks, route/status/request/response digests, whitelisted synthetic observations, actual effect counters and cleanup. A missing/malformed/refused step or cleanup failure stays FAIL; no retries or denominator exclusions. No bearer, source credential, full request body or thrown error text is emitted. Successful outcomes are deterministic in semantics; generated IDs/timestamps/hashes are fresh and intentionally variable.

The exact accepted templates/gold remain in `docs/qualification/candidates/local-application-20261013/pilot/cases.json`; this runner does not rewrite that documentation packet. No copied retrieval/SQL engine, shared-pool fixture extension, approval endpoint, model orchestrator, listener, native database or paid/provider operation is added. Success is an implemented route/semantic baseline, not human-authored-case provenance, NL/model quality, native durability, deployment qualification or approval of the paid pilot.

The accepted demo reuses its synthetic binding-template tenant/actor/run IDs across instances; each case receives a new process-local identity owner, opaque session, stores and generated lookup/result/proposal IDs. These checks do not claim distinct native tenant namespaces or fresh database rows.
