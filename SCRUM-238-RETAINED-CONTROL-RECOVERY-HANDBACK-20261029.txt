2. THE DEFECT AND THE FIX
   useRunQuestion minted crypto.randomUUID() per submit and kept no record of the attempt, so a second invocation or a
   reload of the same run produced a new control identity for a delivery the client could not account for.
   The fix reuses the existing owner rather than adding one: apps/web/src/shared/meri-conversation-lifecycle/journal.ts
   already retains exactly one unresolved control per run in the signed-in tab record, and useRunLifecycle already
   establishes retain-before-dispatch, current identity and known-NOT_DISPATCHED versus unknown handling.

   - journal.ts: `same()` now compares answers exactly (questionId plus the submitted labels, key order normalised) so
     two different answers to the same question can never be treated as the same retained control. The steer,
     approval.wait and checkpoint comparisons are unchanged.
   - useRunQuestion.ts: sendAnswer() retains the exact answer control *before* dispatch, refuses any fresh attempt while
     this run still holds an unresolved answer (returning `refused: retained`, never a second id), replays the retained
     control only on an explicit `reconcile` (the card's "Check the same answer again"), retires it only on a proven
     NOT_DISPATCHED refusal, and keeps it across APPLIED, UNKNOWN, transport loss and a superseded conversation.
     Retention is mandatory: with no usable tab journal the card refuses to send (`refused: unretained`, new `retention`
     state) instead of minting an unretained identity.
     settleRetainedAnswer() clears the retained control only when the run's own durable projection reports
     answered/cancelled for that exact questionId via the existing questionOutcome; a pending event, a missing event in a
     partial page, an unavailable view, or the refusal of an earlier attempt never release it.
     On mount or reconnect the read path reopens a question this run already attempted as `unknown` (reconcilable) rather
     than as a fresh decision, so a same-run reload shows the retained attempt.
     The concurrency guard (`active` ref) makes a second in-flight invocation a no-op, and the old port/question
     completion guard still discards a late result.
   - QuestionCard.tsx: adds the `retention` state (locked, honest message) and an optional `onCheckAgain` action rendered
     only in the unknown state; unavailable / waiting / unknown / retention / error all stay non-editable, while local
     validation problems and proven refusals stay editable. ConversationView passes
     `onCheckAgain={question.retryable ? question.reconcile : undefined}`.
