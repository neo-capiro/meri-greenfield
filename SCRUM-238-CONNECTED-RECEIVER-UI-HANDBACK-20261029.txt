4. WHAT CHANGED (behaviour, not scaffolding)
   Admitted receiver: contracts 0.1.36 carries `answer` (with questionId/answers), `question.pending` and `question.answered`, validated by
   the same generated validators the client already calls.
   Answer disposition (review item 3): capabilities/questions.mjs now exports `answerSelectionRefusal`, the single semantic check of an answer
   against the questions actually asked; `registry.deliver` calls it BEFORE recording anything, so a malformed answer (array on a single-select,
   missing/extra key, unoffered label) returns its code, leaves the question pending and resolves no callback. Dispatch therefore cannot
   acknowledge APPLIED or write a success event for it.
   Admission (review item 4): apps/runtime/product-ports/capability-policy.mjs PREVIEW_PROFILE now admits `userQuestions` (platform maximum);
   tenant/role narrowing and every other flag are untouched. This is source configuration only — no deployed enablement is claimed.
   Card (review item 2): the card's phase is a reducer with `open | waiting | unknown | rejected | local | error`. A local selection problem and
   an explicitly refused answer stay editable and resendable; a delivery the server reports UNKNOWN latches and is never resent under a fresh
   control id; availability is derived from the durable observation (`isSettled(runState)`) and the question's own `expiresAt`, so a settled,
   expired or absent question renders as no longer answerable with an inert fieldset. Selections reset when the question identity changes, and
   the pending question is re-derived from `question.pending`/`question.answered` events, so a reload or reconnect of the same live run
   rehydrates the same card.
   Types: `answerControl` returns the contract's own answer variant and `questionAnswers` returns the contract's option-tuple shape, so the
   client no longer needs a cast at the wire boundary.
