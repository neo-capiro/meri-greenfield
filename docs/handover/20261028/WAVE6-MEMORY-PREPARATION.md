# Memory item 3 — connected source flow

Native `save_memory` prepares the exact normalized text and destination in the existing immutable approval-metadata owner. Preparation creates no candidate. The existing intent journal retains the proposal for review and replay. Current conversation authority, Core membership and destination permissions are checked before retention and release. Changed arguments require a new proposal.

Core [PR219](https://github.com/neo-capiro/capiro-backend/pull/219), merged at `7f0201c45079572ecaff24392f4a98ff6bc54803`, connects approval admission and execution. The existing native database execution transaction owns the current attended session, active membership, conversation selection, client walls, approval/revocation lock and execution receipt. The existing memory receiving owner writes the pending candidate and its content-free submission ledger within that same transaction. It never publishes inline. No schema, migration, alternative candidate writer or new ledger is introduced. The original producer and its historical journal remain unchanged.

Personal, selected-client and canonically permitted firm additions use this path. General cannot target a client; the model cannot choose a client ID. A keyed addition that collides with existing memory is refused: a correction requires a separately reviewed exact target. Fractional TTLs are refused rather than rounded after review. Proposal expiry uses the existing 15-minute native proposal ceiling, bounded by admission expiry, independently of the short preparation request timeout. Fresh authority is still required at every effect and release.

The native approval forwarder uses the existing execute/read endpoints with the original proposal and binding. Core replays the retained receipt, so duplicates cannot create another candidate. Uncertain replies are reconciled by reading the original execution; missing/unknown evidence never authorizes a replacement submission. Both normal and initial-binding metadata custody admit the memory action and retain expired/superseded provenance for reconciliation under a current attended session. Conversation retention checks continue to gate custody and release.

## Receiving contract

Contracts package **0.1.28** adds generated `IntentsNativeMemoryOutcome` to the existing intents result union. UI-stream **0.1.15** adds this contracts version to its peer metadata; UI-stream runtime/declaration bytes are unchanged. Only the canonical intents generator creates its browser bundle, schema, declarations and source metadata. Package lock edits are version/peer metadata only.

The execution receipt has `kind: native-memory`, exact proposal/command/decision hashes, idempotency key, original binding and `completedAt`. That time means candidate submission, never publication. The result has `candidateId`, `candidateSha256`, `reviewId` and `review: {status, decidedAt, publishedMemoryId, checkedAt}`. Candidate ID equals the original proposal ID; its hash binds the exact proposed text, destination and origin.

`review.status` is the current owner-observed `pending`, `approved`, `rejected`, `withdrawn` or `not_found`. Only `approved` with a canonical published memory ID establishes publication. `not_found` reports a removed/unavailable candidate and never causes reconstruction. `reviewId` is an opaque submission correlation in the existing ledger, **not** a `memory_review_request` ID; do not construct an inbox URL from it. Later personal decisions use the existing candidate owner-decision path, while shared review remains with Core's canonical review owners. This native approval approves submission only.

The parent source batch owns the full-content review UI and package pin/provenance integration. Worker text describes an unsubmitted proposal and a later pending candidate accurately. Historical `review_pending` receipts remain readable through their original contract.
