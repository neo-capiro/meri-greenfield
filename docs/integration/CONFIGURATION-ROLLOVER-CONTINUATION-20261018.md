# Conversation continuation across a changed workload — source decision packet

Source base: first-chat PR175 `993f52a97e5d9edcf65c9f89423c097aa52831c7`. The user reports run `64c90145-0350-4d20-8a2e-52472da8b140` as failed with `ATTEMPT_LOST` and next target `5e96fb55-2af3-4343-a0bb-54d7d3f0d60f` as `RESERVED`. This packet uses those observations as input; it makes no live state claim or deployment change. This dedicated branch is separate from PR175 and the retained-read/retention worktrees.

## Exact missing contract

`initial_run_bindings` migration 0017 stores an immutable original `ADMITTED` record with configuration SHA, versions, policy, selected client, original binding and expiry. `initial-run-binding-journal.mjs` only replays a matching proposal. `compilePreparedRunConfigurationSha256` excludes rotating credentials and render-time deadlines but includes image/SDK versions, task request, workload plan, budget/allocation semantics, approved reads and qualification. A changed hash is a changed workload, not a cosmetic deploy.

`next_runs` migration 0009 stores one immutable source-to-target reservation. Only `RESERVED` to `ACCEPTED` is allowed. `next-run.mjs` returns the existing reserved target unchanged, before gathering new settlement; `admitTurn` also returns the prior mapping as a read receipt. The reservation has closed fields and pins the old versions, scopes and policy; it has no configuration-transition field. `next-run-journal.accept` and `.execution` compare the target run to those old pins.

The cold `prepared-candidate.mjs` validates the original admission against its *current* configuration and versions before it selects the reserved target. `prepared-run-registry.mjs` and `prepared-run-bindings.mjs` repeat that comparison. The latter also reconstructs source admission/revocation from the current retargeted allocation, which cannot safely stand in for an older workload's allocation. A one-line relaxation of the configuration check would therefore neither admit the target coherently nor prove old cleanup. PR175 repairs Stop for a matching cohort; it adds no cross-configuration transition authority or historical configuration resolver.

A canonical `RESERVED` row records that the source was terminal and that the reservation owner verified either `FORECLOSED` with exact no-authority evidence or `RETIRED` with physical stop and revocation evidence **at reservation time**. Its journal checks the retirement record and grant IDs, but does not independently read present budget grant states or match the revocation receipt to budget rows. `ATTEMPT_LOST` alone does not identify which branch applied. The saved reservation, allocation and canonical revocation facts must be read back and rechecked before a transition; the revocation owner's explicit `authorityAbsent` proof is valid for a source that never installed grants. Neither a terminal status nor a reserved target settles unknown model/tool cost. The budget owner retains `UNKNOWN` liabilities and a new run must obtain its own capacity/hold under current caps.

## Accepted transition and required source boundaries

The parent accepted **adopting the already reserved, unaccepted target binding** through one versioned, append-only transition receipt. A conflicting second adoption is an explicit HOLD. This first source slice resolves **one adoption per conversation lineage**; a second later configuration transition, even on a different successor, needs a multiepoch contract. The old initial binding, reservation, run/events, allocation, issuance, grants and budget receipts remain immutable historical evidence. Do not reinterpret a replay of the frozen `{conversationId,sourceRunId}` next-turn command as consent to migrate, silently redispatch the failed prompt, reuse an old task/model credential, or invent a checkpoint.

1. Add a distinct trusted transition intent (not an optional field in the old reservation). It names the exact source/target bindings, original admission record SHA, reservation SHA, old configuration/versions and newly reviewed configuration/versions. At explicit user input admission, verify current membership and selected-client authority through the Core identity/context owner; persist only bounded receipt hashes and lineage, never a browser bearer or provider credential. Tenant, actor, selected client, one client scope and current policy must match. A policy/client change refuses pending its own explicit contract. Require a proven retention serving fence; its presence in this first-chat path is not established by this source audit.
2. Claim one immutable transition per target under the existing conversation advisory lock. Re-read the original admission, reservation, latest terminal source and allocation proof. Require the source's exact `FORECLOSED` hash or `RETIRED` physical stop plus a fresh canonical revocation read matching all old grant IDs and the saved receipt, according to the reservation branch. Require the target still `RESERVED`, no accepted run, no `run_issuances` row including `CLAIMED`, no `model_run_issuances` or `native_allocations` row, and no product-budget run, tenant reservation, allocation, grant, request or invocation claims for the target, including UNKNOWN. A `CLAIMED` issuance may already have generated external material. The present conversation advisory lock does **not** cover independent task/model issuer and budget writers. The allocated 0020 source makes each first write take that same lock and compare the immutable transition SHA; the trusted issuer and budget owners must separately compare the full effective descriptor and current accepted Run. If an old write wins, the adoption sees it and HOLDs; if adoption wins, an old writer cannot claim under old pins. An uncertain read or commit refuses; retry returns exactly the same receipt, never a second target. Migration installation and narrow runtime table grants remain separate gates.
3. For this failed source, require `reservation.facts.checkpoint === null`; the successor starts a fresh SDK session on the newly qualified image. Preserve the transcript and conversation-wide event sequence. A completed/checkpointed source with changed runtime versions remains held until checkpoint-format and SDK compatibility are separately qualified. Never claim a resume from the lost attempt.
4. Resolve one canonical effective *target* descriptor under the conversation lock: exact binding, selected client, scopes, policy, effective configuration and versions, original admission SHA, reservation SHA, transition SHA and descriptor SHA. Identity, acceptance, durable issuer intent, registry and execution must consume that descriptor. The accepted adopted target's later successor inherits its new configuration lineage; the original admission remains the historical Stop pin. `context-adapter.mjs` currently rejects an added run-fact key, and 0011 issuer intent lacks a transition digest, so both wire and persisted claim predicates must be revised as one contract. At accept, recheck fresh user Core currentness, the same target receipt, client/policy and source settlement. Issuance, kickoff, bootstrap and output release need phase-specific task-bound currentness checks. Existing marked Meri control identity can read Core identity/context with fresh selected-client checks, and existing preallocation/task-verifier owners bind a run, but these phases do not yet compose an adoption-digest assertion. Keep adopted execution closed until they do. At allocation, effect and release, recheck exact target admission/cap and account for old `UNKNOWN` liability; budget admission does not yet exist at transition claim. Target issuance uses a new single-run capability and model grant. Source `UNKNOWN` budget holds stay in the canonical budget ledger and count against the next run.

5. Before a rollout can strand any live original, preserve an old-cohort **stop-only** path keyed by its immutable configuration/issuance/allocation facts. That path does not exist across changed configurations today: `prepared-run-bindings.mjs` and the registry still compare current config. The allocation journal has hashes and grant identities but not the old allocation JSON or task request bytes; budget only has those bytes after admission. Commit a non-secret historical stop fact capsule before allocation claim, or resolve a verifiable immutable old configuration by SHA. Use the existing allocator and revocation owner for the effect. If an already claimed source lacks those facts and is not proven retired/foreclosed, HOLD; never rebuild old Stop from current task/allocation bytes or reissue a credential.
6. A user must submit an explicit input to the adopted target through existing input admission. The failed prompt remains in history and is not auto-executed. Completion requires a newly qualified image/configuration, fresh authority and budget readbacks, successful streamed answer, saved transcript/reload and stop settlement in the same conversation.

The read-only effective-descriptor resolver is a historical pin lookup, including for old Stop. A descriptor for an old original can remain valid after a later accepted successor. Execution callers must additionally prove canonical current-run state and the exact target acceptance or reservation under the same lock. Before first acceptance or issuance of a RESERVED adopted target, the owner must read the receipt under that lock, check `now < validUntilMs`, and refresh Core authority; historical accepted descendants retain their epoch after this decision deadline. The receipt's Core authority observation must postdate the exact reservation; its digest records lineage but is not itself an authorization signature.
