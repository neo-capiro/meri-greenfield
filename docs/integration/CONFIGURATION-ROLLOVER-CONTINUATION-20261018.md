# Conversation continuation across a changed workload — source decision packet

Source base: first-chat PR175 `993f52a97e5d9edcf65c9f89423c097aa52831c7`. The user reports run `64c90145-0350-4d20-8a2e-52472da8b140` as failed with `ATTEMPT_LOST` and next target `5e96fb55-2af3-4343-a0bb-54d7d3f0d60f` as `RESERVED`. This packet uses those observations as input; it makes no live state claim or deployment change. This dedicated branch is separate from PR175 and the retained-read/retention worktrees.

## Exact missing contract

`initial_run_bindings` migration 0017 stores an immutable original `ADMITTED` record with configuration SHA, versions, policy, selected client, original binding and expiry. `initial-run-binding-journal.mjs` only replays a matching proposal. `compilePreparedRunConfigurationSha256` excludes rotating credentials and render-time deadlines but includes image/SDK versions, task request, workload plan, budget/allocation semantics, approved reads and qualification. A changed hash is a changed workload, not a cosmetic deploy.

`next_runs` migration 0009 stores one immutable source-to-target reservation. Only `RESERVED` to `ACCEPTED` is allowed. `next-run.mjs` returns the existing reserved target unchanged, before gathering new settlement; `admitTurn` also returns the prior mapping as a read receipt. The reservation has closed fields and pins the old versions, scopes and policy; it has no configuration-transition field. `next-run-journal.accept` and `.execution` compare the target run to those old pins.

The cold `prepared-candidate.mjs` validates the original admission against its *current* configuration and versions before it selects the reserved target. `prepared-run-registry.mjs` and `prepared-run-bindings.mjs` repeat that comparison. The latter also reconstructs source admission/revocation from the current retargeted allocation, which cannot safely stand in for an older workload's allocation. A one-line relaxation of the configuration check would therefore neither admit the target coherently nor prove old cleanup. PR175 repairs Stop for a matching cohort; it adds no cross-configuration transition authority or historical configuration resolver.

A canonical `RESERVED` row records that the source was terminal and that the reservation owner verified either `FORECLOSED` with exact no-authority evidence or `RETIRED` with physical stop and revocation evidence **at reservation time**. Its journal checks the retirement record and grant IDs, but does not independently read present budget grant states or match the revocation receipt to budget rows. `ATTEMPT_LOST` alone does not identify which branch applied. The saved reservation, allocation and canonical revocation facts must be read back and rechecked before a transition; the revocation owner's explicit `authorityAbsent` proof is valid for a source that never installed grants. Neither a terminal status nor a reserved target settles unknown model/tool cost. The budget owner retains `UNKNOWN` liabilities and a new run must obtain its own capacity/hold under current caps.

## Minimal production transition, contingent on the decision below

Recommend **adopting the already reserved, unaccepted target binding** through a separate versioned, append-only transition receipt. The old initial binding, reservation, run/events, allocation, issuance, grants and budget receipts remain immutable historical evidence. Do not reinterpret a replay of the frozen `{conversationId,sourceRunId}` next-turn command as consent to migrate, silently redispatch the failed prompt, reuse an old task/model credential, or invent a checkpoint.

1. Add a distinct trusted transition intent (not an optional field in the old reservation). It names the exact source/target bindings, original admission record SHA, reservation SHA, old configuration/versions and newly reviewed configuration/versions. At explicit user input admission, verify current membership and selected-client authority through the Core identity/context owner; persist only bounded receipt hashes and lineage, never a browser bearer or provider credential. Tenant, actor, selected client, one client scope and current policy must match. A policy/client change refuses pending its own explicit contract. Require a proven retention serving fence; its presence in this first-chat path is not established by this source audit.
2. Claim one immutable transition per target under the existing conversation advisory lock. Re-read the original admission, reservation, latest terminal source and allocation proof. Require the source's exact `FORECLOSED` hash or `RETIRED` physical stop plus a fresh canonical revocation read matching all old grant IDs and the saved receipt, according to the reservation branch. Require the target still `RESERVED`, no accepted run, no `run_issuances` row including `CLAIMED`, no `model_run_issuances` or `native_allocations` row, and no product-budget run, allocation or grant rows for the target. A `CLAIMED` issuance may already have generated external material. Acceptance shares the reservation lock; issuer and budget owners need coordinated lock ordering, claim-first predicates and receipt rechecks so adoption cannot race an independent claim. An uncertain read or commit refuses; retry returns exactly the same receipt, never a second target. The migration ID, SQL role and runtime grant must be centrally allocated before writing that journal.
3. For this failed source, require `reservation.facts.checkpoint === null`; the successor starts a fresh SDK session on the newly qualified image. Preserve the transcript and conversation-wide event sequence. A completed/checkpointed source with changed runtime versions remains held until checkpoint-format and SDK compatibility are separately qualified. Never claim a resume from the lost attempt.
4. Make the transition receipt the effective *target* pin at the existing owners: identity selection/currentness, `next-run-journal.current/accept/execution`, run registry, and prepared-run bindings/issuance. Historical original readers validate old pins without treating them as permission for new work or extending old expiry. At accept, recheck fresh user Core currentness, the same target receipt, client/policy and source settlement. Issuance, kickoff, bootstrap and output release must recheck a bounded task-bound Core authority/currentness receipt or a trusted equivalent port; existing registry control/task capabilities do not carry the browser credential used by `conversation-currentness.mjs`, so these later steps stay closed until that port exists. At allocation, effect and release, recheck exact target admission/cap and account for old `UNKNOWN` liability; budget admission does not yet exist at transition claim. Target issuance uses a new single-run capability and model grant; existing issuer compare-or-set refuses drift or partial old issuance. Source `UNKNOWN` budget holds stay in the canonical budget ledger and count against the next run.
5. Before a rollout can strand any live original, preserve an old-cohort **stop-only** path keyed by its immutable configuration/issuance/allocation facts. That path does not exist across changed configurations today: `prepared-run-bindings.mjs` and the registry still compare current config. If a historical qualified configuration or equivalent existing owner cannot be resolved, hold continuation; never rebuild an old stop or revocation using current task/allocation bytes. The reported reserved target is not proof that every older source in the deployment has settled.
6. A user must submit an explicit input to the adopted target through existing input admission. The failed prompt remains in history and is not auto-executed. Completion requires a newly qualified image/configuration, fresh authority and budget readbacks, successful streamed answer, saved transcript/reload and stop settlement in the same conversation.

## Ownership and verification

Extend the canonical initial/next-run journal and existing candidate, registry, prepared bindings and budget owners; do not create a parallel run launcher or grant system. A migration, transition authority and later task-bound Core currentness port are currently **absent**, so no executable source change is safe before the target-identity decision, central migration allocation and port contract. The versioned intent/receipt should be a closed contract owned with conversation transitions. Source tests must exercise old receipt replay, old-to-new image/version adoption only for null checkpoint, reserved-vs-accept/issuance races, lost COMMIT, wrong tenant/actor/client/policy, changed current Core membership, unresolved stop/revocation, UNKNOWN budget liability, no credential reuse, and no old-prompt redispatch. A disposable PostgreSQL role/concurrency/restore control and exact runtime image/config readback are later gates; no live SQL, AWS, prompt or deploy is authorized by this packet.

**Decision requested:** May an already `RESERVED`, unaccepted target keep its exact binding and receive an immutable, target-scoped adoption receipt for a newly qualified configuration/image/versions? The alternative is an explicit supersession contract that preserves this reservation as a tombstone and creates a different target; migration and all current-run readers would be more extensive. Neither behavior is represented by current approved authority.
