## Conclusions

1. There is a real production composition gap for selected structured requests: production does not derive `ProductSession.limits` from the accepted request. Injecting a fixture `BodyLimits` only demonstrates the isolated transport path.
2. It is **not an unconditional plain first-chat blocker**. Ordinary input has `skill:null`; no default Objective output format is selected. Plain chat has no outputFormat. This does not establish the deployed request/configuration or explain dot's separate live startup investigation.
3. A resolver-only fix is insufficient: the product app requires `session.limits == body_limits` globally, and the CLI CountTokens parser also captures a global allowed-tool set. Both must consume the same trusted session-local policy before native/count validation. No global StructuredOutput grant is necessary or appropriate.
4. A valid trusted selected-skill source already exists. Objective has canonical schema/issued-custody readers, but the runtime output-format owner is not composed by production callers at this pin; that path needs explicit existing-owner composition before it can claim production readiness.

## Smallest complete reuse proposal — no edits allocated yet

1. Add a cohesive **trusted output-policy projection** beside product-owner-facts. It takes only owner-read accepted run/request plus already verified original allocation/issuance identity, never inbound worker body. For an accepted selected skill, call existing selectSkill, compare the complete accepted pin, call existing selectedOutputFormat and produce exactly `{toolName:'StructuredOutput',schema:<canonical JSON value>,schemaSha256:<JCS digest>}`. For a positively ordinary request, return explicit null. Unsupported selection or a skill/Objective conflict refuses. Clip its read deadline to current admitted/native owner expiry. This requires no new grant table/migration, schema upload endpoint or global tool grant.
2. Extend the **existing** closed authenticated admission source contract to include that exact policy (or null), bound into sourceSha256 alongside the existing accepted requestSha256. Read it through the existing admitted-grant/accepted-run owner on both admission observations; compare policy on refresh. Use a coordinated closed protocol version change if the tuple shape changes, not an unauthenticated optional field or parallel authority channel. Existing placement consumers and source-field exact-key checks must be updated together; ordinary null is explicit. Data comes only from JS's canonical source, never Python's native request tool/input_schema.
3. In owner_admission.py validate the authenticated field's closed shape/digest/tool name/size, preserve it in reader-owned source bytes; in owner_startup.py derive per-session BodyLimits using the unchanged numeric global caps plus only that request's selected StructuredOutput name/schema. No fresh owner receipt means refusal; count and inference cannot use a previously cached policy after accepted-request/binding drift.
4. In host_composition.py preserve global numeric envelope caps while allowing only reader-owned session-local policy. Replace the equality-to-global-schema fence with appropriate cap invariants and exact owned resolver identity. Resolve one trusted ProductSession before creating the existing count ASGI parser/callback for this HTTP request; use the same session for pre/post currentness checks. Do not globally union StructuredOutput. The count path must compare its StructuredOutput input_schema to the exact same trusted canonical schema, not merely accept the name.
5. Objective support must reuse the existing protected issued-facts/current reader above; a `request.skill===null` check alone cannot prove ordinary when a run-start may mark it Objective. Reuse the canonical positive ABSENT/STARTED distinction. If no genuine protected reader is composed or the read is UNKNOWN, keep that Objective path unavailable. To avoid importing a worker private implementation into proxy, extract the existing pure codec outputFormat projection into the existing runtime Objective contract owner and have both callers use it; no second ModelOutcome schema copy. Retain exact accepted request/issued model and source-admission bindings. This is a dependency/composition task, not permission to call Core, activate Objective or mint new authority.

Likely changed files for an approved implementation: product-owner-facts.mjs; a narrowly allocated trusted-output-policy helper; owner-channel.mjs and coordinated owner_admission.py; owner_startup.py; host_composition.py; count parser/callback; owner-entrypoint.mjs only to compose existing trusted sources; associated focused tests. Existing selected/output-format and canonical Objective schema assets should be reused, not edited to loosen output contracts. Adding fields also affects product-owner-placement.mjs's closed facts validator and owner-channel open's exact key set; those must not be missed.

## Why this does not establish a default first-chat blocker

- service.mjs45-47 creates skill:null unless an explicit supported skill is selected. No Objective inference occurs from prompt text.
- activity.mjs55 mounts skill outputFormat only for a saved skill;76 invokes Objective prepare only when a trusted Objective port exists;77 refuses mixing Objective with lineage/skill.
- objective-generation/runtime.mjs15 returns null when its protected pair is absent. options.mjs51-52 adds format only for that explicit result; objective-activity.test.mjs48-54 asserts plain outputFormat is undefined.
- Actual assembleConversationRunner at conversation-runner.mjs62,81 composes selectedSkills but **does not pass objectiveGeneration**. Repository-wide non-test call-site search finds no createObjectiveGenerationRuntime production caller at this pin. Objective lifecycle/start configuration is separately opt-in and absent means disabled (objective-generation/configuration.mjs1-6,14).

Therefore structured custody is a confirmed selected-request production blocker when that format is used, but plain first-chat remains a separate question requiring dot's actual request/configuration/trace. No production default should be changed to force structured output or grant StructuredOutput globally to address it.

## Required bounded verification after a future authorized repair

- Real selected factory to real accepted-run/persisted model-grant source to authenticated admission tuple to ProductSession to pinned SDK native body, with synthetic provider only; cover both admitted skills and plain null.
- Exact schema/property/JSON-type or tool-name tamper; different request ID with same prompt/schema; cross-run/binding/model-grant mix; policy changes between reads; retirement/expiry after count and before inference. All deny without provider execution/settlement.
- Cross-request concurrency: skill A and B receive only own schemas; plain request never gains either. No module/global mutable policy.
- Count request must reject StructuredOutput without custody, with wrong schema, after expiry and on source failure; count cannot establish authority for inference. Preserve the final-native guard and exact body/cost owners.
- Objective positive STARTED uses the existing exact protected pair/current reader; missing owner/UNKNOWN refuses; definite ABSENT alone is ordinary. Do not weaken earlier Objective attestation/currentness gates.
- Supported focused Python/Node suites and affected semantic types; retain original failed fixture-injection result and production wiring limitations. No model/provider/live Core call needed for local checks.
