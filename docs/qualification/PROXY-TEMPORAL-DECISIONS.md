## Proposed model route

**A new trusted proxy with a new Bedrock ECS task role can meet the architecture without any existing Capiro provider secret.** This is a supported design candidate, conditional on model access and qualification. Keep the proxy in the new environment's trusted service plane; conversation tasks receive a short-lived inference-only proxy credential and no Bedrock, database, Clerk-secret, signing or administration credential. Anthropic recommends keeping provider credentials outside the agent boundary and restricting outbound access at the infrastructure layer. Environment variables alone do not establish isolation. [Secure Agent SDK deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment).

Use a standard gateway implementation rather than writing an inference translator. These alternatives have different downstream authentication:

| Candidate | Verified support | Decision proposed for qualification |
| --- | --- | --- |
| Claude apps gateway, bundled native Linux CLI 2.1.295 | Official gateway exists since 2.1.195, offers Anthropic-compatible inference and Bedrock upstreams. Its documented client login uses corporate OIDC authorization/device flows and gateway sessions. | Useful first-party candidate, but **not selected for unattended conversation workers yet**. The reviewed reference does not establish a supported per-run machine-token issuance flow. Do not copy a developer login, manufacture gateway JWTs or assume arbitrary IdP tokens work. Inspect its supported `/protocol` and demonstrate headless issuance/revocation before adoption. |
| LiteLLM proxy | Official client documentation supports Claude Code's Anthropic Messages path with virtual keys, with Claude upstreams on Bedrock. Provider credentials stay on the proxy. | Recommended machine-token candidate to qualify if the first-party gateway's unattended-auth gap persists. Select an exact release, image digest and notices before implementation. This document does not add an accepted dependency or assume Enterprise features. |

Sources: [Claude apps gateway prerequisites/protocol](https://code.claude.com/docs/en/claude-apps-gateway), [LiteLLM client setup](https://docs.litellm.ai/docs/proxy/client_setup/overview).

The first-party gateway explicitly supports empty Bedrock `auth: {}` using the AWS credential chain, including ECS task roles. Its IAM instructions name `bedrock:InvokeModel`, `bedrock:InvokeModelWithResponseStream`, and `bedrock:CountTokens`; inference profiles also require the underlying foundation-model ARNs. Its OIDC session defaults to one hour; group changes propagate at session refresh. That is not a 30-second business-policy revocation guarantee. [Gateway configuration](https://code.claude.com/docs/en/claude-apps-gateway-config).

Anthropic publishes an ECS Fargate/RDS/internal-ALB example, but labels it a worked example rather than a supported production deployment. Use its architecture as documentation only; do not import its existing-network assumptions. All VPC, roles, databases, secrets, certificate configuration, buckets, logs and images here must be newly owned. [Official AWS example](https://code.claude.com/docs/en/claude-apps-gateway-on-aws).

LiteLLM's virtual keys require its own Postgres state and a trusted management credential. Keys can have model allowlists, expiration, budgets and route restrictions. Owner-role inheritance can give a key management access: explicitly restrict `allowed_routes`, avoid admin-owned worker keys, and deny `/key/*`, `/user/*`, `/team/*`, UI, MCP and arbitrary passthrough routes at the worker ingress. Expiration/metadata alone do not bind a token to a live ECS task. A trusted broker must associate issuance with the frozen task/run capability and enforce active-run revocation. Prove key deletion/cache behavior and fail-closed database failures. [Virtual keys](https://docs.litellm.ai/docs/proxy/virtual_keys).

LiteLLM documents Anthropic `/v1/messages` on Bedrock, tool calls and fine-grained tool streaming. Its routes differ in provider translation; qualify the actual selected path with the pinned CLI, not merely a generic chat completion. [Bedrock provider integration](https://docs.litellm.ai/docs/providers/bedrock). JWT/SSO and key rotation may require Enterprise licensing; avoid silently depending on them. Creating a fresh expiring virtual key per task is the proposed baseline, subject to the selected release's API verification. [Client authentication feature limits](https://docs.litellm.ai/docs/proxy/client_setup/overview).

## Exact SDK connection and isolation settings

This is configuration design, not product code. Do not supply host `process.env` wholesale. TypeScript `options.env` replaces the child's environment, whereas omission inherits it. Construct an allowlist with required runtime paths/home, dedicated configuration directory and the following deliberate values. [Agent SDK gateway environment behavior](https://code.claude.com/docs/en/llm-gateway-connect).

| Setting / option | Proposed use and verified semantics |
| --- | --- |
| `ANTHROPIC_BASE_URL` | Private HTTPS origin of the new Anthropic-compatible gateway; the client appends the Messages endpoint. This selects the client wire format even when the upstream is Bedrock. |
| `ANTHROPIC_AUTH_TOKEN` | Sends `Authorization: Bearer`; contain only the new short-lived inference credential. `ANTHROPIC_API_KEY` instead sends `x-api-key`; do not set both as an accidental fallback. |
| `CLAUDE_CONFIG_DIR`, `options.cwd` | Dedicated per-conversation configuration and work directory, stable logical path across an authorized checkpoint restore. No host credentials, prior tenants, auto-memory or global plugins mounted. |
| `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` | Suppress documented background traffic; firewall remains authoritative. |
| `settingSources: []` | Exact 0.3.295 spelling. Disables filesystem settings sources; omission loads defaults. |
| `settings: { autoMemoryEnabled: false }` | Exact declared setting. Canonical business memory stays behind the new governed tool boundary. |
| `model`, `maxTurns`, `maxBudgetUsd`, `abortController` | Declared SDK options. Freeze exact model/profile mapping and limits; SDK budget/turn controls complement trusted admission and wall-clock enforcement. Estimated SDK spend is not the provider invoice or a cross-resume tenant budget ledger. |
| `includePartialMessages: true` | Declared option yielding `stream_event` in addition to complete assistant/result messages. Transport must preserve final messages and avoid treating deltas as completed tool calls. |
| `resume`, `sessionStore`, `persistSession`, `enableFileCheckpointing` | Resume by broker-authorized exact session ID. External transcript mirroring requires local persistence and cannot combine with SDK file checkpointing in the pinned candidate; use independently verified workspace snapshots. |

The API/header/environment behavior above is documented in [gateway connection](https://code.claude.com/docs/en/llm-gateway-connect); SDK option names were independently checked against the exact tarball. Stream semantics are documented in [SDK streaming output](https://code.claude.com/docs/en/agent-sdk/streaming-output). No consumer claude.ai login, personal subscription token or existing developer profile is a product credential; the SDK overview directs third-party products to API authentication unless otherwise approved. [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview).

Alternative provider-format route, if an adopted gateway supports it: `CLAUDE_CODE_USE_BEDROCK=1`, `AWS_REGION=us-east-1`, `ANTHROPIC_BEDROCK_BASE_URL=<new gateway>`, `CLAUDE_CODE_SKIP_BEDROCK_AUTH=1` and the gateway `ANTHROPIC_AUTH_TOKEN`. Skip-auth is needed to retain that bearer header. This avoids asking a conversation worker to obtain AWS signing credentials; the trusted proxy signs upstream. It is an alternative requiring separate protocol tests, not an additional production route. [Provider-format proxy configuration](https://code.claude.com/docs/en/llm-gateway-connect).

For the proposed Anthropic Messages path, the gateway must preserve supported beta/version information, tool blocks, usage and streaming event order, including final `message_delta`/`message_stop`; avoid buffering and preserve or emit heartbeat pings. Translation from Bedrock's binary event stream needs explicit testing. Bedrock-format passthrough must retain `application/vnd.amazon.eventstream` rather than converting to SSE. Anthropic-format clients can send features the upstream does not support; reject unsupported features visibly rather than strip them. Fast-mode and WebFetch checks can contact Anthropic directly, so disabling features and network denial are necessary. [Gateway protocol requirements](https://code.claude.com/docs/en/llm-gateway-protocol).

Bedrock has provider feature differences, including unavailable built-in WebSearch. Use the separately qualified public browser/search tools; do not widen worker access to restore a missing model feature. Pin dated model IDs or immutable inference-profile mappings and inspect destination regions before choosing cross-region inference. [Claude Code on Bedrock](https://code.claude.com/docs/en/amazon-bedrock).

## Model access and remaining qualification evidence

The AWS account/region are approved; the exact provider/model route and qualification spending ceiling are unresolved. A new role does not create account model entitlement. AWS documents Anthropic first-use requirements, Marketplace activation and separately controlled account access; `GetFoundationModelAvailability` can report agreement status. Runtime invocation roles need not retain subscription permissions after activation. This research did not activate anything or query account entitlement. [AWS model access](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html).

Proposed bounded evidence before proxy acceptance:

1. Record image digest, SDK hash/bundled binary, gateway release, model/profile ARNs and effective IAM policy; confirm the gateway has no Capiro-source permissions and the conversation task has no upstream/admin role or key.
2. Demonstrate headless token issuance, exact allowed model/routes, expiration, revocation of a running task, rejection after executor replacement, cross-task reuse rejection and fail-closed proxy-state outages. Caller-supplied tenant headers are attribution only.
3. Complete real SDK text plus local tool-result round trips, MCP calls, long thinking/tool-input streaming, usage/cache accounting, cancellation, 429/5xx retry behavior and interrupted streams. Reconcile repeated model requests against task budgets.
4. Inspect effective Fargate controls and probe denial of direct model/provider APIs, metadata credentials, Capiro private networks, source databases and management endpoints. Public browser access must traverse its separate qualified egress policy, not create a bypass to these destinations.
5. Kill the conversation task, authorize a replacement, restore transcript plus filesystem checkpoint and resume the exact session. Confirm old credentials fail and no duplicate command executes. Preserve all negative results.

Sessions preserve conversation history, not filesystem state. Use stable store keys/logical `cwd` and exact session IDs rather than most-recent-session continuation across users. [SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions). The official SessionStore can continue after a failed mirror batch, reporting `mirror_error`; deduplicate by entry UUID and fail closed when the application's expected remote checkpoint is absent. Require subagent transcript enumeration if subagents are enabled. [External session storage](https://code.claude.com/docs/en/agent-sdk/session-storage).

## Production Temporal candidate

**Proposed server pin: Temporal 1.32.1**, the upstream latest stable release returned by the official GitHub API on 9 October 2026: published `2026-10-08T21:56:07Z`, `draft=false`, `prerelease=false`, release branch `release/v1.32.x`. Resolve and record the platform-specific `temporalio/server:1.32.1` digest before deployment; a tag alone is not the immutable runtime pin. Pair schema tooling with the same release and pin all participating `@temporalio/*` TypeScript packages to **1.24.0**. [Server release](https://github.com/temporalio/temporal/releases/tag/v1.32.1), [TypeScript release](https://github.com/temporalio/sdk-typescript/releases/tag/v1.24.0).

Official Worker Versioning minima are Server 1.29.1 and TypeScript 1.12, so these candidates exceed the documented feature floors. That supports the proposal; it is not a certification of this exact pair. A real TLS connection, workflow/activity/signal/timer/schedule run, worker restart and history replay must pass with the pinned images. [Versioning requirements](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning).

### New topology

Propose private ECS Fargate services for Temporal frontend, history, matching and internal server worker roles, with service discovery and independently scalable replicas across Availability Zones. The application orchestration/activity workers are separate trusted services. Conversation/browser/artifact executors do not poll Temporal directly and receive no Temporal administration credential. Only trusted orchestration clients reach frontend gRPC; administrative tooling and optional UI use restricted operator access. Server internode membership/RPC paths must be tested under Fargate replacement, not inferred from a single-process smoke test.

Use `temporalio/server`, explicit production configuration and a migration task; do not qualify `temporal server start-dev`, embedded SQLite or auto-setup convenience containers as production. [Self-hosted deployment](https://docs.temporal.io/self-hosted-guide/deployment). Size replicas, database connections, CPU/memory and fixed history-shard count from declared pilot load and load tests, with queue-latency/backlog/database/storage alarms. [Production checklist](https://docs.temporal.io/self-hosted-guide/production-checklist).

Propose a **new encrypted RDS PostgreSQL Multi-AZ deployment**, private and reachable only from trusted Temporal services and a separate migration role. Use separate logical databases `temporal` and `temporal_visibility` on the same RDS deployment for a recoverable snapshot boundary. Keep model-proxy state and application state in separately authorized stores. No existing Aurora endpoint or database principal is reused. PostgreSQL 16 is a candidate major; discover and freeze a currently available exact AWS minor before provisioning and qualify it with these schemas.

Use the `postgres12` plugin for both stores and advanced SQL visibility, with matching release schema trees. PostgreSQL 12+ supports advanced visibility. [PostgreSQL visibility](https://docs.temporal.io/self-hosted-guide/visibility/postgresql). Read-only GitHub inspection at tag v1.32.1 observed schema directories through **primary v1.19** and **visibility v1.14**; verify required versions against the exact image/tool before migration. [Pinned primary schema](https://github.com/temporalio/temporal/tree/v1.32.1/schema/postgresql/v12/temporal/versioned), [pinned visibility schema](https://github.com/temporalio/temporal/tree/v1.32.1/schema/postgresql/v12/visibility/versioned). Server runtime roles receive data privileges, not unrestricted schema administration.

### Transport, authentication and authorization

Require TLS with hostname verification to RDS and frontend, and mTLS on internode and trusted-client traffic. Separate private trust roots/leaf credentials and rotation from any Capiro credentials. The official security guide distinguishes encryption from API authorization; namespace roles are `read`, `write`, `worker`, `admin` in verified token permissions. Private networking and UI login alone do not authorize the API. [Temporal security](https://docs.temporal.io/self-hosted-guide/security).

Use built-in `global.authorization.authorizer: default` and `claimMapper: default`, an explicit nonempty `audience`, dedicated trusted JWKS URLs and nonzero key refresh. Empty authorizer permits all requests; empty audience disables that check. Do not assume issuer-string validation beyond the selected plugin's tested behavior. Configure internode certificates on every server role, including frontend. `numHistoryShards` is fixed after first boot; select it deliberately before initialization. [Configuration reference](https://docs.temporal.io/references/service-configuration).

Proposed new workload issuer/credentials grant orchestration clients namespace write, application workers namespace worker, and operators separately issued administration rights; test each required API rather than broadening to system admin on failure. No signing key is distributed to clients. Pin namespace/task-queue routing on the trusted side. Temporal namespace permissions do not enforce business tenant/client walls; every source/tool/command still requires the new gateway's current authorization. Avoid private source text, credentials and artifact bodies in histories or visibility attributes; record authorized object references and minimal run metadata. If payload encryption is needed, qualify an upstream codec in the trusted plane with backup/key retention.

### Backup, restore and compatibility

RDS automated backups/PITR protect the whole instance, including both logical Temporal databases. Configure a nonzero retention period, encryption/key retention, storage alarms and pre-upgrade snapshots. AWS warns backups do not run while the instance is unavailable or storage-full. [RDS backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html). PITR creates a new endpoint; restore to new isolated resources and validate security configuration rather than assuming original networking/settings are reproduced. [RDS point-in-time restore](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html).

Proposed recovery exercise: stop admissions; restore both stores to one point; restore matching server/configuration/worker images and necessary KMS/certificate material; verify open histories, timers, schedules and visibility consistency; reconcile SDK checkpoints, object versions and command receipts; then allow selected synthetic runs to resume. Keep external/source writes disabled until authoritative command outcomes are reconciled. A restored history may retry an activity whose external write succeeded after the backup point, so backup restoration does not replace executor idempotency. Measure actual RPO/RTO and document endpoint switching. Temporal history/visibility archival supports retention; it is not a full service/database backup. [Temporal archival](https://docs.temporal.io/self-hosted-guide/archival).

Before server upgrades: snapshot and rehearse on an isolated restore; upgrade required database schemas first, then the server; advance sequential minor versions and latest patches, allowing history-shard metadata processing between versions. Do not promise schema downgrade or instant rollback to an old image after migration. [Server upgrade procedure](https://docs.temporal.io/self-hosted-guide/upgrade-server).

For new application workflows, propose Worker Deployments with **pinned** workflow versions and retained old worker images while their executions remain live. TypeScript configuration uses `workerDeploymentOptions.useWorkerVersioning` and `version: { buildId, deploymentName }`. Independent inspection of the **v1.24.0** source confirms these fields and also requires `defaultVersioningBehavior` when `useWorkerVersioning: true`; the current documentation example omits that required field. Set a deliberate pinned default and compile against the exact installed package rather than copying the example. [Worker configuration](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning/configure-worker), [pinned 1.24.0 option definitions](https://github.com/temporalio/sdk-typescript/blob/v1.24.0/packages/worker/src/worker-options.ts). Move long-lived runs at explicitly tested Continue-as-New boundaries; use deterministic patching where auto-upgrade is required. Replay stored histories before rollout, including retry/cancel/replacement/approval and schedule fixtures. [Workflow versioning](https://docs.temporal.io/develop/typescript/workflows/versioning). Keep the SDK runtime/checkpoint format and workspace skill manifest bound to the run's immutable executor version; a Temporal worker upgrade does not establish SDK session-format compatibility.
