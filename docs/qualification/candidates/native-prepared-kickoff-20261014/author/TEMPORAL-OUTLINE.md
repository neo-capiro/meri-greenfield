# Prepared-task Temporal kickoff outline

Pinned base: PR80 d0ff0928509edf46cdda211622eb0037e2c098fa, dedicated `/workspace/meri-prepared-kickoff` worktree.

Canonical allocation/admission remains `allocateRemoteNativeController` and the existing allocation journal. SDK descriptor prepare/consume/STARTED remains the existing preparation authorizer and launchBinding in that same journal. The conversation task retains one actual SDK Query and native CLI. The existing execution broker owns native readiness, polling and physical-stop acceptance. Temporal retains deterministic orchestration and one-attempt durable activities; it does not run an SDK/model loop.

Owned modules: `prepared-kickoff.mjs` supplies one original-task Runner gate and the finite startup observer; `prepared-kickoff-http.mjs` supplies role-separated control HTTP adapters and the concrete private task readiness/release client; `temporal-worker.mjs` opts prepared activities into kickoff/status before existing broker polling, preserving legacy default startup. Parent owns configuration, native-controller, task bootstrap, remote composition and task-local listener/gate composition.

Proposed ports: Runner gate wait/release/readiness/close, guarded by the existing task-capability preparation authorizer's admitted proof. Control caller supplies only the pre-existing scoped control capability to the private exact-original task gate. Task caller receives only its original task capability. Gate release does not confer model/tool authority; actual native release still requires canonical descriptor latch, current admission and original execution start barrier.

Kickoff returns the exact original binding/execution/lease receipt for a bounded owned startup attempt. Its volatile Promise prevents overlapping effects; it creates no journal. The startup sequence calls the borrowed canonical allocation owner once, waits for task-resident gate readiness using read-only probes, and sends one release request, then waits for the existing canonical STARTED record under that same finite lease/deadline. Lost/failed release is UNKNOWN and never replayed. Status reads the existing allocation journal; it does not call broker.start. Only persisted launchBinding STARTED permits the existing broker.poll call, which proves native readiness or a completed run's physical stop. A fast completed native run must not be rejected merely because it is no longer executing.

The finite startup has its own original-lease deadline so HTTP kickoff can return within the existing native client's three-second request guard while Temporal continues heartbeats/status polling. Cancellation/stop aborts that owned attempt and invokes the borrowed controller's latched physical cleanup. Parent confirmed this prompt-ACK arrangement before production implementation; no new durable owner or detached scheduler is proposed.

Verification: role separation and malformed originals; one allocation/release under concurrent calls; no readiness/start before allocation; canonical STARTED before execution polling; terminal stop proof; cancellation/expiry/lost release; actual local HTTP gate and task-resident filesystem/process fixtures where useful; existing Temporal/activity compatibility checks. Local synthetic authority/SDK fixtures do not establish AWS, real Temporal, deployed isolation or provider acceptance. No AWS/provider calls, new credentials, security changes, lockfile edits or dependency installs are authorized in this slice.
