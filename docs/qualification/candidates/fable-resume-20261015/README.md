## Next-turn rehearsal with the real CLI (dot task 6, local part): written, blocked on a provider stand-in binding

`scripts/qualification/first-chat-rehearsal/composed-next-turn-rehearsal.mjs` composes two prompts in one conversation at the pin over the real control plane: the real store, the opaque session owner with dot's next-run selector (`createPreparedCandidateIdentity` with `createNextRunOwner`), the conversation and lifecycle services, the worker run application, one admitted-task authority and one budget admission per run over the local budget rows, dot's completion capture with immutable-object readback, the next-run reservation and acceptance through the real session issuance and `submit`, grant revocation through the real budget admission, and the second run's continuation restore of the first turn's checkpoint, with the real CLI launched through the remote task worker and the runner on the lifecycle path. Shared helpers moved to `rehearsal-support.mjs`; the first-chat rehearsal imports them and still passes (`rehearsal/composed-refactored.json`, 2/2).

Finding, retained as `rehearsal/next-turn-1.json` and its stdout: on the lifecycle path the SDK streams every prompt as a client-composed user message. Unlike the string-prompt path, the CLI never handles such a message locally, so the zero-turn `/status` trick does not apply: the first run reached `running`, the CLI mirrored 19 transcript entries, then retried the unreachable synthetic proxy until the activity deadline and the run ended `EXECUTION_STOPPED` with no completion. Every lifecycle-path turn therefore needs the configured proxy host to answer. The product launch environment is fixed by the option builder (five keys, no CA variable), so a local stand-in can only be trusted by mapping the proxy host to loopback and trusting its certificate at host level. That host change was refused by this session's permission policy (TLS trust change), and it is in any case an environment-owner action, so it was not made.

What is in place: `provider-standin.mjs`, a qualification-only HTTPS Messages stand-in that answers `POST /v1/messages` with one canned streamed reply, contacts no provider and carries no credential; and a fail-closed preflight in the rehearsal that probes the configured proxy host before any allocation or launch and refuses with `REHEARSAL_PROVIDER_STANDIN_REQUIRED` otherwise (`rehearsal/next-turn-preflight.json`, refused in 0.4 s with `ENOTFOUND`, nothing allocated). Running the rehearsal to completion needs an environment owner to bind `proxy.synthetic.invalid` to the stand-in and trust its certificate in a disposable environment, or an approved provider route; neither is a product change. The database state the failed run left behind is truncated by the fixture on the next run and no process survived it.

The tagged `deps/zlib/gzwrite.c` is byte-identical between v24.21.0 and v24.22.0 (sha `2ce78329…`, 22,721 bytes). Compared with the upstream file at madler/zlib `df84af25`, the inspected tags lack the two reset assignments (`avail_in = 0`, `next_in = state->in`) that commit `df84af25` introduces on the failed `gz_comp` path in `gz_write`; the file diff also shows a `next_in == NULL` guard and an early `return state->err` after the stalled-write error in `gzvprintf`, which belong to the wider upstream history between the two files and are not attributed to `df84af25` here. What this establishes: the current candidate's security HOLD remains justified by the two inspected sources; it does not prove that no fixed Node 24 base exists anywhere, and no binary, image, scan or admission was inspected or produced.
