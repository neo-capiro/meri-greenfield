## Approved ACH policy and remaining owner contract

Figma pending ACH says two profiles were added and users can keep working. Returned ACH says the profile remains active, gives **five business days**, then changes to **read-only**. Candidate 372 intentionally withholds paid entitlement until exact authoritative invoice/intent payment evidence. Canonical lifecycle instead uses configurable whole-tenant past-due lockout, default 14 elapsed days.

**Human decision relayed by root on 2026-10-11: grant capacity ONLY after confirmed payment.** This is an approved departure from the Figma provisional-access copy. Processing/pending ACH must not grant the added capacity or show profiles as successfully added. The five-business-day grace is not a prerequisite for granting processing capacity, because processing grants none. The earlier proposed provisional-access policy question is resolved and must not be asked again.

Confirmed payment does not make later reversals impossible. The billing owner still needs to define authoritative reversal/chargeback events, reconciliation and the applicable later access/lockout policy. Do not invent a five-day or fourteen-day purchased-profile policy from these conflicting references, and do not present the existing tenant lifecycle as a verified returned-payment contract.

Also needed for CORE-079: does the annual-firm choice co-term the added slot to the existing renewal, or create a separate monthly item/subscription? Supply approved catalog/interval semantics before expanding the monthly-only candidate.

## Independent composition and remaining owner work

The independently usable action is **Manage billing** as authorized navigation to the explicitly configured existing app's `/settings/billing`. It must not automatically open a provider session, change capacity, label a purchase successful or substitute for inline confirmation. Deployment configuration must supply an approved return origin. Once inline payment is activated, external Portal/dashboard updates must participate in the owner's publication/recovery protocol; do not assume provider CAS or exclusive writers.

At frontend `1c0b18a`, `shared/api/proxy.ts` omits `billing` from Core permitted roots, so actual state/summary proxy requests are refused before forwarding. Component interception did not exercise this boundary. Root was notified and owns the narrow GET-only state/summary correction plus proxy tests; this discovery report does not claim the correction is applied. No Onboard origin/service is currently configured in this frontend. A future direct Portal/payment adapter requires a reviewed Onboard origin/proxy and safe returned-URL handling; it cannot be routed to Core by name.

PR 2370 activation remains owned by Billing + Core conversion + database owners. Exact confirmation consent is not dispatch proof. Remaining dependencies include global quantity/status publication fencing (including external writers), unknown preparation/payment reconciliation, invoice compensation/abandonment, one-time receipt consumption with tenant-wide capacity reservation across all client-create paths, persistence allocation, route registration and live sandbox SCA/webhook verification. A prospect lock does not serialize tenant capacity. Current candidate's `default_incomplete` preparation changes provider quantity before payment; `pending_if_incomplete` is not a drop-in remedy because it can collect before exact actual-invoice consent. Prior pending-update discovery is preserved separately.
