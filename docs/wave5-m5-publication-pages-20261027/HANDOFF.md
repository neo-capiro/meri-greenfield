## Design and ownership

The implementation outline was sent to root before edits. The existing publication/S3 owner now reads both legacy monolithic and paged roots. Adjacent `artifact-publication-pages.mjs` owns only an immutable publication B-tree, `s3-artifact-publication-pages.mjs` binds its pages to the existing bucket/purpose/native verifier, and `artifact-publication-paged-journal.mjs` owns publication decisions and indexes. Each page has at most32 entries/references and8MiB; internal references bind canonical content hash, exact native VersionId, first/last key, subtree count and height. Point/range traversal is bounded by tree depth and the requested page. Current tenant root CAS remains the sole publication operation; orphan immutable pages grant no publication or authority. Pages are not a new reservation ledger, authority registry or tenant inventory.

The private indexes retain exact original decisions and receipts, current artifact heads, immutable history sequence, creation ordering and object/conversation lookup. Old ordering is preserved. Creation-order entries for superseded versions are skipped against the current head. A page scans at most the requested number of candidates; an empty authorized page can truthfully have a continuation. No hidden count/total is returned and no complete-library claim is made until the snapshot is exhausted.

`postgres-paged-publication.mjs` compares each nominated SQL row and current head to canonical point proofs. Repair is limited to the nominated version and its current head, under the existing journal/exclusion and artifact advisory lock. Immutable mismatches, unknown heads and terminal/suppressed subjects cannot be repaired into valid publication. Explicit `recoverPage` provides bounded snapshot continuations for metadata repair; a partial repair page never certifies a complete purge inventory. Preview prerequisite recovery nominates its retained exact versions under the same existing exclusion. Existing legacy complete-partition logic remains only for legacy roots; it is not copied into the paged path.

`library.mjs`, `history-page.mjs` and the existing service dispatch use the new bounded ports. Every library row still receives fresh per-origin Core authorization before SQL repair/metadata release and again at release; colleague/private/client walls and unknown-authority refusal remain. Direct inspect/download/history scope fences remain unchanged. The64-hex public cursor envelope is unchanged: a masked64-bit position plus192-bit digest selects a page bound to the exact root/query/caller, rather than searching all possible offsets. It grants no authority; every page reauthorizes. Cursor/source changes invalidate continuation.

Coordination: M5 owns the service `read()`/private `revisionSource()` return span. This slice changes only its agreed recovery call to `recoverTenant(life,context,versionId)`; the helper uses targeted recovery when supported. M5 also owns the rest of `product-ports/documents.mjs`; our single coordinated custody-field addition forwards `publicationPagedWrites:declared.publicationPagedWrites??false`. M7 run-history/routines/public contracts remain disjoint. The previous MM10 preview source, immutable contracts0.1.23/UI0.1.10 archives and all other checkouts remain preserved.

1. Deploy and qualify a dual-format reader/writer release first while `artifacts.publicationPagedWrites` is absent/false. This is the minimum rollback binary for any later upgraded tenant. Verify its actual source/image/config binding through Release; a source commit alone is not that receipt.
2. Retain that compatible binary/image/config as the rollback floor. Never label an old monolithic-only binary compatible with a paged root. The focused witness proves the old reader refuses v2.
3. After a separately coordinated activation decision and idle/exclusive release window, enable the closed trusted write switch and invoke the private canonical owner's explicit `upgrade(expectedPositionSha256)` for a selected actual tenant. This is not a public route/body or an automatic size fallback. No upgrade invocation or config change was performed by this task.
4. Upgrade validates the complete bounded legacy root, bulk-builds immutable pages with at most four native writes/readbacks in flight, and performs one exact-position root CAS. The old root's native VersionId and canonical hash are retained as provenance; all prior native versions remain untouched. A failed/uncertain page write never advances the root. Uncertain root ACK requires canonical read/reconciliation, never an assumed failure or blind republish.
5. Roll back only to the qualified dual-format floor with compatible v2-write configuration. Disabling the write switch leaves v2 reads available and v2 writes refused; it is a write hold, not a format downgrade. Do not overwrite the current root with its old snapshot after later decisions. No reverse migration, object deletion, snapshot rewrite or live schema migration is included.
