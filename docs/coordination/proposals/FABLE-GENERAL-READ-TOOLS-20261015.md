# General read tools for ordinary Meri conversations (design proposal)

Date: 15 October 2026. Lane: Fable P3, branch `fable/p3-general-reads-design-20261015`, base `6d9bb391` (`fable/p1a-sdk-capabilities-20261015`). This phase covers inventory, mapping and design. It implements no server, enables no source and changes no contract, catalog, lockfile, migration or deployment. Everything below is a proposal for dot/Codex review. **Nothing in this document is live.** All 97 operation contracts are `availability: unimplemented`, `qualification: pending`, `handler: null` (see the inventory's `counts.operationsByAvailability`).

Machine-readable inventory: [`general-reads/inventory.json`](general-reads/inventory.json), generated by `node scripts/general-reads/cli.mjs --write` and guarded by `node --test scripts/general-reads/inventory.test.mjs`. That test fails if the inventory drifts from its sources: `packages/contracts/retrieval-0.2/catalog.json`, `docs/CAPABILITY-SCOPE.md`, `packages/skills/assets.json` plus every manifest it indexes, the gateway dispatch profile list, the worker's admitted-skill list, and the two curated inputs `scripts/general-reads/adapters.json` and `product-routes.json`.

## Product owner direction (binding)

Neo, 15 October 2026. Meri must not need a preselected workflow skill to search Capiro data. Skills guide how tools are used; they are not the only route. Approved with these requirements:

1. Reuse the existing typed gateway adapters (`apps/gateway/sources/*`), their authorization checks and the gateway execute path that `apps/worker/conversation/skills/mcp.mjs` (`meri_original_reads`) already uses. One SDK in-process MCP server (`createSdkMcpServer`) for general reads is acceptable. There is no second data-access layer and no generic SQL/query escape hatch.
2. A read becomes available in ordinary conversations, with no skill selected, only once it is both implemented and qualified. Availability is filtered by the current user's and client's permissions and by the capability policy. An unavailable tool is either absent from the tool list or returns a closed, explicit unavailable error. It is never a successful empty result.
3. Writes and external actions stay on the governed command path. Every product operation (create a document, spreadsheet, slides or analysis; schedule, inspect, update or cancel work; create or update a task proposal; propose a memory change; read or save chat attachments) still needs a supported conversational route, even where it is not a raw model tool.
4. "Reachable through skills" means source-level wiring only until an actual SDK → gateway → backend test proves it. Nothing here is called live.

## 2. The general read server

### 2.1 Name, tools and descriptions

- **Server:** one `createSdkMcpServer({name:'meri_reads', version, instructions, tools, timeout})` per run. It is constructed only when the resolved policy enables general reads and at least one read is available. Otherwise no server is mounted, and the existing default prompt ("No institutional source tool is enabled…") stays true.
- **Tool names:** `mcp__meri_reads__<operation id with "." replaced by "_">`, reusing `sdkToolName` from `skills/mcp.mjs` (for example `mcp__meri_reads__mail_read_thread`, `mcp__meri_reads__search_congress_bills`). Legacy aliases are never exposed as names. The build refuses name collisions, and any name in the 43-name exclusion list fails the guard.
- **Descriptions** are derived only from the catalog descriptor, never hand-written:
  - `displayName`, then `whenToUse`.
  - `limitations`, bounded, under a "Limits:" heading.
  - `negativeExamples` as "Do not:" lines.
  - The canonical input schema id and SHA-256.
  - The fixed sentence "Supply literal arguments only; credentials and scope authority remain with the gateway."
- **`searchHint`** comes from `positiveExamples`. Annotations: `readOnlyHint:true`, `destructiveHint:false`, `idempotentHint:true`, `openWorldHint:true`.
- **Tool loading:** when the available list is small (at most 24, the current skill tool-call ceiling) the server sets `alwaysLoad:true`. Above that, tools are deferred behind SDK tool search with `searchHint`. This is an assumption to verify in qualification; tool-search behaviour is unproven here.

### 2.2 Input and output schemas

- **Input:** the canonical contract input schema, resolved by id from the schemas the retrieval validator already loads (`packages/contracts/retrieval-0.2/validate.mjs`; non-retrieval domains are located by `execution-schema-sources.mjs`), with `$ref`s inlined and then converted to the SDK's Zod raw shape with `z.fromJSONSchema`. Zod 4.6.7, present in the worker's resolved dependencies, exports it. Conversion of these `$ref` graphs is unverified.
  - The qualification test must assert that the JSON Schema the SDK advertises is equal to or narrower than the canonical schema.
  - The SDK silently drops a tool whose schema it cannot convert (`CLAUDE_SDK_MCP_TOOL_SCHEMA_UNCONVERTIBLE`). The build must therefore treat any dropped tool as a configuration failure.
  - Fallback: the existing `{arguments: record}` envelope that `meri_original_reads` uses, with the schema id in the description.
  - Either way, the gateway re-validates (`assertOperationArguments`, `normalizeInput`) and rejects argument-borne authority (`rejectArgumentAuthority`). The SDK schema is only advisory.
- **Output:** the gateway's canonical closed wrapper `{binding, subject, operation, argumentsSha256, result}`, returned as one text block. It is bounded by `maxOutputBytes`. It is never rewritten. Any notices go in a separate content block (§5).

### 2.3 Availability: which reads appear

The tool list is the intersection of six gates, computed once per run (and per resume or fork) from trusted inputs only. Model and UI hints never take part.

1. **Contract:** catalog descriptor with `sideEffect:'none'` and `approvalBoundary:'none'`. `createInstalledRuntimeCatalog` already enforces this.
2. **Implemented and qualified:** a current installation receipt from the native qualification owner (handler `sourceSha256` measured from files, unexpired), as in `createSelectedSkillInstallationOwner.readForSkill`. Repository flags, the catalog `state` and inventory rows never count. Until the contract owner records a qualified descriptor and the native owner issues a receipt, **zero reads are available**. That is the current state.
3. **Capability policy:** proposed `generalReads:true` and the operation's family in `readFamilies` after `resolveCapabilityPolicy` (platform maximum ∧ tenant settings ∧ role ceiling ∧ tenant role narrowing; flags AND, lists intersect). See P8.
4. **Actor and tenant eligibility:** a gateway discovery decision. `createToolDispatch.discover()` returns `[]` today, with the comment "No exposure until a separately qualified discovery grant contract exists". This needs P1. Eligibility means the claims carry `tool.read`, the business policy grants the operation's `requiredGrants` to this actor/role, and the operation's sources are enabled for the tenant.
5. **Client scope:** operations whose adapter requires a client subject (`actions.query`, `get_client_context`, `read_client_documents`, `query_action_items`) are listed only when the run carries an authorized client scope. No client is implicitly selected. Operations with an optional client (meetings, contacts, memory proposals) are listed, but a model-supplied `clientId` grants nothing: the gateway's subject checks decide.
6. **Exclusion:** the 43 deferred names are never registered.

Gates 3 to 6 are coarse pre-filters. **Per-call authorization stays authoritative**: the full `createCurrentToolAuthority.check` chain runs on every call, before effect, at effect and at release.

### 2.4 How unavailability is expressed

- **Primary:** absent from the tool list.
- **If called anyway** (mid-run revocation, installation expiry, policy change, or a deferred tool loaded through search): the tool handler returns `isError:true` with one fixed text per gateway code, for example `UNAVAILABLE: <tool> is not available in this conversation. No evidence, absence or completeness is established.` The other codes get the same treatment: `ACCESS_DENIED`, `DEADLINE`, `CANCELLED`, `INVALID_ARGUMENTS`, `BUDGET_UNCERTAIN`, `INVALID_RESULT`, `RESOURCE_LIMIT`, `INTERNAL_ERROR` (the gateway's closed codes in `operation-result.mjs`). There is never a success with empty content, and no source detail.
  - Today `meri_original_reads` collapses all of these into `SOURCE_READ_REFUSED`. Distinct closed codes let Meri tell the user why (not available, versus not permitted, versus timed out) without leaking anything.
- **Instructions block:** the server's `instructions` include a short generated line listing the *families* that are not available in this conversation, by descriptor display name, so Meri can say plainly that, for example, federal bill search is not available yet. Names only: no policy reasons, no tenant facts.
- **No server mounted:** the default prompt already discloses that no institutional source tool is enabled. P12 makes that sentence conditional once the server is mounted.

### 2.5 PreToolUse and canUseTool gating

This reuses the `skills/mcp.mjs` pattern, generalized:

- **PreToolUse hook** with matcher `mcp__meri_reads__.*`:
  - Checks the hook event, tool-use id format and session id. The session id is pinned to the resume/fork target when continuing.
  - Checks the tool is in the run's available list, and enforces the per-run call budget.
  - Records a one-time correlation token keyed by the argument hash.
  - Derives `deliveryId = 'sdk:' + sha256({binding, sessionId, toolUseId})`.
  - Rewrites input to `{arguments, _meriInvocation: token}`. Any failure denies.
- **Tool handler:** consumes the token, requires an exact operation and argument-hash match, calls the gateway mount, and enforces output bytes.
- **`canUseTool`:** allows only exact names in `allowedTools` and denies everything else ("Tool unavailable"). It is chained with the capability fragment's `chainPermissions` (`capabilities/fragment.mjs`), so every layer must allow.
- **Audit hooks** (`capabilities/hooks.mjs`, `tool.audit`) record names and hashes only.

### 2.6 Receipts

Each call goes through `createDurableToolDispatch.executeOwned` with the run's tool-grant facts and producer identity. That gives one durable invocation record per `deliveryId`, budget reservation/settlement, and replay without repeating source effects. This is the same owner the skill mount uses.

The worker keeps `{deliveryId, operation, argumentsSha256, resultSha256}` per call. It adds the decision id, policy revision and installation `executionCatalogSha256` from the gateway result for the run's completion record. Raw results are never published as events. Conversation event admission for receipts needs P9.

### 2.7 Budget and timeout

- **Per call:** the gateway `maxRequestMs` and the shortest of run deadline, capability expiry and decision deadline. The server `timeout` is at most 60 s and at least 1 s. Cancellation propagates from the SDK `extra.signal` through `AbortSignal.any`.
- **Per run:** proposed initial ceilings mirror the original skill assets (24 tool calls, 1 MiB per result, 2 MiB aggregate read bytes, zero recovery attempts). These are **unqualified upper bounds pending approval**, carried by a general-read budget allocation (P3), never spending authority. A selected skill's budgets are the minimum of the base allocation and the skill's own.

### 2.8 Relationship to skills

The general server is the base and skills narrow and guide it.

- With a skill selected, the same `meri_reads` construction receives `skill.allowedOperations ∩ available`.
- The skill adds its prose, rubric, budgets (min), structured output and pin-tagged receipts.
- Two servers never expose the same operation in one run.
- `meri_original_reads` stays as is for the two runtime-admitted skills (`relationship_brief`, `commitments_audit`) until `meri_reads` is qualified. Then the skill runtime becomes a narrowing profile over `meri_reads`, as a separately reviewed change.
- Skill prose keeps model invocation disabled. Making skills model-invocable is out of scope.

### 2.9 What stays out

- No generic SQL or free-form query tool.
- `query_global_data` and `search_capiro_data` are typed contracts: dataset-registry `select`/`filter`/`order` fields and closed query classes. Their adapters must validate fields against the registry from `list_global_datasets` and must never pass raw query text to a database.
- No write, no external action, no artifact generation and no browser tool is exposed through `meri_reads`.

## 3. Conversational routes for product operations

Writes and product effects never go through `meri_reads`. Proposed route: a separate governed intent surface, `meri_intents` (P10; this adds a component, so it **needs approval**).

- Each intent tool is a thin adapter over an existing control owner. It only **prepares**: it validates and returns either an `approval_required` immutable proposal or a draft artifact version.
- Effects run only after the user approves through the existing approval controls: the action-application approve route, or the conversation `approval.wait` control.
- Execution then runs with fresh `command.execute` (or artifact/schedule) authority.
- Fallback if approval for a tool surface is refused: a typed `intent` field in the turn's structured output that control turns into the same proposal card. This loses in-turn validation feedback.

## 4. Neutralizing legacy guidance that names deferred tools

The inventory scans model-visible text (retrieval contract validators, gateway adapters, skill prose, catalog descriptors) for the 43 deferred names. It finds exactly two, both pinned by the test:

- `packages/contracts/retrieval-0.2/tenant-contacts-validation.mjs:61`. The `find_contacts` note is enforced byte-exact by `assertTenantContactsResult`: "Propose only the missing ones via update_client_profile people[]." `update_client_profile` is deferred and never implemented.
- The `lookup_client_registry` free-form `guidance` field ("compatibility guidance is untrusted… create_client remains deferred").

The identity-contacts adapter cannot remove the note: the canonical validator would reject the result, and the adapter must preserve the canonical DTO. Proposal:

1. **Interim (Fable, general server):** leave the canonical result untouched (receipts and hashes unchanged). When a result's text contains any deferred tool name, append a separate fixed content block, for example: "Notice: update_client_profile is not available in Meri. Do not propose or claim a client profile change. You may offer a governed task proposal instead." The tool is never registered, and `canUseTool` denies unknown names in any case.
2. **Permanent (dot, as contract owner, with the source producer):** publish a successor contacts contract, or change the version, so the note omits the deferred-tool clause (for example "…not yet on the People tab. These come from synced mail and calendar — cite them as such."). The producer then emits it. Apply the same to the registry `guidance` text. The adapter follows the new contract with no logic of its own.

## 5. Qualification plan per adapter family

**What counts as qualified for a family.** All of the following:

- An automated test drives the **real** SDK (`query` 0.3.295 / CLI 2.1.295) with a model call through the approved proxy under the approved synthetic model budget.
- The model calls a `mcp__meri_reads__*` tool. The PreToolUse correlation runs, and the gateway mount runs with real current authority ports, the durable Postgres budget and invocation owner.
- The adapter's HTTPS call reaches the Core/backend endpoint (owned by dot) for a synthetic, dedicated qualification tenant, with broker-issued short-lived credentials.
- The test asserts every outcome below.
- dot independently reviews the exact commit and records ACCEPT.
- The contract owner then records `availability: enabled`, `qualification: qualified` and the handler `sourceSha256` for that operation, and the native owner issues the installation receipt.

Anything less is **source evidence**. That includes offline tests that drive the in-process server through `@modelcontextprotocol/sdk` `Client` + `InMemoryTransport` with a scripted gateway (the existing tier used by `apps/worker/conversation/skills/test/mcp.test.mjs`), and runs against a local fixture backend.

**Common assertions, every family:**

- The tool list matches the policy/role/tenant/client matrix: present when all gates allow, absent when any gate denies.
- An authorized read returns the canonical wrapper, and the receipt matches (`deliveryId`, argument and result hashes, decision id).
- These all produce a closed error, never an empty success: cross-tenant, other client, revoked membership between calls, policy flipped off mid-run, installation expired, budget exhausted, deadline, cancellation.
- Argument-borne authority is refused.
- Duplicate delivery replays without a second source call.
- Output limit is enforced.
- All task-owned processes have exited after completion, failure, cancellation and timeout.
