# Package 3: product integration, general reads and schedules

Reviewed 15 October 2026. Exact candidate: `neo-capiro/meri-greenfield`, `fable/repair-package-3-20261015`, **81e20025b7a805ac28a44f2044df87b0ebab905b**, tree `324764ed9358c45cf0ab72a7f7ca523715e2a83e`. This report reviews the new general-read/mail and scheduled-dispatch additions. L1/L4 settlement, PDF, dependency ownership and deployment acceptance are separate reviews.

## Verdict

**Useful source foundations; complete product integration and scheduled execution remain HOLD.** Mail now has a real single-SDK-server implementation and a path into the canonical gateway. Scheduled firings now have fixed identities, current-owner admission checks and evidence-based reconciliation. Neither feature is reachable through the canonical production composition. No qualified general-read installation, ordinary-run read allocation, schedule authority/instruction store or registered schedule worker exists in this candidate.

There is also a new source correctness issue in schedule-intent reconciliation: matching an action tuple is treated as proof of the entire schedule effect even though cadence, policies and state are not compared. Disclosure of other residuals is not acceptance of those residuals or completion of L6.

Source acceptance can be bounded to the implementation patterns described below; do not label the whole new schedule capability accepted while these gaps remain. [Package report](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/docs/coordination/reports/FABLE-REPAIR-PACKAGE-3-20261015.md).

## 1. General reads: real foundation, zero qualified normal-conversation reachability

### What is implemented

- One SDK in-process MCP server, `meri_reads`; it does not introduce another model loop. Tool definitions derive from canonical descriptors. The current family map contains only mail: `mail.list_messages`, `mail.search_messages`, `mail.read_thread` at 0.2.0. Public SDK names are `mcp__meri_reads__mail_list_messages`, `mcp__meri_reads__mail_search_messages`, `mcp__meri_reads__mail_read_thread`. [families.mjs:1–15](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/worker/conversation/reads/families.mjs#L1-L15), [tools.mjs:9–34](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/worker/conversation/reads/tools.mjs#L9-L34).
- Availability is the intersection of read-only contract, measured installation, platform/tenant/role policy, discovery grant, client-scope requirements and the closed catalog exclusion set. A selected skill narrows operations; operations already exposed through its server are excluded. Mail allows personal or client subjects; optional client prefiltering does not grant either subject. [availability.mjs:36–50](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/worker/conversation/reads/availability.mjs#L36-L50).
- A per-run SDK hook pins session/tool-use correlation, generates a one-use argument-bound token and derives a stable delivery ID. The handler consumes that token, refreshes availability, enforces deadlines/output ceilings, and returns closed errors rather than empty success. [server.mjs:43–85](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/worker/conversation/reads/server.mjs#L43-L85).
- The gateway mount delegates execution to the existing durable owner, rechecks installation at release, and retains source access off unless explicitly supplied by trusted composition. [mount.mjs:18–47](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/gateway/general-reads/mount.mjs#L18-L47). The canonical authority verifies capability action/audience/expiry, current run, actor/tenant, required business grants, source enablement and final run state. These are real checks in source, not proof of any actual tenant's grants. [current-tool-authority.mjs:20–89](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/gateway/authorization/current-tool-authority.mjs#L20-L89).

## 2. Scheduling: fixed occurrence identity is valuable, execution ownership is incomplete

### What is implemented

- Server-set Temporal schedule ID, scheduled time and workflow ID, plus generation and owner, derive deterministic conversation/run/request/event identity. Replay names the same run. [scheduled-occurrence.mjs:14–40](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/scheduled-occurrence.mjs#L14-L40).
- Dispatch checks current projection/generation, active-intent barrier, state, catch-up window, instruction digest and original-owner authority before admission and start. Current scopes must match the scheduled resources, while policy revision may be refreshed. It accepts through the canonical conversation store, then starts the exact conversation workflow with existing duplicate protection. [scheduled-dispatch.mjs:65–125](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/scheduled-dispatch.mjs#L65-L125), [temporal-dispatch.mjs:24–28](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/conversations/temporal-dispatch.mjs#L24-L28).
- UNKNOWN is followed by a two-minute wait and evidence-only reconciliation. A typed absence is distinct from an unavailable owner. Activities have one attempt; evidence-backed redispatch retains the same occurrence identity. [scheduled-dispatch-workflow.ts:14–32](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/conversations/scheduled-dispatch-workflow.ts#L14-L32).

These are source properties, not a measured two-minute recovery SLO or live PostgreSQL/Temporal restart proof.

### Startup and authority still absent (P1 integration HOLD)

Canonical worker options register conversation activities only: [temporal-worker.mjs:43](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/runtime/temporal-worker.mjs#L43). The scheduled workflow and activities are not registered anywhere in canonical startup. Placement remains an explicit proposal, not a flag to turn on. Current schedule-authority and durable approved-instruction owners are also missing; the existing intent stores an instruction hash, not the retained text needed by later firings. [Schedule proposals:46–80](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/docs/coordination/proposals/FABLE-L6-SCHEDULES-PROPOSALS-20261015.md#L46-L80).

### Actual job lifecycle is not owned by the schedule wrapper (P1 completion HOLD)

The wrapper returns at DISPATCHED, after starting a separate conversation workflow; it does not wait for that job. Schedule overlap therefore controls dispatch only. The wrapper's run timeout/retries likewise do not enforce the issued job's lifetime, and cancelling the schedule's original wrapper does not prove cancellation or physical stop of the separately launched conversation. [workflow:26–32](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/conversations/scheduled-dispatch-workflow.ts#L26-L32), [schedule mutation:21–27,48–55](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/temporal-schedule-mutations.mjs#L21-L55).

The added admission persists scopes, prompt and runtime versions, but no schedule linkage or per-schedule cost/runtime/delivery allocation. `ScheduleProjection.maxCostMicrousd`, `maxRuntimeSeconds`, `retryLimit` and `destinationId` are not propagated into the issued conversation admission/dispatcher. This path therefore does not establish enforcement of the scheduled task's budget, retries or destination. [admission:98–104](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/scheduled-dispatch.mjs#L98-L104), [ScheduleProjection schema](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/packages/contracts/meri.schema.json).

Other disclosed residuals remain unresolved: UNKNOWN can outlive its wrapper timeout, admitted-but-refused runs can remain queued, and unresolved-intent firings are dropped rather than queued for later. [Lane report:133–149](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/docs/coordination/reports/FABLE-S3-L6-SCHEDULES-20261015.md#L133-L149). These disclosures are accurate limitations, not acceptance of a complete schedule capability.

Minimum repair: one durable schedule-occurrence → conversation/native-effect association; actual-job overlap, cancellation/stop, budget and result delivery ownership; an UNKNOWN barrier that survives wrapper timeout; approved worker placement and real authority/instruction owners. Test two close firings while the first job runs, cancel during execution, revoke before/after admission, crash after each durable boundary, and retry without replacement identities.

## 3. New source issue: reconciliation proves an action tuple, not the complete schedule effect

**P2 source correctness; HOLD before schedule activation.** For create/update, `scheduleStatePresent` compares schedule ID and action type/workflow ID/type/queue plus `{generation, projection, task}`. It does not compare `spec`, `policies`, paused state, remaining actions or the action's timeout/retry configuration. It then acknowledges the intent and clears the durable projection barrier. [intent-reconciliation.mjs:58–75](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/intent-reconciliation.mjs#L58-L75).

Static witness: keep the matching action tuple while changing `state.paused`, or supply different timing/overlap policy. None of those changed fields is read on the create/update branch, so it still returns true. The positive synthetic provider omits timing and policies altogether: [intent-reconciliation.test.mjs:8–15](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/test/intent-reconciliation.test.mjs#L8-L15). The tests only mutate the tuple fields: [lines 46–51](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/test/intent-reconciliation.test.mjs#L46-L51).

Impact: an UNKNOWN effect can be marked acknowledged even when the actual provider schedule remains paused or has different execution timing/policy. This is a source-level witness, not a live reproduction or proof that Temporal itself partially applies a request.

Minimum repair: define the exact provider-normalized configuration that establishes applied intent, compare every approved semantically material field (or bind independently trustworthy atomic-effect evidence), keep non-comparable evidence unresolved, and add mismatch tests for cadence/timezone, policies, state, limits and retries using real SDK describe shapes.

## 4. Recovery and the reported frozen-clock failure remain open

A CLAIMED intent, or a dispatched intent with no observed effect, cannot be recorded as NOT_APPLIED. `active_intent` remains set, future edits fail and firings are refused. This is explicitly implemented as UNRESOLVED, with P-L6-1 still only a migration proposal. [intent-reconciliation.mjs:65–75](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/intent-reconciliation.mjs#L65-L75), [proposal:7–44](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/docs/coordination/proposals/FABLE-L6-SCHEDULES-PROPOSALS-20261015.md#L7-L44). A safely blocked schedule is not recovered availability. The proposed absence/quiescence rules also need independent review; this report does not approve the DDL or treating transient absence as proof of non-effect.

The integrated report's **153/154** schedule result remains a failed run, even though the isolated test passed 5/5 later. The reported clock problem is traceable: the harness freezes `time = Date.now()` at construction, but the expiry-substitution test uses a later ambient `Date.now() - 1`. If real time advances by more than 1 ms, the supposedly expired receipt is future-dated relative to the injected frozen clock. [test:13–21,31](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/test/temporal-inspection-independent.test.mjs#L13-L31).

This is a concrete test-clock inconsistency; it does not establish a production expiry bypass. The inspector supplies its injected clock to the operation lifetime, which enforces the receipt deadline. [inspector:22–48](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/control/schedules/temporal-inspection.mjs#L22-L48). Minimum correction: derive both harness time and receipt times from the same explicit clock, assert past/equal/future boundaries deterministically, and rerun the integrated suite under load without erasing the failed receipt. A rerun pass alone does not fix this source flaw.

[availability.mjs:24–48](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/apps/worker/conversation/reads/availability.mjs#L24-L48), [scope ledger:17–54](https://github.com/neo-capiro/meri-greenfield/blob/81e20025b7a805ac28a44f2044df87b0ebab905b/docs/coordination/ledgers/MERI-FINAL-SCOPE-LEDGER-20261015.md#L17-L54).
