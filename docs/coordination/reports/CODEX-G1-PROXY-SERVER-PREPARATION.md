## Failure model and <=30-second target

A5-second poll plus bounded state/observer waits can be designed below30 seconds, but this remains a target to measure under actual server scheduling, CPU load, TLS backpressure and database/network failures. The existing state wrapper waits up to5 seconds for a `to_thread` call; its synchronous transaction uses5-second statement and2-second lock timeouts. These do not establish a total process/thread termination bound. Do not accumulate new check threads behind an unresolved check.

Use finite task observation and retained strong references for unresolved cleanup. Python documents that `wait_for` waits for cancellation completion and can exceed its timeout, while `asyncio.wait` returns pending tasks without canceling them. TaskGroup exit also awaits its children. None forcibly terminates a task/thread. [Python asyncio task/cancellation documentation](https://docs.python.org/3.11/library/asyncio-task.html).

This is a real upstream integration constraint: `_UpstreamClosingStreamingResponse.__call__` shields iterator cleanup and awaits `aclose`; its first-chunk disconnect helper also shields cleanup. A cancellation-resistant upstream can therefore outlive the wrapper's bounded observation. Record pending work, deny further local admission/readiness and retain liability; process/task supervision and actual transport stop are later independently reviewed controls. A canceled DB await may still commit UNKNOWN in its worker thread. Never refund because the client disconnected, a Python timeout fired or an iterator failed to close.

ASGI supplies scheme/client metadata from the protocol server; it does not authenticate ECS identity. Disconnect receive events and failed sends can race, and older implementations need not raise on a closed send. The wrapper must handle both without claiming that ASGI cancellation physically closes a remote provider. [ASGI HTTP specification](https://asgi.readthedocs.io/en/stable/specs/www.html).
