The current 3.8.13 manual dates the `gnutls_x509_crt_check_hostname2` API to 3.3.0. An API's introduction is not the CVE's introduction. For any later certificate-validation fixture, record API/flags and verification output independently: the manual explains that successful API return alone does not imply an accepted certificate. No fixture was created or executed here.

The standards question should also be precise. [RFC 6125§6.4.4](https://www.rfc-editor.org/rfc/rfc6125.html#section-6.4.4) ties Common Name fallback to the absence of specified presented identifier types, including URI-ID. [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html), which obsoletes 6125, removes Common Name as a service identity source. These are requirements to clarify with the maintainer and actual consumer protocol/profile, not independent proof that this Debian binary is fixed, vulnerable or exempt. Do not turn the issue reporter's broad claim about every unsupported SAN type into a demonstrated vendor decision.

## TIFF: concrete binary-package split, incomplete all-copy adjudication

[CVE52490](https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/52xxx/CVE-2026-52490.json) identifies `process_command_opts` in `tools/tiffcrop.c`. [Upstream issue 846](https://gitlab.com/libtiff/libtiff/-/work_items/846) describes optionS unsigned multiplication and `writeImageSections`, reporting 4.7.1. No proof-of-concept attachment was downloaded or executed. [Debian](https://security-tracker.debian.org/tracker/CVE-2026-52490) still flags the installed source package revision and identifies unstable 4.7.2-1 as fixed. The exactu3 changelog's pixarlog 12912 repair does not establish 52490 repair.

There is a stronger component-specific lead than a simple dormant-operation assertion:

- The image package inventory contains **`libtiff6=4.7.0-3+deb13u3`** and contains no `libtiff-tools` row.
- The [official libtiff6 package page](https://packages.debian.org/trixie/libtiff6) matches that exact version and identifies it as the shared-library package. Its [amd64 file list](https://packages.debian.org/trixie/amd64/libtiff6/filelist) contains the library/symlink and three documentation files, with no utility executables.
- A different [libtiff-tools package file list](https://packages.debian.org/trixie/amd64/libtiff-tools/filelist) supplies `/usr/bin/tiffcrop` and `/usr/bin/tiff2pdf`.
- The retained image's **26,901 metadata entries** contain no exact basename or case-insensitive path mention for either utility. The observed library is `/usr/lib/x86_64-linux-gnu/libtiff.so.6.1.0`, SHA-256 `7f2309b13404f98171b54c07f75ad7c54673cec26ecaa874ac5273feda916c6f`.

This supports a **system-package component-split applicability proposal**, potentially using a missing-vulnerable-component rationale after owner/vendor review. It is not accepted here: package file lists and metadata names are not proof of every compiled/renamed/static copy, source-level function exclusion or consumer reachability. The metadata declares complete coverage of specified roots/aliases, with explicit exclusions; it is not universal image byte verification. SDK, Node, Chromium and Skia remain opaque for this purpose. `tiff2pdf` absence is supplementary; 52490 names `tiffcrop`, not every TIFF library parsing operation.
