## Service guard: successful admission is not always verified identity

[ToolServiceSecretGuard](https://github.com/neo-capiro/capiro-backend/blob/b525032222515d636b0dae2d46e40c7c3d8b5528/apps/api/src/meri/tool-service-secret.guard.ts#L13-L66) hashes both values to fixed-length buffers and uses `timingSafeEqual`. It enforces the secret in staging/production or when `MERI_TOOLS_REQUIRE_SERVICE_SECRET` is enabled. In development/test observe mode, however, it returns `true` both when the server has no configured secret and when a missing/invalid supplied secret was merely logged. A non-string header likewise does not establish a match. The guard exposes no verified-service marker at this pin.

The [tool controller comments and guard](https://github.com/neo-capiro/capiro-backend/blob/b525032222515d636b0dae2d46e40c7c3d8b5528/apps/api/src/meri/meri.controller.ts#L506-L525) explicitly preserve that observe-mode behavior and ordinary native user authentication. Therefore a new trusted observation carrier cannot rely on guard success, header presence, a caller boolean or the user JWT alone. It must require an actual service-secret match in every environment while retaining the authenticated native tenant/user. That stricter requirement is scoped to the opt-in observation path; unrelated legacy observe-mode behavior need not change.

There are relevant existing patterns, with limited scopes:

- [Prior-attachment transport, L55-L73](https://github.com/neo-capiro/capiro-backend/blob/b525032222515d636b0dae2d46e40c7c3d8b5528/apps/api/src/meri/meri-chat-attachment-transport.ts#L55-L73) strictly verifies service identity for `read_chat_attachments` before accepting its own special body. It passes other tool bodies through and does not admit a funding observation.
- [Research-portfolio transport, L71-L89](https://github.com/neo-capiro/capiro-backend/blob/b525032222515d636b0dae2d46e40c7c3d8b5528/apps/api/src/meri/meri-rp-tool-transport.ts#L71-L89) similarly verifies only its finite special operation set and has its own request-local scope. Its current-turn body protocol is not a generic funding context channel.
- [Internal telemetry admission, L132-L163](https://github.com/neo-capiro/capiro-backend/blob/b525032222515d636b0dae2d46e40c7c3d8b5528/apps/api/src/meri/meri-telemetry.runtime.ts#L132-L163) checks actual service identity before trusting linkage; unverified linkage becomes an isolated trace. ## Unsupported old servers and the held qualification gate

An old server can ignore an unknown request header and still return an ordinary native funding envelope. The unchanged exact `asOf` receiving check rejects a differing anchor, but an independently sampled default could coincide at millisecond precision. Even an equal echoed timestamp therefore establishes consistency, not support for carrier admission or verified service identity. A successful HTTP response, body/header reflection, synthetic test, installation of a Meri handler or source hash alone cannot prove the Core bridge is deployed.

Without inventing an unallocated acknowledgement/capability protocol, the available safe boundary is the existing availability/installation/credential gates:

1. Keep this pending family out of executable SDK/runtime availability and current installed/discovered/approved funding operations while bridge qualification is held. A test-only Meri adapter/DTO may exist without an executable current installation. Source connectivity or credentials for this family must remain unavailable through existing trusted composition; do not probe the old route to decide whether it is supported.
2. Require reviewed Core bridge source and separately obtained, genuine qualification of the approved native route/server composition before an existing installation/discovery/execution gate can be opened. That evidence must cover the actual serving Core implementation and authenticated admission, including any mixed-version servers. Existing Meri handler measurement is not a substitute for this backend evidence.
3. If the owner cannot establish that approved route's support with existing trusted deployment/qualification facts, keep the gate held. The current wire provides no automatic way to identify an old instance before invoking it. Adding a version endpoint, response acknowledgement, capability flag or handshake would be a new protocol requiring explicit allocation; this report does not introduce one.
4. Once qualified and activated by its owner, the new-mode adapter must always send the agreed observation and apply frozen receiving. Refusal, unsupported-server/error or transport uncertainty must never trigger a legacy retry, timestamp resampling, response repair or newly generated delivery identity.

This means no unsupported old server is treated as available today because funding remains gated off. It does **not** claim an activated header-only transport can identify every old server automatically. Qualification and live availability remain held until the backend side is completed and verified; Meri source progress is reported separately.
