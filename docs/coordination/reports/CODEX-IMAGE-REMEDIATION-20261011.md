## Remediation options and recommendation

1. **Preferred: supported stable security/backport closure plus exact applicability.** Keep the approved Debian13/Node24/SDK/Office architecture. Establish vendor-backed applicability for operations not contained in the installed binary and every embedded copy. For applicable issues, acquire one coherent supported Trixie package set whose security changelogs/source patches cover every retained obligation. Freeze the signed repository state and all package versions/hashes before changing the recipe. This path is currently HOLD because several records have no verified supported fix.
2. **If upstream fixes exist but distro packages do not: propose a maintained, reproducible backport build.** Rebuild the existing distro source against Trixie with a reviewed complete patch series, ABI/symbol/reverse-dependency and regression checks, source/binary/signature/notices closure, and an explicit ongoing maintenance owner. Known upstream commits are leads; an ad hoc `make install`, unsigned private `.deb`, partial curl TLS replacement or copied sid binary is not that proposal. No patch-series closure, build hashes or vendor support was established here, especially for pending GnuTLS/SASL/Poppler records.
3. **Architecture/component alternative only after a concrete comparison.** A different supported stable vendor image or separate document execution service could be evaluated if1/2 cannot close the risks. It must preserve the full artifact/SDK scope and demonstrate all equivalent runtime/browser/Office behavior. No verified complete alternative set was found in this bounded research, and none is selected. Existing dedicated-browser-host approval does not automatically approve relocating Office or changing base/component choices.

[Debian's security FAQ](https://www.debian.org/security/faq) explains stable security backports and why an unchanged upstream version can still be patched. Compare exact distro package revisions and changelog/advisory/source facts; a newer upstream number alone is not closure. The FAQ also distinguishes stable from testing/unstable security support. This is the reason to avoid arbitrary sid mixing. A `no-dsa`/lower vendor severity annotation is useful assessment information, not a Meri waiver.
