## Implemented boundary

`common.schema.json` separates untrusted requested subject/window from server-resolved identity and normalized windows. It distinguishes a client, an authorized versioned active-client portfolio, a personal subject and a typed entity. Requests cannot inject tenant, actor or grants. Window kinds distinguish calendar week/month/year, explicit bounds, fixed 24-hour relative days, fiscal year/stage/revision and unbounded history. The local checker rejects decreasing bounds, unknown timezones and invalid local calendar boundaries, including a 167-hour DST week with explicit Monday/Sunday policy. It preserves explicit/relative/fiscal bases across normalization. It does not choose this/last periods from a trusted clock, resolve text/entities, implement fiscal calendars or authenticate any identity.

`catalog.schema.json` defines closed operation descriptors with immutable schema/handler identities, examples, limitations, sources, effects, grants, approval boundary, bounded retry/outcome taxonomy, aliases, retirement/replacement and requirement/fixture mappings. The consistency checker rejects disposition drift, duplicates, absent replacement targets, contradictory aliases, canonical shadowing, replacement cycles, enabled descriptors without qualified handler metadata and invalid metadata paths. It never loads a handler or grants authority. The four explicitly prohibited unrestricted-query names are a narrow consistency rule, not a semantic query-language detector; this namespace has no operation execution API or arbitrary filter/SQL argument language. Real operation-specific schemas and implementation bytes still require separate qualification.

`retrieval.schema.json` separates candidate discovery, typed exact operations and full decisive source reads. Evidence retains source/record/snapshot versions, content/citation identities and contributing scopes. Coverage records requested/checked/unavailable sources, enumeration/known totals, returned records, truncation/history support, continuation and unread decisive handles. Source outages and denial remain distinguishable. The checker rejects contradictory outcomes, counts, future source timestamps, lineage, missing follow-up reads, incompatible comparison revision/stage/units and complete claims with unfinished coverage. Exact results require authoritative sources; complete history binds its total to all returned history records. Explicit absence requires an empty exact count/history, known zero total, fresh authoritative complete coverage and no cursor/truncation/unavailable source or unresolved read. These are declaration-consistency checks; receipts and actual source pagination/query semantics must establish truth later.

`skill.schema.json` carries explicit skill ID/version and requested subject/window separately from editable prose. Immutable manifests bind prose/catalog hashes, allowed operation versions, required source authority/purpose, completion obligations, approval boundaries, budgets and lifecycle policy. Cross-checks reject missing/disabled operations, unsupported required sources and silent manifest/catalog/skill-version or tenant/actor substitution across lifecycle. No manifest authoring system, workflow runner, migration mechanism or completion ledger is implemented. The Commitments & Deliverables documentation preserves promises-versus-suggestions, owner/date uncertainty, delivery evidence, conflicts/deduplication, authorized client-mapped monday.com boards and separate approved task actions. Auto task creation is forbidden in this foundation.
