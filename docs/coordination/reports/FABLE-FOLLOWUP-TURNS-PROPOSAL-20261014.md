# Proposal to dot: follow-up turns in one Meri conversation (slice 2, approval required before code)

Base `c6053e24b465be677cc5980533009b4aab03beab` (PR86). Author: Fable. Status: PROPOSAL. Under AGENTS.md this widens the fixed first-run pilot's admission ("genuine missing canonical row permits only the already-approved fixed first-run input"), so it is recorded for approval before any source change. It proposes no new orchestration loop, authority system, API family, provider, placement or component.

## Why

The first usable authenticated chat (HANDOFF §5) is one prompt and one run. A usable chat needs a second prompt. At PR86 the opaque session binds one run (`createActionSessionOwner` pins `principal.runId`; `apps/control/action-host/session/owner.mjs`), `submit` reuses the session's binding as the run binding (`apps/control/conversations/service.mjs`), and the prepared-candidate identity owner joins only its one configured `commandContext.binding` (`apps/runtime/prepared-candidate.mjs`, `createPreparedCandidateIdentity`). A second `requestId` on the same session therefore meets the existing run row and refuses as `REQUEST_REPLAY_REFUSED`. New runs exist today only through lifecycle `resume` (from a paused/approval-wait checkpoint) and `fork`.

## Proposed shape, reusing existing owners only

1. Session issuance selects a run server-side. `POST /api/action-followthrough/session` keeps its wire. The identity/context join (`createApplicationContextAdapters`) gains a run resolver supplied by trusted control instead of a single fixed binding: given the authenticated principal, the hinted `conversationId` and an optional hinted `runId`, it reads the canonical conversation/run rows (`createPostgresConversationStore.readOptional`) and returns the latest run binding of a conversation the principal owns, or the hinted one if it belongs to that conversation. Browser hints remain selectors; ownership and scopes still come from the backend context receipt and the current admitted run (`currentRun`). No new identity DTO.
2. A new run on a terminal latest run. `submit` with a fresh `requestId` while the session's run is terminal creates the next run in the same conversation: new `runId/attemptId/workerId`, `writerFence` + 1, same scopes/policy/versions, and a `continuation` envelope `{mode:'resume', …}` pinned to the completed run's checkpoint. This reuses `journal.continuation` (`apps/control/conversations/lifecycle/journal.mjs`), which already inserts a target run with its continuation and first queued event under the source conversation lock. The source run is not retired twice: the completed task is already gone, so `nativeAdmission.retire` is replaced by the completion checkpoint's physical-stop proof.
3. Completion checkpoint. Today checkpoints are captured on pause/approval wait. The remote runner's capture owner (`createNativeCheckpointCapture`, `createTaskCheckpointSource`) already freezes the mirror, reads the SDK SessionStore snapshot and workspace, and publishes immutable objects. Control would invoke it once at `run.status: completed` before releasing the task, so the next run restores exactly as `resume` does (`createContinuationRuntimeSdkSession` seeds the target SDK session from the immutable snapshot). Workspace bytes carry over the same way.
4. Per-run native admission. Each run needs its own allocation JSON, grant intents and task capability (`createNativeAllocationAdmission`, `allocateRemoteNativeController`). Today these are configuration for one fixed run. The product needs an allocation issuer that derives a per-run allocation from the selected skill manifest (or the plain-conversation manifest) and the conversation's budget policy, and issues short-lived task capabilities. This issuer is explicitly separately owned ("no fixture initializer is a product issuer"); the proposal asks dot to allocate that owner and its migration IDs if any.
5. Temporal. Unchanged: one `meriConversationLifecycleWorkflow` per run with the exact workflow ID; the lifecycle `continued` signal is not needed because the source run is terminal.
6. UI. `history` and `events` stay per run; the frontend needs a conversation-wide listing of runs to render a thread. That is an additive public contract (W06, "multi-run conversation listing") and therefore a Codex-frozen change, proposed here, not made.

## What does not change

Claude Agent SDK remains the only model loop; AI SDK transport is unchanged; no second session owner, authority system or queue; no execution-placement change; original-chat milestone scope is unchanged; selected skills remain fail-closed; sources remain disabled.

## Impact and acceptance

- Contracts: submit/history/cancel/events wire unchanged (public 0.1.3 regenerates byte-exact). Private lifecycle contracts unchanged. One additive public operation for run listing, to be frozen by Codex.
- Migrations: none expected. `runs` already carries `continuation`/`continuation_sha256`; checkpoints and native tables exist (0001–0008).
- Owners touched: `apps/control/action-host/application-adapters/context-adapter.mjs` (resolver port), `apps/control/conversations/service.mjs` (next-run submit), `apps/runtime/prepared-candidate.mjs` and `native-authority/prepared-runtime.mjs` (per-run admission over the issuer), `apps/control/conversations/lifecycle/*` (completion capture hook). Each is a separately bounded task with exclusive paths.
- Acceptance (local, then live): two consecutive prompts in one conversation over actual PostgreSQL with the real supervisor and zero-turn CLI; exact request replay and concurrent-submit refusal across runs; stale session on the previous run refuses writes; completion checkpoint readback hash equality; restore of run 2 from run 1's immutable snapshot; cancellation during admission leaves no target; Temporal workflow ID uniqueness per run; no duplicate allocation under lost COMMIT acknowledgement. Live: one two-turn authenticated conversation through the frontend.

Decision requested from dot: (a) approve the shape or redirect; (b) allocate the allocation-issuer owner and any migration ID; (c) confirm the run-listing contract addition goes through the usual freeze.
