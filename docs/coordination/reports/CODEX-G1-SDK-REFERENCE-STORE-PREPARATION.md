## Compatibility and reference limitations

The [Postgres adapter](https://github.com/anthropics/claude-agent-sdk-typescript/blob/85d8f8e0772199ec7965a0c2e874ac88343f2a01/examples/session-stores/postgres/src/PostgresSessionStore.ts) and [S3 adapter](https://github.com/anthropics/claude-agent-sdk-typescript/blob/85d8f8e0772199ec7965a0c2e874ac88343f2a01/examples/session-stores/s3/src/S3SessionStore.ts) implement the same opaque `SessionStore` append/load/key model present in installed SDK0.3.295. There is no SDK-version blocker to this interface. The local version-specific evidence is `w02-image/apps/worker/qualification/node_modules/@anthropic-ai/claude-agent-sdk/{package.json,sdk.d.ts,sdk.mjs}`; full hashes are in `data-result.json`.

SDK types at lines1810–1840 require local persistence for resume and describe eager/batched remote mirroring. Lines6596 onward define opaque entries, optional UUID deduplication, deep-equal load, and subkey enumeration needed for subagent restoration. `projectKey` is a logical namespace, not tenant authorization. `listSessionSummaries` is optional and absent from these examples; that omission must not silently eliminate planned product session capabilities.

The installed SDK implementation actually awaits transcript mirror `flush()` during result processing and cleanup. This is useful existing drain machinery. It is not a public successful durability receipt: retry exhaustion reports `mirror_error`, discards that batch and permits the process to continue; the types describe three attempts and a sixty-second rejection timeout. Therefore neither a final SDK result, `close(): void`, nor process exit alone proves remote durability. No native behavior was measured here.

## Existing canonical ownership

The adopted plan at `docs/plans/MERI-DEPLOYMENT.md:30–39,98–102,181,378` already assigns the SDK loop/session APIs, Temporal orchestration, S3/PostgreSQL persistence, workspace snapshots and stored-context authorization. Reusing that architecture needs no plan departure.

`packages/contracts/meri.schema.json` already defines canonical `RunBinding`, capability actions `session.persist`/`workspace.persist`, `ObjectReference` with version/hash/size, scoped `WorkspaceManifest`, and `Checkpoint` with opaque session object, workspace hash, runtime versions, event sequence and durable receipt ID. Its `validate.mjs` supplies canonical hashing and strict workspace paths. These are schema/validation guarantees, not storage commits or access grants.

`apps/proxy/qualification/state/{grants.py,admission.py,postgres_store.py}` supplies an existing trusted current-run/grant transaction pattern, revocation checks, explicit database migration and commit-uncertainty handling. It currently owns qualification model accounting, not a storage endpoint. Its integer attempt/task-ARN binding differs from canonical UUID attempt/worker identities and lacks canonical tenant/actor/conversation fields. A trusted registry mapping is required; do not relabel it as canonical authority. `runtime/ingress.py` admits only HTTPS POST `/v1/messages`, so a SessionStore transport cannot be smuggled through this model route or given direct worker database/S3 credentials.

`apps/control/qualification-temporal/activities.ts` currently heartbeats/echoes a checkpoint; its workflow is offline orchestration preparation. There is no implemented durable session broker/checkpoint commit here. No existing reviewed external storage seam can safely wrap the reference unchanged. Accordingly no runnable adapter wrapper or migration was created in this allocation.

## Concrete minimum proposal for root freeze

The data artifact `contract-proposal.json` makes these proposed operations explicit; it is not a new accepted schema or service. Keep the SDK-facing `append`, `load`, `listSubkeys` interface unchanged. A thin worker transport uses a task-bound capability and opaque entries only. Trusted control/broker resolves canonical tenant/actor/conversation/run/attempt/worker/fence/policy and authorizes the logical `/workspace` namespace; worker-supplied `projectKey` never chooses authority.

1. A focused trusted session-persistence module implements `appendSessionBatch(batchId, sessionKey, entries, expectedPriorReceipt)`. In one current-binding/grant-checked transaction it serializes the writer, binds batch ID to content and records ordered opaque entries. Known UUIDs can deduplicate only with identical content; UUID-less entries cannot be discarded. An uncertain commit stays UNKNOWN until exact reconciliation; no new batch ID/retry may hide uncertainty.
2. A focused checkpoint module implements `sealCheckpoint(sessionCommitReceipt, workspaceManifest, versions, lastEventSequence, parentCheckpointId)`. Reuse the existing Checkpoint schema and immutable S3 versions for opaque session/workspace objects. Verify quiescent source, complete transcript/subkeys and object version/hash/size before a fenced commit publishes the checkpoint. Fence advancement and publication must serialize with current-run authority; an earlier check followed by an unrelated write leaves a stale-writer race.
3. The same module implements `loadSessionCheckpoint(checkpointId, sessionKey)`, checking current reader scopes/policy, compatible pinned runtime and all referenced object bytes before exposing restored entries/workspace. Missing, corrupt, partial, deleted or revoked checkpoint content must refuse restoration. The SDK's unknown-key `null` behavior must not turn a failed restore into a new empty session.

Minimal additive contract work is the typed batch/commit/UNKNOWN receipt and restore-refusal boundary, plus mapping qualification identities to canonical bindings; existing Checkpoint/Workspace/ObjectReference types should remain canonical. Root must allocate the central migration and trusted service owner. No second authorization ledger, agent loop or generic persistence framework is proposed.

Unresolved implementation facts are specific: stable batch identity across SDK mirror retry (especially UUID-less entries); a verifiable successful drain watermark despite best-effort SDK mirroring; atomic checkpoint/fence advancement; exact opaque transcript/subkey coverage after compaction; bounded payload/page/file/session/deadline policies; and retention/revocation over stored context. Validate the thirteen upstream contracts against the chosen implementation, then new authority/durability cases: foreign tenant/fence, revoked writer, duplicate batch with altered content, UUID-less retry, commit uncertainty, corrupt/missing S3 version, partial subkeys and failure between snapshot and checkpoint publish. Actual interrupt/task replacement/resume must later prove these properties with the SDK and original skills. Pure tests cannot replace that native evidence.
