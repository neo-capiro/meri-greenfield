# Minimal connection boundary for real Meri chat

Reviewed frontend PR36 source `7e170defb9442aa3ce0fd1d5b14060af831ce8d0`, [production handoff](https://github.com/neo-capiro/capiro-frontend/blob/7e170defb9442aa3ce0fd1d5b14060af831ce8d0/docs/production-data-20261014/HANDOFF.md). The truthful unavailable state is correct until the following existing owners are serving. This is a contract mapping, not permission to activate or a live acceptance receipt.

1. Preserve Core account/auth and SelectedClient verification. Trusted Meri identity/context composition calls the unchanged backend POST `/api/clio/application-authority/identity` and `/context`; the browser's greeting, selected client or conversation selector cannot supply authorization. Use the existing opaque issuance owner at POST `/api/action-followthrough/session` with JSON hints limited to optional `conversationId`, `runId`, `clientId` and the existing verified identity Bearer credential. The receipt is exactly `{credential, expiresAtMs, context:{tenantId,actorId,conversationId,runId,selectedClientId}}`; verify its actual account/client/current-conversation mapping. It yields a short-lived opaque Meri session bound to the current identity, conversation/run/fence/client/scopes/policy/expiry. The native authority bearer and task/control capabilities remain server-side. No new token issuer or frontend SDK upgrade is required.
2. Mount a fixed frontend server proxy to one owner-approved Meri control HTTPS origin. Bind the existing frontend session to the returned current conversation session; forward only the public conversation operations and preserve their exact SDK0.1.3 envelopes, statuses, cache controls and stream bytes. Current actions/document activation is not evidence that conversation activation exists. Host/proxy allowlisting and authentication must be concrete before enabling the composer.
3. The Meri control public routes already implemented are POST `/api/conversations/submit`, `/history`, `/cancel`, `/events`, and GET `/api/conversations/events/{conversationId}/stream`. POSTs use JSON and the opaque Meri Bearer session; reconnect has no body/content-type and carries `x-meri-resume-sequence`, not Last-Event-ID. Selectors are checked against the session's actual conversation. Preserve the existing UI stream protocol and native SDK receiver's operation mapping. Lifecycle controls/checkpoint inspection use their existing public owners separately; no recent-conversation listing or approval count is implied.
4. Behind those public routes, mount the real task-authorized runner relay and native broker runtime. POST `/v1/execution/start` and `/poll` use the control capability; `/v1/runner/runtime` and `/v1/runner/session/{snapshot,register,load,append,list-subkeys}` use the original task capability and fresh authority. These private routes are never browser destinations. The existing Temporal activity starts/polls the same original execution and the approved isolated task owns the only Claude SDK Query/model loop.
5. Supply approved serving origin, exact source/image/entrypoint, real product database/migrations, Temporal namespace/queue/TLS, actual allocation/grant/fence/lease, task/supervisor transport and isolated proxy/model/budget bindings. Validate one authenticated conversation, genuine native registration, durable UI events/transcript and physical task cleanup before replacing unavailable with active chat. The current zero-turn component probes and scripted ECS/authority controls do not meet this gate.

Canonical source owners: `apps/runtime/control.mjs`, `product-applications.mjs`, `worker-http.mjs`, `native-runner-gateway.mjs`; `apps/control/conversations/http.mjs`, conversation service/session issuance; `apps/runtime/native-authority/{runnable-runtime,execution-http,session-http}.mjs`. Backend extraction and frontend host/proxy work remain their owners' work. No legacy Meri path, fabricated provider result, new public API or alternate storage owner is proposed.

Existing public request bodies (frontend SDK0.1.3 / wire contract0.1.0):

| Operation | Body / cursor |
| --- | --- |
| Submit | `{requestId,prompt,windowRequest?,skill?}` |
| History | `{after?,limit?}` |
| Cancel | `{}` |
| Subscribe | `{command:{conversationId,intent:'view.subscribe'}}` |
| Reconnect GET | `x-meri-resume-sequence` header; no body, Content-Type, query or Last-Event-ID |

The current opaque session chooses the run. Do not add conversation/run/client selectors to submit/history/cancel. Configuration must keep runner runtime on the broker receiver; the fixed runner gateway forwards run-owner operations to control and session operations to their private control mount. `sdkSessionSnapshot: stack.continuation` is now a supported borrowed control port, locally tested through that fixed gateway; the real canonical owner and deployment origin still require binding.
