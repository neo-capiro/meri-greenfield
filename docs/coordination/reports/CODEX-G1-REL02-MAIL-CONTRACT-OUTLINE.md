## What the retained metadata establishes and does not

`mail-query.ts:36–97` establishes numeric-coercing legacy list/search bounds: limit 1–50/default 20 unless the caller supplies another default; offset 0–10000/default 0; withinDays 1–3650; asOf defaults now and is required for offset >0. Registry prose says list threads, but this query emits deduplicated **messages**, with threadId. The list wrapper is not retained, so neither its defaultLimit nor message-vs-thread return parity is established. The new `mail.list_messages` counted unit is therefore an explicit proposed correction requiring approval and a visible alias compatibility note.

Query matching covers subject/body/from/to/cc, with bcc additionally in participant matching; it escapes SQL wildcard syntax. Records deduplicate per `(connectionId, internetMessageId-or-recordId)` before paging, and order by COALESCE(receivedAt,sentAt) descending/null last, ID descending (`:134–166`). A copied message in another owned mailbox remains distinct. Source record/version identity must not be deduplicated merely by equal body/citation.

Tenant, connection owner, Microsoft/Google provider, thread/connection joins and nonremoved message are explicit (`:101–111`). The query reports connection status but does **not** require an active connection status in the read predicate. New-contract owner-active-eligible connection requirements are stricter proposed policy, not an observed old guarantee. `engagement-access.helpers.ts:67–80` delegates active-message/thread rules to unretained `mail-message-state.js`; those exact predicates are missing. Tenant filtering is supplied separately. Neither policy metadata nor UUID hashes authorize a call.

`asOf` limits createdAt and received/sent times; it does not freeze mutable body/updatedAt, deleted rows, connection status or client reassociation. It is not proof of repeatable snapshot pagination. `messageUpdatedAt`/preview SHA are returned metadata, not immutable body-version proof. The query uses a separate mail-sync-coverage helper not retained here; it explicitly warns that general connection sync time/oldest/newest stored mail do not prove coverage, and initial/recovery sync scans a bounded 365-day window. A no-mailbox result is unavailable/unknown search coverage, not zero email.

Schema models MailThread/MailMessage (`schema.prisma:1312–1385`) establish tenant/thread/connection UUID relations, nullable bodyText and HTML object locator, removedAt, metadata and updatedAt. They do not establish a body completeness flag, immutable body revision, canonical normalization, HTML extraction or snapshot service. IntegrationConnection (`:1139–1168`) provides owner/provider/status/sync metadata; status eligibility must be explicitly bound by the future adapter. Meeting/Note/Debrief schemas and policy helpers show distinct private/shared, confidential and approval states; one tenant predicate is insufficient.

For legacy `get_email_thread`, only registry prose establishes bodyOffset/maxCharacters <=6000 and messageOffset/limit <=10. **Unknown:** required/default/minimum/null/type-coercion rules; offset unit (UTF-16/code point/byte); per-message vs thread-wide bodyOffset; order/null ordering/tie-breaks; limit behavior with messageId; authoritative body source/HTML normalization/completeness; exact continuation fields; source version/snapshot handling; and behavior during edits/removal/revocation. The implementing thread service and canonical body/state/coverage helpers were not retained; no legacy behavior is guessed from list/search SQL.

## Proposed first contract slice (root approval required)

Define `mail.read_thread@0.2.0`, alias `get_email_thread`, sideEffect none, requiredGrants bound to the existing gateway read grant plus current source/mailbox policy, approvalBoundary none, handler null, availability unimplemented, qualification pending, retry maxRetries 0 until adapter retry semantics exist. Map only that original ID when its descriptor/schema/fixtures are accepted; the other 95 selected mappings remain pending. No invented callable handler or enabled discovery record.

Model input is a closed object with exact keys `subject`, `threadId`, `messageId`, `messageLimit`, `bodyStart`, `bodyLimit`, `cursor`. `subject` reuses SubjectRequest and permits personal or one explicit client (not arbitrary actor/mailbox/tenant, nor implicit selected-client narrowing). `threadId` is UUID; `messageId` is UUID or null; `messageLimit` integer 1–10/default 5 when messageId is null, and exactly 1/default 1 when messageId is supplied; `bodyStart` integer 0–2000000/default 0; `bodyLimit` integer 1–6000/default 6000; cursor null or opaque bounded string <=256. No coercion. Defaults are materialized before argument hashing. These defaults/bounds are proposed normalized semantics, not legacy characterization.

`bodyStart/bodyLimit` mean Unicode scalar values in canonical stored plain text, with no whitespace normalization. Reject ill-formed surrogate input; hash exact UTF-8 normalized-source bytes, not a JS slice/hash of a preview. Null/missing body is not empty complete body. HTML-only source requires a separately versioned approved representation; this slice does not invent an HTML extractor. Message order is proposed oldest effective received-or-sent first/null last/ID ascending, preserving conversational sequence; this is intentionally separate from newest-first mail search. The same bodyStart applies independently to each selected message in that page; next body sections use the exact message selection and source version. Message and body continuation must never silently skip one another.

A server-resolved context reuses RunBinding, ResolvedSubject, NormalizedWindow, SourceState and Coverage definitions. Trusted context binds exact mailbox connection, tenant, actor, current client walls, ownership policy revision, source snapshot, arguments/filter digest and adapter version; none is accepted as authority merely because the request supplies it. Thread and message must agree on tenant/connection/thread and current nonremoved state. Personal mailbox selection does not bypass a message's client wall; explicit client selection cannot grant another owner's mailbox. Current active connection plus actual mail-read entitlement is rechecked on initial/continuation/citation/full-read use and after resume/revocation.

Use opaque server-held continuation bound to actor/tenant/policy revision/selected subject/thread/message/filter/order/window, source snapshot and exact next message/body position. Cursor expires with source retention/revision or authority; changing any binding refuses continuation rather than restarting invisibly. `asOf` alone is insufficient. If the adapter cannot retain an immutable snapshot, it returns disclosed partial/unavailable continuation support; it must not advertise snapshot-safe exhaustive enumeration. Snapshot ownership/storage is REL-03, not a contract package side effect.

### Preserve full-read evidence while transporting sections

Do **not** relax existing `assertEvidence`, add snippets to source-read, label fragments full-read, invent a new record-version for each chunk or mislabel a deterministic body page as candidate discovery. A message page can already contain only full-read records and still be partial because more messages remain. That existing behavior stays unchanged.

For incomplete bodies propose a closed operation-specific `MailThreadSourcePage` **transport** DTO in mail.schema, explicitly `evidenceReady:false`; it is not EvidenceEnvelope and is not citeable completed evidence. Header fields reference existing binding/subject/window/source/coverage types; canonical context/source eligibility checks are factored within the existing validator and reused, preserving old behavior. Exact page keys: `kind`=`mail-thread-source-page`, `operation`, `requestId`, `traceId`, `binding`, `subject`, `window`, `argumentsSha256`, `appliedFilters`, `sources`, `coverage`, `selection`, `messages`, `continuation`, `evidenceReady`, `negativeAssertion`. Selection is exact threadId/messageId/order/snapshotVersionId. Each message is exact mailboxId/threadId/messageId/recordVersionId/citationId/scopes/bodyCompleteness/contentSha256/readHandle/section. Section is exact start/endExclusive/unit/text/hasMore; unit is unicode-scalar; bodyCompleteness complete/truncated/missing/unknown. Text is nullable only when missing/unknown, bounded by bodyLimit; full-body content hash may be null unless actually known. Cursor/read handle is opaque, not a URL/credential. Unknown total stays null. negativeAssertion is always none.

The specialized validator enforces full context/source eligibility, unique immutable message-version identities, selection/order/range/count agreement, required read handles for every unfinished message, partial/unknown enumeration and no claim that retrieved fragments complete a source. A denied source contributes no body/metadata; legitimate partial data from other eligible sources is preserved. Reusing/factoring these checks needs a precisely scoped validator extension, not a second authorization implementation. No method/source-read invariant changes are proposed.

Only after complete same-version text/ranges are assembled and source completeness is positively established may the adapter emit the **existing** source-read EvidenceEnvelope with full-read records and actual content hash. Gaps/overlaps, changed versions, truncated upstream body or unknown completeness keep requiredReads unresolved. Completing one message is not completing the thread or mailbox. Empty/partial thread reads always use negativeAssertion none; no assertion that a commitment/email never existed. Oversize >2,000,000 scalar content cannot be completed under this initial bound and remains disclosed partial; future limits need review.

## Synthetic examples and meaningful future checks

Literal first input, not a real request: `{"subject":{"kind":"personal"},"threadId":"11111111-1111-4111-8111-111111111111","messageId":null,"messageLimit":5,"bodyStart":0,"bodyLimit":6000,"cursor":null}`. A body page with version `synthetic-v1`, start 0/end 6000/hasMore true is transport-only, evidenceReady false, requiredReads nonempty, partial coverage and no negative assertion. A known-complete 12-scalar single message assembled at version synthetic-v1 can become one full-read record; additional unread thread messages still keep overall status partial. These are proposed examples, not executed validation or source truth.

Negative literals: `bodyStart:-1`, `bodyLimit:6001`, `messageLimit:"5"`, injected `actorId`, a cursor reused with another thread/client/policy/version, wrong connection/thread message, denied/removed mailbox, bodyCompleteness unknown labeled full-read, two citations counted as two identical message versions, different chunk versions assembled together, and a partial page asserting absence must refuse. Unicode boundary (emoji/combining text), exact UTF-8 hashing, late-body decisive text, tied/null dates, missing vs empty body, multi-message body continuation, snapshot mutation/removal/revocation, and eligible+denied mixed-source partial output need literal fixture coverage. Contract tests validate shape/invariants only; adapter/live policy tests separately prove source semantics.
