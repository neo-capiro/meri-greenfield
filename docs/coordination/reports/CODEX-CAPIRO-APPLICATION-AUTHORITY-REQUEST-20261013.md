# Capiro application authority: narrow owner request

The existing production owners can verify a Capiro principal and authorize an active client-bound conversation. Their current HTTP DTOs do **not** close Meri's session receipts. Implement the two narrow Capiro bridge endpoints below; keep Meri's admitted run, attempt, worker, fence and policy scopes under Meri ownership. This is a metadata-only investigation and implementation request, not an implemented or live-qualified bridge.

## Exact requested Capiro interface

Add a small Capiro-owned controller/service boundary using existing authentication and policy owners, with closed DTOs and no new auth implementation:

- `POST /api/clio/application-authority/identity`, body `{}`; response `{principal:{tenantId,actorId},identityRevision,checkedAtMs,expiresAtMs}`. `actorId` is current backend `TenantContext.userId`, not Clerk's subject string.
- `POST /api/clio/application-authority/context`, body `{identitySha256,conversationId,clientId}`; response `{identitySha256,principal:{tenantId,actorId},identityRevision,conversationId,selectedClientId,contextRevision,checkedAtMs,expiresAtMs}`.

Both use the native bearer and current existing TenantContext. Bodies contain selectors and a correlation hash only. The context path must use the active owned conversation predicate, preserve portfolio access checks, require its nonnull stored client to equal the selected UUID, and apply current client visibility plus the existing ethical-wall owner. A null/unbound conversation, unrelated client, archive, removed membership or wall denial must refuse. No conversation creation/rebinding or latest-row selection is requested.

The context response must contain a freshly established principal and identity revision. Meri compares these to the exact verified identity snapshot; merely echoing `identitySha256` would not authenticate it. Revisions must come from actual server-owned authority state and change when relevant policy state changes, not from caller values or an arbitrary `Date.now()` nonce. The Capiro owner must document and test stable revision inputs: native session identity, verified principal, current membership role/status/version and any applicable impersonation state. Exclude dynamic checkedAt, lastSeen and lastActive values, which would invalidate every subsequent action. Context revisions similarly cover relevant conversation/client/wall/policy facts, excluding unrelated activity timestamps; hashing a selector alone is insufficient. Expiry must be bounded by the original verified JWT/session expiry and applicable current authority expiry. No fabricated TTL or local refresh may replace or extend that expiry.

Return only bounded authority metadata with `no-store`. Omit profile/contact data, raw claims, tokens, conversation content and private metadata. Preserve existing sanitized denial behavior. The required bridge must also check online/current native-session revocation through the existing Clerk backend session owner once its supported API is established. The traced verifyToken path alone does not provide that check. Capiro owns establishing the exact supported session API, current-status/expiry semantics and fail-closed behavior; this report neither invents that SDK method nor claims the requirement is already implemented. Source tests and live qualification must distinguish that new current-session check from existing signature/expiry and local membership/wall checks.

This request does not require Capiro to mint Meri scopes, grants, policy revisions, approvals, run IDs, attempt IDs, worker IDs or writer fences. Meri's adapter separately joins the fresh bridge facts to its trusted admitted command context and authoritative current-run port, requiring exact tenant/actor/conversation/client correlation, current policy revision and shortest deadline. Missing run ownership refuses rather than substituting telemetry, qualification rows or fixture state. The adapter implementation can be source-tested now, while deployment still requires both real Capiro endpoints and the authoritative Meri run composition.

The current authentication files carry the explicit change-control instruction: “Investigate read-only and PROPOSE first; wait for go-ahead before editing, merging, or deploying.” No Capiro implementation is changed here. The request belongs to its designated owner under the existing Neo approval rule; no auth, deployment or network approval is inferred from these source findings.

Reuse existing owner checks rather than copying their algorithms. Tests must state the actual revocation window and distinguish an identity hash echo from current authentication.
