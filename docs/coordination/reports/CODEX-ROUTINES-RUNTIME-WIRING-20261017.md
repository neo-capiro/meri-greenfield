## Delivered source and receiving boundary

The foreground feature is implemented through `createRuntimeRoutinesFeature`, captured as `routinesApplicationFactory` and created with the actual control assembly's opaque session owner. It composes actual native currentness, canonical proposal custody, schedule lifecycle and Temporal SDK calls. Missing owners return unavailable; the explicit feature kill switch does not inspect dependencies. Routes are admitted on the public listener by exact path and excluded from the private listener. No frontend UI is included in this source stack.

Preparation durably claims a request identity, captures its original release expiry and retains an immutable proposal. Exact replay rereads that proposal without allocating IDs. Approval requires the same original owner, original request hash, ID/digest, current native identity/client/scopes and positive policy. The server derives the canonical human decision; a journal record supplies custody only. Approval must occur before the original captured release expires; this implementation does not renew that window. Acknowledged replay reads the existing effect. Unresolved mutations are never resent; reconciliation observes the exact old provider effect and gates metadata acknowledgement with fresh authority. Revocation and lost acknowledgement preserve `ACKNOWLEDGED_NOT_RELEASED`, `UNRESOLVED` or `UNKNOWN` rather than claiming no effect.

The separate service exports `startScheduleWorker(configuration,{runtimePorts,signal})`; it reuses C's existing poller and composes the actual PG schedule owner, PR120 instruction custody bridge, conversation store, native original-binding and original-input owners, dispatcher and run evidence. Required firing authority and native admission are captured before secrets or connections. Schema presence is checked read-only before polling. Borrowed resources are retained; owned resources close after the poller in reverse order. The service is source-complete at this receiving seam; the main CLI/config/package edits remain **PROPOSED, NOT APPLIED** in [the exact primary receiving proposal](CODEX-ROUTINES-PRIMARY-RECEIVING-20261017.md).

The additional control-host ABI proposal is to pass its already borrowed Temporal `client` into `productPortsFactory`. That lets the trusted host construct this foreground factory, while `product-applications` supplies the actual sessions after canonical session construction. This lane did not edit `control.mjs` or any currently owned first-chat entrypoint, configuration, image or infrastructure path. The primary must reconcile this receiving proposal against its current head; the documented baseline is PR121 `0d6ba1590b41e3bc911e8c50f7c7407632101832`.

The native worker adapter supports an exact configured original owner/client/policy/task/allocation profile. It rejects an unenforceable smaller cost cap, nonzero retry policy, changed configuration/task/destination or unsupported scope rather than pretending the static prepared runtime can enforce it. It fixes admission eligibility; it does not implement a standing unattended policy producer, broad per-owner allocation, output delivery, or proven physical stop. Full per-occurrence total-cost/retry/cancellation policy and inbox delivery remain the explicit product choices above.
