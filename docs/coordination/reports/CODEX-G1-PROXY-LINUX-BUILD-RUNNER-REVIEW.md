## Findings requiring repair

**F1 — output accepted after the child exits can exceed the stated cap.** In preserved `linux-run.py`, lines 54–68, `run()` tests stream sizes only inside `while process.poll() is None`. If a child exits before the first poll, or writes beyond the limit between the last size check and exit, that branch never sets `exceeded`. An allowed exit code then passes, and `stdout.read_bytes()`/`stderr.read_bytes()` read the complete files without a final size check. A rapid oversized Docker response can therefore bypass the declared 32 MiB acceptance bound. Even while the process is alive, regular-file polling permits disk output to overshoot between polls; this is not a physical stream cap. The next version should drain pipes while counting all observed bytes, write only a bounded prefix, record truncation/incompleteness, check final counts before accepting any result, and fail closed. This finding follows directly from source control flow; no oversized child or candidate run was executed here.

**F2 — the finally upload can disappear on a capture failure.** The inline packer in `buildspec.json` (generated by `prepare-buildspec.py`, lines 26–40) asserts every result file is at most 32 MiB and the total at most 512 MiB before writing the capture manifest, archive and S3 object. The recipe has `set -e`. Thus an oversized raw stream left by F1, or even an overshoot correctly detected during polling, makes finally fail before upload. The raw failure evidence remains only on the ephemeral builder; there is no guaranteed bounded failure bundle. A repair should preserve receipt JSON first, retain explicit bounded prefixes and truncation/observed-length facts, and upload a bounded incomplete bundle without presenting missing evidence as success. The source must continue to refuse invalid links/types rather than archive them. ROOT's proposed repair direction addresses these responsibilities, but its new bytes require separate review.
