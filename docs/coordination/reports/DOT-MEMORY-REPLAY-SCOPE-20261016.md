# CORE5 retained correction: current proposal scope before resubmission

Independent review of `89aaff209217bc86e49c866c57d83a2f6bd6590a` found that immutable correction replay preserved the original candidate but checked only retained-read visibility before a possible resubmission. That visibility enforces tenant, proposer and current client membership. It intentionally does not grant `memory.propose.firm`. If Core status could not establish a receipt, a retained firm correction could reach `review.submit` after that business permission was removed.

`apps/control/memory/producer.mjs:submitRecord` now applies the existing `assertProposalScope(principal, record.candidate)` immediately before any submit. It checks the immutable retained candidate rather than the mutable correction target. Tenant/proposer/client visibility remains first; acknowledged/status-only paths retain their existing visibility semantics. PREPARED custody, SUBMISSION_UNKNOWN custody, original candidate/hash and current Core status reconciliation remain unchanged. No new permission, policy, target read, journal or wire is introduced.

The focused controls use the actual producer, eligibility, candidate, wire and Core adapter code over the existing synthetic journal/Core transport doubles. Only the declared hash dependency is replaced by SHA-256 of JSON bytes; real canonical JSON, membership authorization, Core and PostgreSQL remain unqualified. They add six tests:

- Four negatives cross PREPARED/SUBMISSION_UNKNOWN with lost submission acknowledgement/status unavailable or never-received submission. Removing firm proposal permission must yield MEMORY_SCOPE_REFUSED with **zero new submit**, even after the mutable target is deleted. The prior published source performs an extra submit in all four cases.
- A retained known Core review remains visible through status/list and a status-only correction replay after proposal permission removal, with no submit/target read.
- A never-received retained candidate remains readable without proposal permission, while restored permission submits exactly the original candidate/hash and original correction reference, without rereading the target.

Reproduction: `./docs/qualification/candidates/dot-budget-planner-20261016/run-controls.ps1 -MemoryScope`. The runner temporarily reads producer bytes from the exact prior published pin, runs the four negative cases, and restores the repaired bytes in `finally` with SHA-256 verification. Results: **4/4 expected failures before** (each proves two submit attempts where one was expected); **22/22 pass after**, including the 16 preserved producer controls. One Node process at a time, heap 128 MiB, test isolation disabled, concurrency one, 30-second deadline and own-process cleanup; sampled maximum working set **51,011,584 bytes**. Actual argv, exits, durations and byte restoration are in `memory-scope-controls.json`; stdout/stderr are retained separately. Tested repaired producer SHA-256: `5acba862dc5994790b29263708e208c7e44f0c98c81c93a7ef66aa92d7fe18b1`.

No broad suite, dependency install, compiler, browser, database, provider, credential or cloud action ran. Earlier failed/unrun evidence and historical manifests/proposals remain unchanged. This is a focused successor for independent source review, not a claim of live authorization qualification.
