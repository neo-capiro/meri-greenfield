## Exact design requested for parent review

- One primary key is `(tenant_id, actor_id, conversation_id, delivery_id)`, with SDK delivery syntax and existing identity bounds. Run/attempt changes in the same conversation cannot create a second preparation for the delivery. The immutable record holds the exact operation id/version and arguments SHA-256, plus its canonical record hash. Changed records conflict.
- Claim inserts PENDING with SQL NULL outcome, created timestamp and no settlement timestamp, using the scoped unique key. Conflict reads that exact key after the insertion attempt. There is no check-then-insert, dispatch retry or claim replacement. PostgreSQL unique-key arbitration must be tested on a real database; the current serialized double does not establish it.
- Only the matching PENDING record may settle once to PREPARED, FAILED or UNKNOWN. Identity, delivery, record/hash and terminal state/outcome are immutable. Terminal settlement needs a non-null timestamp; PENDING must have none. PENDING/UNKNOWN outcome is SQL NULL, not JSON `null`. The exact DDL constraints/immutable-update trigger need explicit design release before authoring.
- PREPARED outcome is `{result, release:{binding,scopes,expiresAtMs}}`, as one custody write. The canonical result-release proposal remains subject to acceptance. A legacy PREPARED result without release metadata may be retained/read by the journal but is withheld by the mount. Stored custody never implies current authority. FAILED contains a closed canonical failure code. No UNKNOWN claim becomes executable from expiry, cancellation or absent acknowledgement.
- A claim commit acknowledgement loss returns UNAVAILABLE through the existing journal without invoking a preparer; a retained PENDING entry then returns UNKNOWN. Settlement commit loss returns UNKNOWN; an independently recovered PREPARED entry can replay the same output after fresh authorization. No blind rollback claim is made after an attempted COMMIT.
- No deletion is exported. Any future retention design must preserve a non-reusable delivery fence for a purged result; deleting an idempotency claim and silently preparing again is not approved. Retention roles/policy and migration execution are separate decisions.
