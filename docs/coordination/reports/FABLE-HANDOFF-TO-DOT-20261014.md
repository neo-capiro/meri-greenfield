## 5. Proposed amendment to migration 0009 before allocation

Completion checkpoints need their own durable row. The existing `meri_conversations.checkpoints` table requires a `control_id` foreign key into `controls`, and every row of `controls` must decode as a lifecycle command. Adding a `complete` intent would change the private lifecycle contract (`packages/contracts/conversation-lifecycle`), which AGENTS.md requires to be proposed to Codex before editing. Fable therefore proposes, inside the same unexecuted migration source, a table `meri_conversations.completion_checkpoints (tenant_id, conversation_id, run_id, checkpoint_id, proof jsonb, proof_sha256, PRIMARY KEY (tenant_id, run_id), UNIQUE (tenant_id, checkpoint_id), FK to runs)` with the same `BEFORE UPDATE OR DELETE` immutability trigger pattern, one row per completed run. `next-run-journal.mjs` would read it instead of the controls join, and the test fixture would use the real journal method. Decision requested: amend 0009 (one migration for the feature) or allocate 0010.

## 6. Slice B implementation outline (IMPLEMENTATION-STANDARDS §4), not started in code

Responsibilities and canonical owners:

1. Session issuance for the target run. Owner: `apps/control/action-host/application-adapters/context-adapter.mjs` (`createApplicationContextAdapters`) joined by `apps/runtime/prepared-candidate.mjs` (`createPreparedCandidateIdentity`, proof row). Today the adapter admits only the single configured `commandContext.binding` and refuses any hint that differs. Proposed change: an optional `selectRun` port (trusted control only) consulted when the hinted `conversationId` equals the configured conversation; it returns the selected run binding (reserved target or live latest) as a JSON fact `{binding, policyRevision, deadlineMs, checkedAtMs}` and the adapter then calls the existing `currentRun` on that binding and pins it for the session. Without the port the adapter is byte-for-byte today's behavior. The prepared candidate supplies `selectRun` from `createNextRunOwner` over its store, with `retirement.verifyRetired` reading `store.allocations` and `revocation.verifyRevoked` reading the budget grants through `createNativeAllocationAdmission.read`/`revoke` facts. Independent controls to extend: `adapters.test.mjs`, `context-independent.test.mjs` (hint selection must still refuse another conversation and a run outside it).
2. Completion checkpoint before disposal. Owners: runtime capture `apps/runtime/native-authority/checkpoint-capture.mjs` (proof row) and task source `task-checkpoint-source.mjs`; control journal `apps/control/conversations/lifecycle/journal.mjs` (new method, no contract change) or a small `completion-journal.mjs` beside `next-run-journal.mjs`; worker activity `apps/worker/conversation/activity.mjs` and `continuation/activity-lifecycle.mjs`. The capture window exists only while the CLI is alive: with streaming input (`createConversationInput`, always on the remote path) the CLI stays alive after the `result` message until the input is closed, which is where the hold capture already runs. Proposed flow at `result`: the activity calls a new `lifecycle.captureCompletion` (route `/v1/runner/checkpoint/complete`, task capability) instead of closing the input first; the controller's capture owner reuses the quiesce, snapshot, object publication and readback steps of `captureCheckpoint` but publishes through the completion journal, which inserts the `completion_checkpoints` row and appends `checkpoint.verified` and `run.status completed` in one transaction (the activity then skips its own `completed` publication). Failure before the journal commit leaves the run `running` and the task's capture state `unknown`; the existing failure path then records `failed` with no checkpoint, so no next run can be reserved (`NEXT_RUN_SOURCE_NOT_COMPLETED`). `recordCheckpoint` and the hold path stay unchanged.
3. Per-run issuance inside the existing owners. `createNativeAllocationAdmission` requires the allocation JSON's `run` keys to equal the binding and one grant intent per capability digest; `allocateRemoteNativeController` compiles one `original` per binding from `runtime`, `plan` and `preparationIntent`. For the reserved target the prepared candidate must compile a second `original` with the target binding, a per-run allocation JSON derived from the configured one with the target's `run` keys, per-run grant intents, and a per-run task request; the admission then installs grants atomically as today. What source cannot do: mint the per-run task capability. The grant intent carries only the capability digest; the capability value is issued by the native capability provider (W03 packet row "Native capability provider", owner shipping/dot). Slice B can therefore prepare and prove everything up to a capability whose digest is configured, and the controller for the second run needs the provider's issued value at runtime. Dot's decision: whether a per-run capability issuance port on the provider is in scope for the pilot, or whether the pilot reuses one task capability per conversation with per-run grants (weaker, and it must be stated as such).
