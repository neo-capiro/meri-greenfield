## Existing canonical owners

Meri public `meri.schema.json` already owns immutable Command, ApprovalProposal,
ApprovalDecision, CommandExecutionRequest, CommandReceipt, ArtifactVersion and
ScheduleProjection. `validate.mjs` checks command hash, proposal expiry and stable
execution identity; structural validation does not authorize or persist actions.
The Command action enum is exactly `memory.propose`, `task.create`, `artifact.file`.
Reuse it; do not create a second approval engine or reinterpret another action to
smuggle task updates or schedule mutations through it.

Frozen Capiro action-proposal input/public-result types and contract tests establish
server-owned payload fingerprints, policy identity, expiry, exact stored execution,
single claim, owner/tenant refusal and distinct ambiguous outcomes. Schedule receipt
readback can confirm historical creation without claiming it is still active;
missing receipt leaves uncertainty. These are source requirements, not permission
to copy its orchestration or scheduler. Its older meri-approval service is not an
execution authority. No private implementation is included in this checkpoint.

## Decisions versus routine follow-up

1. **Central contract/action surface:** choose how task.update and application
   schedule lifecycle commands use the canonical command/approval protocol. They
   are absent from the frozen public 0.1 action enum. This needs central allocation;
   a private shape contract can proceed without editing public exports.
2. **Current task authority:** the inspected ordinary task update path does not
   establish the complete actor/wall authorizer. The engagement/current-policy
   owners must identify the existing rule or explicitly decide a missing rule;
   tenant lookup alone must not be promoted into permission. This checkpoint does
   not assert that the whole application lacks such a rule.
3. **Selected replacement semantics:** memory proposal-only execution needs a
   candidate-only source adapter despite legacy personal auto-commit; this is
   implementation against an already chosen scope, not a reason to reopen memory
   policy. New Temporal owner must specify supported lifecycle/in-flight behavior
   under existing selected scope. Legacy automatic email is not implicitly adopted.

The approved Institutional Memory exception remains exact: authorized user_admin
and capiro_admin may approve their own shared candidate without assigned-reviewer
membership, but never bypass tenant/client/wall restrictions. Standard firm/client
requirements, personal owner isolation, exact automated personal review paths and
separate shared reject/withdraw restrictions remain intact. The old wrapper's
unconditional another-reviewer wording is a known source-owner correction, not a
new consequential approval question. This discovery adds no grant decision.
