The backend must retain its authoritative schema, contract generator and public package/artifact ownership. `packages/contracts/validate.mjs` currently reads the schema through `node:fs`, hashes with `node:crypto` and compiles Ajv on import: it is the **Node qualification validator, not a browser entry point**. ## Concrete application organization

This is a destination proposal, not files/directories to create as empty feature stubs:

```text
capiro-frontend/
  apps/web/src/app/           thin Next entry/layout and approved routing
  apps/web/src/shell/         shared header, active mode, account/nav presentation
  apps/web/src/features/meri/ Meri screens/local interaction composed by capability
  packages/ui/               canonical adopted presentation primitives/tokens
  packages/meri-client/      validated event consumption, projection, React facade
  packages/qualification-transport/
  packages/qualification-elements/
```

Start `features/meri` with the actual conversation/composer integration. Add activity/approvals/artifacts/scope/schedules modules only with their real screen/API contracts and callers, keeping a thin page/container. The shell owns common navigation presentation; Meri owns its domain views. `packages/ui` has no model, source access, tenant authorization, persistence or workflow policy. `meri-client` depends on the public contract artifact, ai7.0.137/@ai-sdk/react4.0.140 and React19.3.0, never on private backend implementation. Product flow: web shell/Meri feature→meri-client and ui; client→public contracts and upstream UI transport. Backend separately→public contracts and upstream stream writer. There is no reverse dependency on `apps/web` and no frontend provider/orchestration loop.

Future Portfolio, Modules and Settings are frontend ownership areas, not implemented features in this migration. D008 remains the current execution rule: authenticated independent Meri entry, Meri active, unavailable Portfolio/Modules destinations disabled. Shared hosting may eventually provide verified authorized destinations; it does not justify invented routes, credentials in URLs or passing client hints as authority. Meri Preferences remains its planned existing v1 capability; future global Settings cannot silently replace it. Actual routing, canonical Clerk/server membership integration, versioned tenant/client handoff and revocation checks remain open. Next16.4.0 is a candidate in COMPONENTS, not a dependency or build proven by these packages.

Use the adopted owned-section design only:85 main roots including5state boards,29overlays,60state examples,15families/70variants,11starts, initial34Home rows. These are reference counts, not functional control coverage. Full semantic control mapping,18styles/light/dark/browser themes, responsive/keyboard/accessibility and live behavior still need implementation/checks. The separate frontend approval expands repository ownership, not adoption of other Figma sections or Portfolio/Modules implementations.
