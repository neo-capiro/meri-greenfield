## Meri-owned execution remains outside capiro-backend

Conversation submission/history/events/cancellation and opaque action sessions; PostgreSQL Meri run/event/budget/session journals; Temporal workflows and native task broker; SDK SessionStore/registration observation; trusted runtime/model proxy; skill selection/MCP/continuation; approvals/governed output; DOCX/artifact generation/storage/rendering all live in meri-greenfield and its separate trusted stack. The new gateway relay forwards ten task operations only to Meri control, never to Capiro. The backend should not implement `/v1/runner/*`, `/v1/worker/authorize`, execution launch/poll/runtime/readiness or an SDK/model loop to serve this integration.

No rebuilt Meri callsite here requires legacy `/meri-api`/MERIV2_ORCHESTRATOR_URL orchestration, recipes/planner/semantic agent gateway, old queue/worker/frontend runtime, or legacy Office generators. Keep ordinary data/auth/domain services and extract the two authority handlers from their historical Meri location, retaining the existing wire/current permission checks. This task authorizes no deletion or production capirov2 change; the backend owner performs its separate successor audit/removal.
