### Full context/recent coverage for unlinked prospects (proposal only)

The implemented two-operation subset still refuses a prospect with `linkedClientId:null`. The existing context request/receipt requires a nonnull client UUID and requires both the stored conversation client and prospect link to equal it; passing a fabricated client, replacing null with the conversation's selected client, or substituting the Meri run conversation would be false authority. Keep that closed endpoint and its validators unchanged.

The smallest additive proposal is a purpose-bound sibling POST `/api/clio/application-authority/prospect-context`, restricted to these two reads. Its closed request is `{identitySha256, conversationId, purpose}`, where `purpose` is exactly `get_business_development_context` or `get_business_development_recent_changes`, the hash is the real current identity receipt hash, and `conversationId` is the explicit canonical Core UUID. No caller-supplied prospect ID, owner, nullable client override or roster is accepted. Its proposed closed receipt is `{identitySha256, principal, identityRevision, conversationId, purpose, prospectId, conversationSelectedClientId, prospectLinkedClientId, resourceRevision, checkedAtMs, expiresAtMs}`. Both client fields are independently observed `UUID|null`; they must never be conflated. Prospect ID is an actual persisted UUID; the resource revision binds the current prospect's organization/link/scope version and the current conversation tuple, so no organization fields need be exposed.

Reuse `loadOwnedActiveClioConversation` and `authorizeMeriProspectScope` before content retrieval. Require the exact authenticated tenant/actor's active, unarchived Core conversation and its actual current prospect scope. Every nonnull stored conversation selection and prospect link must independently pass the existing current client visibility/wall owner, even if they differ. For the unlinked branch, issue only an actor-owned **native conversation/prospect** grant and admit it in Meri only under a coherent current actor-bound personal task subject; a prospect-specific subject would require its own separately approved canonical subject/grant allocation. This is not a claim that a prospect row is actor-owned, nor an invented `prospect.ownerUserId` equality. A client task subject must not silently become this personal grant. Existing linked-client requests retain their exact selected-client admission until broader distinct-link semantics are explicitly reviewed.

Allocate backend changes to `apps/api/src/auth/application-authority.controller.ts` (sibling route), new `apps/api/src/auth/application-prospect-authority.ts` and `.spec.ts` (closed DTO/receipt and purpose-specific repeated current observations), reusing `apps/api/src/context/application-authority-resource.helpers.ts`, `context/context-security-scope.service.ts` and `business-development/bizdev-meri-scope.service.ts` as the actual resource owners.
