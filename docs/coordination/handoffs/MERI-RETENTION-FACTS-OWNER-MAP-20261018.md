# Meri retention facts owner map — 18 October 2026

This is a source coordination map for the production `facts` argument to `apps/control/retention/purge.mjs:recomputePlan`. It does not qualify or enable purge. `apps/runtime/control.mjs` composes `purge:{enabled:false}` and `apps/runtime/config.mjs` refuses `purge.enabled:true`. The only complete `facts` implementation is the synthetic `apps/control/retention/test/fixture.mjs`. The canonical active-class list is `apps/control/retention/data-classes.mjs`; `inventory-source.mjs` requires all 14 explicit non-continuation snapshot fields and adds only the store-owned proposal continuations. The pure enumerator synthesizes log and telemetry markers; planned editor drafts remain optional and are refused if present.

## Facts contract and implementation order

`recomputePlan` requires six current facts: `policy`, `inventoryFor`, `sharedFor`, synchronous `holds`, `liabilities`, and `lastActivityFor`. Before composing production `facts`:

1. The policy owner must publish a versioned complete class policy, duration and cooling choices, nonpurgeable retained classes, subject mapping for schedules and surface memory, and a rule for last activity across conversation, artifact and external owners. `policy.mjs` validates a supplied policy but produces none.
2. Existing data owners must add bounded, exhaustive, hash-checked retention reads for the rows above, then define a coherent snapshot or version/fence protocol across the local and Core sources. Per-run APIs and the process-local `createReferenceIndex()` do not prove complete cross-subject holders. Integrate 0018 local memory classes before calling the snapshot complete. The existing `inventory-source.mjs` can consume the resulting complete base snapshot without another wrapper.
3. The object/storage owner must provide current per-version legal-hold and Object Lock retention facts. The planner's `holds(object)` is synchronous, so the owner must prefetch and pin those facts for a recomputation or explicitly revise that planner contract; `storage-port.mjs:headVersion` reports presence, not hold authority. The liability owner must aggregate unresolved run/task/export effects; the product budget view covers money only.
4. The canonical PostgreSQL row owner must gain exact routes, target records, guarded triggers and recovery readback for every row class. `postgres-journal.mjs` currently routes only SDK entries and artifact versions in production; its proposal-continuation route is synthetic-qualified only. Most active row classes therefore fail preflight even if a complete snapshot were supplied.
5. Only after the source contracts and independent review should `apps/runtime/control.mjs` and `apps/runtime/config.mjs` bind the complete facts, ledger, storage and row owners and review the purge switch. Today the CLI does not construct a production `retentionLedgerSink`; a read gate cannot claim a recovered external ledger without it.

Source work includes the owner-specific enumerators, registry/policy/subject decisions, coherent snapshot and current-facts implementations, exact row routes and focused source checks. Live qualification separately requires installed migrations and narrow roles, actual PostgreSQL concurrency/restore and trigger behavior, S3 Object Lock/legal-hold permissions and readback, the Core retention API and service identity, an acknowledged ledger sink, and measured image/config/readback. No missing owner may be represented by an empty list or a synthetic fact.

## Local 0019 control, source only

Migration `apps/control/conversations/migrations/0019_memory_proposal_contexts.sql` (SHA-256 `117c105ba4fca00c3ee3e76816cae1b00fe5be7a7841f286c83af8d04be97d57`) was applied with conversation 0001 and retention 0010 in a disposable PostgreSQL 16.15 container using a cached image, `--network none`, tmpfs PGDATA and no published ports. Three synthetic context rows exercised the trigger. A same-transaction exact PLANNED target under the current SUPPRESSED plan and ledger generation deleted exactly one row. Committed old, wrong-row, wrong-plan, released-subject, projected-plan mismatch and ledger-generation mismatch targets refused; UPDATE and TRUNCATE refused. Narrow NOLOGIN writer, purger and ungranted bystander role checks passed: the writer could SELECT FOR UPDATE and INSERT but neither DELETE nor mutate an existing row; the purger could execute the exact DELETE but not INSERT contexts; the bystander had no schema or table access. The migration granted nothing. The container and temporary fixtures were removed. This is local SQL behavior, not production role, migration, recovery or live purge qualification.
