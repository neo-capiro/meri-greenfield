## Source ownership

The gateway's `memory-read-context.mjs` remains the current authority for the continuation key, previous-page check, receipt check and final release. The existing control conversation store now owns `memoryProposalContexts.forTask({binding,clientId,policyRevision,expiresAtMs,signal?})`. It returns `loadPrevious` and `retain` over the store's borrowed PostgreSQL pool and per-conversation transaction lock. Each call checks the canonical conversation serving gate before and after the transaction, then rechecks the locked run binding, writer fence, actor, selected client, policy revision, running state, unheld state, original ADMITTED allocation and STARTED launch. Rows are immutable, keyed by the full tenant/conversation/run and canonical continuation-key SHA. An exact replay returns the same receipt; a changed record refuses. The second and later pages must have the immediately preceding durable page under their original cursor; the canonical validator checks page-to-page progress and ordering. A three-page continuation check covers this path.

The CLI constructs an inert `memory-context-relay.mjs` only when the measured family set includes `memory-proposals`, passes `relay.forTask` into `createSelectedRetainedTaskPorts`, and gives the relay to control startup. Control binds it to that control's conversation store before listeners, closes it during shutdown, and checks the proposed relation at readiness. Captured ports also refuse after relay close. Missing retention gate/store or relation fails closed. The memory task composer now admits the already validated production task tuple, which includes allocation and run facts beyond its five required keys.

The proposed relation is in `docs/coordination/proposals/memory-proposal-continuation-20261018.sql`. This is **not a numbered migration and must not be applied directly**. Retention inventory source now requires `memoryContinuations` and lists each distinct continuation row as a conversation row target. The canonical inventory producer and PostgreSQL purge row owner do not yet consume this target, so the relation is not production installable. Its purge preflight currently returns `RETENTION_ROW_CLASS_UNSUPPORTED` if such a target is supplied. The known retention ledger append/projection race is also unresolved; pre/post serving gates are not an atomic suppression fence.
