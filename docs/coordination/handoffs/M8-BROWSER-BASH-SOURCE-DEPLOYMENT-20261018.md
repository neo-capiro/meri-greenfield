# M8 browser and Bash: source deployment proposal (18 October 2026)

## Implementation outline

1. **Ownership.** Keep the existing browser policy, permission gate, run lifecycle, egress decision and proxy, and SDK Bash sandbox settings as the canonical behavior. Add one D005 per-conversation isolated-host owner for provisioning, attestation, run-bound proxy grants, process observation and verified destruction. Application/control and Temporal services retain their approved placement. The integration owner alone changes the shared runtime composer and render; the image owner alone changes Dockerfiles and locks.
2. **Modules and interfaces.** Define small host binding, launch, grant, readiness, observation and teardown modules behind the browser runtime port and trusted capability-preparation facts already consumed by `apps/worker/conversation/activity.mjs`. Infrastructure definitions describe the host's private subnet, blocked direct egress, control channel and bounded cleanup. Reuse `createEgressControl`, `startEgressProxy`, `startBashEgress`, `checkSandboxReadiness` and the existing D005 qualification source.
3. **Dependency direction.** Trusted control/Temporal lifecycle issues a conversation-bound host allocation. The host adapter supplies policy and approval/artifact ports from their canonical owners, plus a run-specific browser proxy grant and Bash sandbox facts. The worker passes these into the single Claude Agent SDK query. The host never receives database, provider, source-administrator or long-lived user credentials.
4. **State and failures.** Persist host allocation, active run, expiry, revocation and destruction evidence under trusted control ownership. Refuse an expired, replaced, mismatched or unqualified host. A grant's unknown outcome is quarantined until revocation or destruction is verified. Unknown process exit or physical teardown fails the run and blocks host reuse. A host is never reused across conversations or tenants.
5. **Verification.** Source tests cover binding/currentness, policy intersection, proxy deny cases, fail-closed startup and cleanup. A later exact-image host qualification proves browser and renderer sandboxes, SDK Bash sandbox, no bypass around the allowlist, revocation, and physical cleanup. Only then may an independently reviewed activation change open the browser gate and admit Bash on that host.

## Status and authority

This is a **source-only proposal**, not a deployment or an activation record. No cloud resource, IAM, security group, route, secret, credential, database, network rule, build or running service changes are made by this document. Its detailed file plan and acceptance sequence follow below.

### Host allocation and currentness protocol

1. Control resolves the actor, tenant, selected client, role and current admitted run from its persisted owners. It computes the effective browser policy and SDK capability policy from their existing platform maxima. It selects a D005 host only when the exact image/source/config tuple and host capacity are admitted. The host allocation has one immutable tenant/conversation/generation; a run is separately attached by exact `RunBinding`. No model argument or UI scope hint chooses a host, origin, role or grant.
2. Before guest startup, control records an allocation and arms an independent managed deadline/teardown owner. Guest bootstrap verifies the immutable image digest, kernel/container settings and private control channel. The supervisor reports readiness only after non-root/browser/renderer and SDK sandbox readiness probes pass on the actual candidate. A failed probe leaves the host unavailable; it never sets `available:true` from a fixture or a Fargate assertion.
3. At each run start, control rechecks current allocation, run/attempt/worker/fence, tenant and client walls, policy revision, expiry, cancellation and quarantine. It issues a task-bound admission to this host/generation and a `createEgressGrant` whose `policySha256` matches the fragment. The host compares both to its local immutable allocation. **Expiry alone is insufficient for revocation.** A bounded currentness lease must be refreshed from control; if refresh is absent, contradictory or stale, the host revokes the browser and Bash proxies, closes live tunnels and quarantines the run. The refresh interval/TTL are chosen against the release's approved numeric revocation bound and measured; do not assume an unapproved bound. Policy widening during a run requires a new run grant and fragment, while narrowing revokes the old grant immediately.
4. Browser interactions still pass `permissions.mjs` and the canonical approval owner before execution. Navigation, redirects, subresources, downloads and WebSockets must also pass the host egress boundary. Networked Bash runs with `autoAllowBashIfSandboxed:false`, the existing Bash approval gate and the exact domain-list digest. A sandbox refusal never triggers an unsandboxed retry.
5. On completion, failure, cancellation, pause, worker death, lost grant acknowledgment or deadline: revoke both proxies first; close SDK/Playwright/Chromium processes; verify browser profile/HOME/output and Bash workspace disposal; publish a content-free receipt; destroy the host at conversation end/lease expiry. An unknown process exit, network revocation or host/root-volume absence is **UNKNOWN**, leaves allocation quarantined and requires independently verified destruction before replacement admission. An AWS terminate acknowledgment is not proof of absence.

### Network and sandbox boundary

- The host has no public address and no inbound public listener. A reviewed private route carries only trusted control/model/artifact traffic. Worker processes have no DB/provider/admin credentials; the SDK parent receives only its existing short-lived task-bound model-proxy capability. The browser MCP, Chromium and Bash subprocess environments/filesystems cannot read that capability or any source credential. The host role is limited to exact image retrieval and its own logs/crypto needs; it has no source, database, ECS/EC2 control or broad S3 authority. Any production IAM, VPC route or NAT change is a separately reviewed activation step.
- Run the SDK parent and the untrusted browser/Bash processes under distinct Linux users/cgroups/network compartments. The browser MCP and Chromium enter a dedicated tool network namespace **before** the MCP starts; the source requires a reviewed launcher for this rather than assuming `server.mjs` already moves its child. That namespace has a loopback relay at the literal `127.0.0.1` (or `::1`) endpoint required by the tightened `server.mjs` contract and one veth path to the host proxy ingress. Host firewall rules admit from that veth only the pinned proxy ingress port, then forward to the existing `startEgressProxy` listener on the host's loopback; they deny direct DNS, metadata, private VPC, trusted-control and public destinations. The relay belongs to one run, can reach no destination other than that ingress and closes on revocation. The SDK Bash sandbox uses its own namespace and Meri's `httpProxyPort`/`socksProxyPort`; its confined SDK bridge reaches a separate local relay to the same run-bound Bash proxy, without arbitrary Unix sockets or local binding. The host proxy alone resolves DNS and dials the checked public IP. The qualification image's `--network none` result is distinct from this production bridge and cannot qualify it. A reviewed OS/namespace rule and native bypass probes must deny direct TCP, UDP/QUIC, DNS, WebRTC, metadata and trusted-control access from browser/Bash cgroups. Security groups alone do not distinguish the proxy process from Chromium on one EC2 ENI.
- Browser grants carry exact effective origins. For every proxy admission, `createEgressControl` rejects unlisted origins, private/special addresses, mixed A/AAAA results, non-web ports and stale grants, then dials the returned IP literal. The host must not route browser requests through Bash's looser domain allowlist. The browser's Playwright `--allowed-origins` and `--blocked-origins` flags remain defense in depth, not the enforcement claim.
- The current HTTP CONNECT proxy cannot see the HTTP origin inside encrypted TLS, so it does **not** prove the mandatory effective-origin allowlist against HTTP/2 connection coalescing, ORIGIN frames or domain fronting. Before activation, the source owner must choose and review a per-request enforcement mechanism or prove on the pinned Chromium/MCP/image candidate that those routes cannot bypass policy, including hostile same-IP/same-certificate probes. If the B12 probe fails or visibility is inadequate, keep `BROWSER_ACTIVATION` held; do not paper over it with a successful outer CONNECT log. Public navigation also requires a separately reviewed network path; D005's existing closed-network qualification stack authorizes none.

1. **Freeze and review.** Repin PR #145; allocate exclusive module ownership. Reconcile the latest D005 qualification source and the inert watchdog. Finish the missing positive volume-absence decoder from actual AWS wire evidence and prove managed survival/termination before a production host definition can depend on it. 2. **Implement source only.** Add host allocation/currentness, supervisor, port adapters and import-safe infrastructure DATA modules above. Keep `BROWSER_ACTIVATION` held. Have the integration owner wire the prepared-run placement and existing browser/Bash facts in the shared composer; the image owner adds packages through reviewed locks and image closure. Approval/artifact owners complete their canonical ports. No schema/contract/shared-file edit happens without its owner and central migration allocation.
3. **Focused offline checks.** Exercise exact binding and stale-generation refusal; platform/tenant/role narrowing; zero-origin behavior; DNS/private/mixed/rebinding/redirect/WebSocket/port/proxy-bypass simulations; Bash digest/approval/unsandboxed refusal; unknown grant and cleanup quarantine; finite watchdog transitions. Run only affected module and existing M8 tests during source development. Offline checks prove source behavior, not isolation or admission.
4. **Exact-host qualification.** After separate authorization for image build and cloud changes, build and scan the exact candidate, review the change set and source/image/config pins, then run the D005 host probes. Record every `browser/ACTIVATION-CHECKLIST.md` A1–F1 item on the real non-root Playwright MCP/Chromium browser and renderer, plus the SDK Bash startup and a real sandboxed command with denied filesystem/credentials and allowed/denied network probes. Test cancellation, revocation/currentness loss, browser/Bash direct-route attempts, same-IP certificate coalescing, worker death, host timer, host termination and exact root-volume absence. Preserve failed evidence and scrub content/credentials.
5. **Independent gate.** The security/host reviewer verifies actual isolation, per-hop allowlist, image scan, task-bound authority and cleanup. The canonical approval/artifact owners verify their live round trips. The integration owner then proposes an evidence-citing `BROWSER_ACTIVATION` opening change and a separately reviewed deployment packet with initial platform-approved named origins; the default destination list stays empty until that explicit platform configuration. Bash is admitted only from a current host attestation and effective policy. Neither a source test nor a readiness CLI exit opens either capability.

### Owner handoff and blockers

- **M8 source owner:** host allocation/supervisor/port/infra DATA code, focused tests, exact source proposal and negative evidence. Do not change shared runtime composer, image/locks or activation record by assumption.
- **Integration owner:** route the single SDK conversation execution unit to the D005 host, connect `browser` and Bash trusted facts, render flags/status, own deployment packet and final activation source review. A held browser must be presented as held even though the policy default is enabled.
- **Image owner:** pin Playwright MCP/Chromium and SDK dependencies, bubblewrap/socat, non-root user, seccomp and image digest; build/scan only after a separate build allocation.
- **Control/Temporal and approval/artifact owners:** durable host/currentness and process-death reconciliation; canonical one-time browser approvals; idempotent browser-download ingest; no source/tenant-wall shortcut.
- **Deployment/security owner:** reviewed network/IAM/route changes, exact-host negative probes and destruction receipts. The present inert watchdog and closed-network qualification stack cannot be reported as a production host.

At this source checkpoint the production host, authenticated run-bound control channel, currentness lease, browser approval/artifact ports, direct-route denial and TLS coalescing proof are **not complete**. Browser activation stays held and Bash remains unavailable without real host attestation. No live action is requested by this document.

## Source hardening in this lane

The companion source diff keeps the held activation record and empty default destination list. It confines Playwright's configured egress proxy to a literal loopback endpoint on the isolated host; reports unknown cleanup when a browser grant acknowledgement or cancellation/deadline leaves host state uncertain, including a late preparation result; and closes proxy sockets/listeners on connect timeout or partial startup failure. The worker still has no production browser port or Bash sandbox attestation. Focused tests exercise these failures with synthetic ports and loopback sockets; they do not qualify the D005 host, real SDK execution, TLS coalescing or physical cleanup.
