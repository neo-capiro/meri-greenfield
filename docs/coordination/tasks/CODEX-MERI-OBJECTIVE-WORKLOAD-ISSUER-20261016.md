# Objective workload issuer proposal — 2026-10-16

**Status: source and deployment proposal only.** No Objective signing key, service credential, public-key trust configuration, replay ledger, issuance adapter, or live route is provisioned or enabled. Ordinary conversation startup must remain available when these Objective facilities are absent. This proposal does not approve deployment or replace the original user action, consent, membership, source, and phase checks.

## Ownership and exact mechanism

Use two separate, deployment-allocated AWS KMS asymmetric `SIGN_VERIFY` keys with `KeySpec=ECC_NIST_EDWARDS25519`. The trusted Meri CONTROL process owns the issuer for Meri-to-Core Objective requests. The Core Strategy process owns a different issuer and key for Core-to-Meri retained-result reads. No worker, browser, proxy, model, or Temporal client can call either issuer. The planned Temporal workload issuer and the existing retained-read Ed25519 assertion are separate audiences and keys.

Each issuer holds an immutable, durable issuance intent keyed by its named subject, operation, phase, generation job, method, literal route, empty-query requirement, SHA-256 of the **exact transmitted UTF-8 body bytes**, source digest, original delegation revision, current claim revision, and authorized attempt. It atomically claims the intent before signing, assigns one `jti`, then calls KMS `Sign` exactly once with `SigningAlgorithm=ED25519_SHA_512`, `MessageType=RAW`, and `Message` equal to the compact JWS signing input `base64url(protectedHeader).base64url(payload)` as ASCII bytes. Reject a signing input over 4096 bytes before the KMS call; do not prehash it or use `ED25519_PH_SHA_512`. Verify KMS returned the expected key ID and algorithm and locally verify the signature with the pinned public key before sealing an `ISSUED` row. Store the bearer only in protected issuer custody. An identical retry reads that same issued token while it remains current; a different intent conflicts. A claimed or uncertain signing outcome stays `UNKNOWN` until trusted reconciliation, with no fresh `jti` or second signing call. A later authorized attempt needs its own separately checked intent.

Proposed fixed identity pairs for the source fixture, subject to deployment/security allocation of actual KMS key IDs and public keys:

| Direction | `iss` | `sub` | `aud` |
| --- | --- | --- | --- |
| Meri CONTROL to Core | `urn:capiro:objective:meri-control-issuer:v1` | `capiro-objective-meri-control:v1` | `capiro:objective-strategy-generation:v1` |
| Core reader to Meri | `urn:capiro:objective:core-reader-issuer:v1` | `capiro-objective-core-result-reader:v1` | `capiro:objective-meri-retained-result:v1` |

The compact JWT protected header is closed to `{"alg":"EdDSA","typ":"JWT","kid":<configured-key-id>}`. The **Core-to-Meri reader JWT** has exactly these top-level members: `{iss,sub,aud,iat,nbf,exp,jti,objective}`. Its nested `objective` has exactly `{operation,phase,method,path,query,bodySha256,sourceSha256,generationJobId}`. This is the implemented but unmounted `apps/control/objective-generation/workload-reader-gate.mjs` source contract:

| Reader claim | Exact meaning |
| --- | --- |
| `iss`, `sub`, `aud` | Configured Core reader issuer, `capiro-objective-core-result-reader:v1`, and the single configured Meri private-reader audience. |
| `iat`, `nbf`, `exp`, `jti` | Integer seconds and a random UUIDv4 `jti`. The current reader gate rejects future `iat` or `nbf`, requires `exp > now`, `nbf >= iat`, and `1 <= exp - iat <= 60`. Issuance also caps expiry by original delegation, current claim, and operation deadline, rounding down to seconds. |
| `objective.operation`, `objective.phase`, `objective.method`, `objective.path`, `objective.query` | Exactly `objective.retained-result.read`, `retained-result-read`, `POST`, `/v1/internal/objective-generation/retained-result/read`, and the empty string. |
| `objective.bodySha256`, `objective.sourceSha256`, `objective.generationJobId` | SHA-256 of the exact received UTF-8 body bytes; canonical SHA-256 of the complete parsed `{generationJobId,binding,sourceAdmissionSha256}` source, which must equal the gate's fixed trusted source; and that source's persisted job ID. The individual source fields are **not** separate JWT claims. |

The **Meri-to-Core generation JWT** is a separate, **unimplemented proposal** for the disabled `core-http.mjs` credential port. Propose the same eight closed top-level members, with nested `objective` exactly `{operation,phase,method,path,query,bodySha256,sourceSha256,requestSha256,generationJobId}`. `operation` is `objective.strategy.draft`; initial allowed phases are `admit`, `admission-read`, `publish`, `request-read`, and `accept`, each paired with its fixed Core method/path. `query` is empty; GET has no body and binds SHA-256 of empty bytes. `sourceSha256` is the accepted Meri `{generationJobId,binding}` digest and `requestSha256` is the fixed Core `{schemaVersion:1,generationJobId}` identity digest already passed by `core-http.mjs`. A Core verifier must freeze this schema and phase matrix before use; this paragraph does not claim one exists.

Neither JWT carries raw Clerk bearer, provider credential, request body, protected facts, or standalone `tenantId`, `actorId`, `clerkSubject`, `delegationRef`, `delegationRevision`, `consentId`, `currentClaimRevision`, `sourceRequestSha256`, or `sourceAdmissionSha256` claims. The issuer uses those original server-owned facts in its durable issuance intent. Each receiver resolves and compares them from its own accepted request, consent, user membership, current claim, parsed source, and retained custody; the signed service identity alone grants none of that authority. Strategy obtains its own narrowly scoped token rather than forwarding Meri's Core-audience token.

The Meri issuer must derive its request from the durable accepted request/run-to-generation-job mapping and genuinely issued protected Objective facts, and recheck the original native Clerk delegation plus current Core membership/claim before signing. Core's verifier independently loads its original consent/delegation and current tenant, actor, membership, client/objective, job, phase, and claim under its authority boundary. The Core reader issuer derives the retained source from persisted acceptance and its own current claim; Meri independently compares that source to its accepted run and retained custody before releasing a result. A service identity never makes an arbitrary source readable.

## Receiver verification and replay

Each receiver has an operator-provisioned, fixed `(iss, sub, aud, kid) -> OKP/Ed25519 public JWK` allowlist tied to the corresponding KMS key. Parse bounded canonical base64url segments, require the exact protected header and closed claim shapes, verify the raw JWS signing input with Ed25519, reject unknown `kid`, wrong issuer/subject/audience, algorithm confusion, missing/overlong clocks, token-provided key URLs, and any extra claims. No `jku`, `x5u`, caller URL, or untrusted JWKS fetch is allowed. Rotation explicitly stages an old/new trusted public-key mapping for only the bounded token lifetime plus skew; unknown or stale keys fail closed. Missing mapping disables only the relevant Objective operation.

After cryptographic and wire binding checks, the receiver uses an atomic durable `runOnce` record keyed by `(iss,sub,jti)` and comparing SHA-256 of the **exact signed token bytes** plus the full operation/phase/method/path/query/body/source/job digest. An altered valid token with the same `jti` conflicts. For a write, the replay record and domain transition commit in one database transaction. A byte-identical replay checks current authority and returns the prior immutable result/reference without repeating a transition or minting authority; a changed replay denies. Pending/uncertain outcomes remain unavailable until reconciled. Reads use the same replay decision and an immutable result/reference; a revoked or changed current claim denies even a matching replay. Retain records beyond the token's expiry and bounded retry window. An effectful later write uses a newly scoped token and rechecks current job and claim. Migration IDs, tenancy, encryption/retention, and transaction ownership need central allocation before implementation.

## Existing source seams and missing allocations

- Meri's fixed Core caller is `apps/control/objective-generation/core-http.mjs`. It already fixes methods/routes, empty GET bodies, exact wire-body SHA, deadlines, and a disabled `authorization.readCredential` port. The callback is **not** an issuer or proof. Its returned echoes must be backed by the proposed signed and durable credential owner.
- Core's `apps/api-strategy/src/planner/objective-canonical-authority.ts` still fails closed in `verifyGeneration`, `verifyGenerationAcceptance`, and current-claim methods. `apps/api-strategy/src/meri/objective-canonical-retained-http-bridge.ts` fixes the Core reader method/path/body/source and named subject but has only an injected credential owner and no composition.
- Meri's `apps/runtime/objective-generation/core-result-owner.mjs` validates the exact retained source but has no authenticated HTTP ingress. `apps/control/objective-generation/workload-reader-gate.mjs` verifies the closed reader JWT against fixed trusted keys and a fixed source selected at enabled construction, yet remains unmounted without a genuine accepted-run/current authority and durable `runOnce`. The ingress must first resolve the accepted run from trusted custody and select its matching fixed-source gate and retained-result owner; caller body or token may not select a generic owner. The agreed unmounted route is `POST /v1/internal/objective-generation/retained-result/read` with `{schemaVersion:1,source:{generationJobId,binding,sourceAdmissionSha256}}`.
- `apps/runtime/native-authority/retained-reads/credential-broker.mjs` contains a pinned OKP/Ed25519 JWK and Node `crypto.verify(null, ...)` pattern. Its custom retained-read envelope is **not** a JWT or Objective grant. `apps/runtime/prepared-run-issuer.mjs` and `prepared-run-issuance-postgres.mjs` demonstrate durable `CLAIMED`/`ISSUED`/`UNKNOWN` custody; their model/task capability rows cannot be reused as Objective token authority.
- Backend `apps/api/src/auth/clerk.service.ts` verifies native Clerk sessions; it is change-controlled and is not a workload issuer. Backend `apps/api/src/auth/internal-service.guard.ts` uses a static shared secret, and `apps/defense-api/src/internal-auth/internal-auth-core.ts` uses HMAC. Neither meets this asymmetric JWT contract. Backend `apps/api/src/auth/workload-authority/workload-authority.policy.ts` is pure eligibility, not an authenticated issuer/verifier.
- Deployment/security must allocate two KMS keys and signer IAM identities, each receiver's pinned public-key manifest and rotation process, separate issuer-qualified subjects/audiences, private TLS ingress, the Meri durable accepted run-to-job binding, the original delegation/current-claim source, both issuer custody stores, both receiver replay stores and migrations, and owner-specific typed response decoders. No such allocation is inferred from synthetic fixture keys or the planned Temporal workload issuer.

Source reference: [AWS KMS `Sign` API](https://docs.aws.amazon.com/kms/latest/APIReference/API_Sign.html) specifies asymmetric signing keys, the 4096-byte message limit, `ED25519_SHA_512`, and `MessageType=RAW` for `ECC_NIST_EDWARDS25519`.
