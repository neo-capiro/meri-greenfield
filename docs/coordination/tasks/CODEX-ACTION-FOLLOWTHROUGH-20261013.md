## Product outcome and implementation outline

A user can select a retained action recommendation, inspect an editable task draft and prepare an explicit immutable task proposal through the existing command approval interface. Viewing a recommendation does not create a task. Current-authorized retained-result reads own evidence access; existing task contracts own fields and command normalization; existing approval metadata and executor owners retain approval and mutation authority. No new approval policy, task acceptance claim, model loop or UI implementation is introduced. Unsupported/ambiguous selections, mismatched result hashes/client identities, revoked reads and caller-supplied authority fail closed. Task edits are explicit, and the source recommendation is evidence rather than an instruction.

The execution harness fills the existing evaluator's missing observation producer. It consumes the gold-free `runnerCases` projection, executes an approved typed lookup/read through actual control services, and captures actual current-read authority callbacks and failures. It produces the exact existing scorer input. It does not infer an SDK route from a prompt, expose gold to a runner, invent real requests or count typed execution as agent quality. Unsupported execution modes stay explicit. Approved real corpus, runtime/model measurements and independent adjudication remain external inputs, without blocking local implementation and synthetic behavioral checks.
