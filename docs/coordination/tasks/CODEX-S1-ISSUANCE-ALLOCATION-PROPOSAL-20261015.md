S1 implementation constraints after reservation:

- Persist the existing intent tuple: unique canonical issuance key and full original RunBinding, request hash and original expiry, with a durable claim fence/CAS version. A durable claim must precede the capability-authority call. Claim replay must compare the complete immutable tuple and return the existing state; exactly one committed claimant can receive `fresh:true`.
- Model CLAIMED and ISSUED as the existing store port requires. A claimed key cannot become ABSENT on restart, timeout, ACK loss, cleanup or reconciliation. Unknown authority results never trigger replacement generation; preserve a durable unresolved/tombstone state until a separately reviewed policy permits retirement.
- Complete once with existing grant ID, capability digest and opaque material reference; conflicting completion, including a changed material reference, must refuse. Bind facts by immutable compare-and-set. Missing-row insertion and subsequent updates need a concurrency-safe database protocol, not only `SELECT ... FOR UPDATE` on an absent row.
- Store no raw capability, proxy/admin/provider credential or secret-store value. A material reference names existing protected material and conveys no authority by itself. Retrieval, revocation and reconciliation remain the capability-material authority's responsibility; schema allocation does not approve that owner or its reference model.
- Reuse the existing issuer/store interfaces and borrowed-pool/lifetime conventions. Put the product PostgreSQL adapter in a focused persistence module, proposed `apps/runtime/prepared-run-issuance-postgres.mjs`; keep `prepared-run-issuance-store.mjs` as port plus explicitly disposable fixture adapter. Do not introduce a second budget ledger or repurpose next-run mappings.
