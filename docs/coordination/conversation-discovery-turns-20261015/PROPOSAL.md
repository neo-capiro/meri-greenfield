### Concrete source gaps

`createNextRunOwner.selectRun` may reserve a successor while selecting a completed conversation; it cannot back a read-only list/open/reconnect. `currentRun` admits only the latest or its pending reserved target, so it cannot silently authorize historical reads. The application context adapter has a trusted selector port, but the reviewed `application-adapters/mount.mjs` does not wire it. A port's existence is not a working product path.

The current public submit is selected by its session and accepts only requestId/prompt plus optional skill/window; it must not acquire caller-selected conversation/run/new-turn fields. History is run-local. The private next-run journal stores conversation sequence bases and an immutable source/target mapping; it supplies neither an authorized discovery API nor a public conversation-wide history receiver. Existing session wire has no read/write-purpose discriminator. These are explicit future extensions, not claimed existing behavior.

## Minimal logical surface and publication boundary

Proposed logical client methods are `discoverConversations`, `openConversation`, `prepareConversationTurn` and `lookupConversationTurn`. Put their eventual reviewed definitions/receivers in the existing shared contracts package and extend the existing client/proxy, rather than publishing a parallel SDK. Route paths, exported symbol spelling and package version stay **unallocated**. [PROPOSED-CONTRACT.json](PROPOSED-CONTRACT.json) records candidate fields and closed alternatives; it is a design document, not an accepted JSON Schema or executable receiver.

All calls authenticate with current native identity through the existing application bridge, including after an old opaque session expires. Browser clientId/conversationId/runId, cursor, source hash and commandId are selectors/correlation only. Actor and tenant come exclusively from verified native identity. No actor headers, saved browser bearer, superuser shortcut or listing entry grants access. Recheck current identity/client-wall/policy/retention before each read, before/after effects and immediately before release. Bound every operation by injected server observation time and the narrowest current receipt deadline; reject future observations and expired receipts.

### Discovery: metadata only, bounded complete traversal

Request: `{discoveryId, clientId, cursor, limit}`; UUID discoveryId correlates this invocation, clientId is a hint, cursor is null or opaque bounded text, limit is 1..50. The client must retain the exact first-page query context and continuation, not splice pages across accounts/client generations. The server supplies the authenticated scope correlation and ignores any UI claim of tenant/actor authority.

Success is `kind: page`, including zero items. It contains only `{conversationId, createdAt, latestVisibleRun:{runId,state}}` per currently authorized, same-owner conversation. Omit prompt/title/snippet, task/worker/provider identifiers, other actors and artifact/source metadata. Never replace a denied conversation with a named redacted row or expose a hidden total. All retained scopes of a row must be authorized under current policy, not merely its selected client. Missing/corrupt metadata is dependency failure, not fabricated empty.

Stable order is **immutable conversation creation time descending, then UUID descending**, explicitly “recently created”, not most recently active. Use a bounded keyset traversal pinned to the first page's upper creation bound; no offsets. Concurrent newer conversations appear on a fresh traversal. Cursor context binds authenticated tenant/actor, selected client, identity/policy revision, query/version/limit, upper bound, last *scanned* key and expiry. A future cursor codec must live in this control read boundary and use an approved existing integrity mechanism; none is instantiated or qualified here. If no approved cursor integrity owner exists, paged discovery stays unavailable; no new key or credential may be invented.

Reauthorize every page and selected row. A changed policy/identity revision invalidates the traversal with `cursor-stale` and an explicit restart; do not return an old authorized snapshot. A valid cursor proves no authorization. A repeated request for the same input cursor may return the same page without mutation; frontend must not append that page twice or accept a cycle/nonprogressing next cursor. A new page's cursor advances by the scanned key even when all scanned rows were filtered. `coverage: more` has a non-null next cursor; `coverage: complete` has null. A bounded scan can legitimately yield zero visible items with `more`; it is not the complete-empty UI state. No runtime promise of a stable count across revocations is made.

Do not emit a partial page on owner/database/authorization uncertainty: return `unavailable`, preserving the input cursor for explicit retry. `complete` means this traversal's retained eligible namespace was exhausted under current authorization, not all former conversations still exist or all withheld objects are absent. A fresh successful page with zero items and complete coverage alone supports “No visible conversations.” Denied scope, unavailable dependency, cursor error and loading remain distinct UI states.

### Open/reconnect: observation cannot create a turn

`openConversation` takes exact conversation/run selectors and `access: observe | admitted-target`. It may only read/issue a fresh bounded session for that exact pair or fail. It never calls a mutating selector, reserves a next run, creates a conversation, accepts a prompt, dispatches a task, resumes or cancels work. A separate client-only compatibility bootstrap returns `selection-required`; it does not choose, create or reserve a pair. This compatibility result requires its own receiver review and is not an alternative to exact open's required selectors. The existing frontend's exact supplied-hint equality remains mandatory.

`observe` sessions expose admitted `allowedOperations: [history,events,reconnect]` only. Historical terminal reads require an explicit retained-read purpose in the existing session/context and conversation read owners, with current visibility/suppression and a retained-data ceiling. They do not pass through current writer eligibility, extend the old worker expiry or grant cancel/submit. If that purpose is unavailable, return `unavailable`; do not pretend historical reads already work. Sessions for active observation are also read-only unless a distinct exact write admission is supplied. Server services enforce allowed operations, not just the UI.

`admitted-target` additionally requires the immutable turn admission reference. The owner verifies the same target and command association. If its first prompt is durably unsubmitted, the same still-valid target may receive its first input through existing submit. If a prompt exists, or its delivery is unknown, grant only exact original submit reconciliation, requiring the browser's original submit requestId and bytes; never a new input. If those original bytes are unavailable, stay read-only/blocked. An accepted or unknown submit keeps its retained bytes and identity. No browser cache entry or cache absence proves committed/not-committed; no generic 404 authorizes a new command. Retained command recovery across browser restart is a server lookup dependency; current QueryClient memory is navigation-only.

Response wraps a fresh existing-issuer session receipt with a proposed admission projection: exact tenant/actor/client/conversation/run, access, allowedOperations, checkedAt/expiresAt, immutable admission reference or null, and a history anchor. These proposed wrapper fields require receiver/issuer review; they are not added to the closed existing session receipt by this document. Receipt/session context must match exactly; mismatches refuse. Do not put credentials in list items, journal metadata, URLs, logs or proposal fixtures.

Exact open also produces a closed **continuation readiness** projection. `ready` supplies the authorized source selectors, complete binding hash and published completion proof hash needed for explicit next-turn input; they must equal the opened pair/binding. `not-ready` reports unsubmitted/active/capture/retirement/revocation pending without a fake proof; `unsupported` reports historical/noncurrent, unsupported terminal state or unavailable history. This is a required new read projection in the existing owner, not data currently exposed by public0.1.3 history or `run.status: completed`. Readiness only reads existing proofs: it must never capture a checkpoint, physically stop/retire a task, revoke grants, close a sequence range or reserve a successor. Explicit prepare freshly rechecks every source fact; readiness confers no continuation or write authority.

### Explicit creation versus continuation

`prepareConversationTurn` accepts `{commandId, clientId, intent}` where intent is the closed tagged alternative `new-conversation` or `next-turn`. It contains **no prompt, model input, credential or browser-selected target IDs**. `new-conversation` requests a new canonical conversation and first run from the existing trusted admission/allocation owners. `next-turn` carries the exact source `{conversationId, runId, bindingSha256, completionReceiptSha256}`. The server loads and compares full source identity, including original attempt/worker/fence, request/context/checkpoint/versions, current scopes and immutable completion proof; hashes are correlation, never authorization. A pending source→target reservation is recovered unchanged.

The command's canonical bytes/hash and immutable association to source and target must be durable *before* returning an admitted result. Target IDs are generated by the existing trusted allocation/next-run owner once, never the browser/model. Bind commandId/hash and admitted target before any prompt/dispatch. The existing next_runs natural key is one immutable mapping per completed source; it is the canonical continuation identity, not a second command scheduler. Two different commands racing for one source must return the same already-bound command mapping only when exact input identity agrees, otherwise conflict, never allocate another target.

**Known blocking gap:** f0 next_runs has source/target reservation but no public commandId/input-hash association; initial session issuance is process-local and has no general durable new-conversation command mapping. Do not assert either ACK guarantee exists. Fable must first propose how existing admission/issuance/journal ownership can durably hold these narrow associations; any necessary schema change requires separate central allocation. This proposal creates no table, does not repurpose Strategy0012 and does not infer0011's unfrozen schema can store these commands.

| Authoritative source state | Explicit next-turn result |
| --- | --- |
| queued/running/waiting-for-approval/paused or any nonterminal | `blocked: source-active`; keep observing/reconciling; no new run |
| completed, missing/unknown completion capture, retirement or revocation | `blocked: source-not-ready` or `unknown` for an ambiguous command; no reservation/dispatch |
| completed, exact published checkpoint + physically retired task + all issued grants revoked, current authority valid | Reserve/replay the single successor through existing next-run owner, then fresh target admission |
| failed/cancelled | `blocked: unsupported-source-state`; new-conversation remains a separate explicit option. No claim that lifecycle resume/fork or failed-run continuation is implemented here |
| source is no longer latest or hash/binding differs | `conflict: source-changed`; never follow “latest” to another run |
| same command already admitted/reserved/accepted | First recover its exact immutable mapping under fresh current authority, even when its source is no longer latest; independently compute present eligibility. Never mint another attempt, worker, fence or grant |

A new conversation may be explicitly prepared while another run is active. It does not cancel/detach ownership of that work, and the browser must retain its old scoped uncertainty. Disable new intent locally while an unknown command in that same interaction is unresolved; other-scope work remains scoped and undispatched by UI guessing.

An explicitly admitted genuinely new target may obtain its own per-run issuance only through the existing durable issuer and approved target admission. Its original target deadline is then immutable. Reads, lookup and a reservation alone issue no grants; recovery never renews an old worker or replaces an unknown issuance. This proposal implements none of the native/0011 issuance path.

An immutable receipt records the historical target reservation/admission outcome; it is never current write readiness. A **`prepared`** response additionally contains a newly admitted bounded session and current operation projection permitting either the first submit on a durably unsubmitted current target or only the same already-retained input. It does not mean the new prompt is persisted, a worker is ready or model execution started. A replay without present write eligibility returns **`recorded`** with no credential. The immutable receipt includes commandId/hash, source pin or null, exact server target binding projection, admission reference/hash and original target deadline; ephemeral sessions and current eligibility are excluded from its hash. Target preparation and prompt submission are two separate receipts/uncertainties.

Precedence is exact retained command identity first, then current eligibility; only a genuinely new command tests source-latest to create a reservation. A changed same-id hash is always conflict. Recovery of an old receipt never redirects to a newer target. When a retained target is stale/terminal/expired, replay can only return recorded/observe-only/receipt-only as permitted by current policy, never prepared.

### Lost ACKs and expiry

`lookupConversationTurn` takes the exact commandId/hash and the same intent/source selectors under fresh native authority. It is read-only: no reserve, dispatch, new session-allocation side effect or task creation. It returns **`recorded`** with the immutable command/target receipt and **no session credential**, `pending`, `unknown`, or `not-committed` with an authoritative durable lookup witness. Recorded includes fresh present eligibility `reopen-target`, `observe-only` or `receipt-only`, never `write-ready`. Reopen-target permits an explicit exact-target open and a new authority check; it is not itself a write grant. An unsubmitted valid target can obtain first-submit authority; an existing/unknown submit can obtain same-input authority only with its retained original identity/bytes. This separates receipt recovery from fresh session issuance.

Timeout/disconnect/unknown commit/lookup unavailability stays `unknown` with the same command. Only trusted durable `not-committed` proof may permit explicit retry of the same original command. Same-id changed bytes/source/client refuses. Never clear a journal, use a replacement UUID, infer absence from cache/404, or call the model to resolve uncertainty. Lookup and prepare share one immutable receipt. A later accepted target prompt is read back by its separate original submit requestId; do not resend an old source prompt or count a reservation ACK as submit ACK.

Fresh read/opaque session expiry is bounded by current identity/policy/retention and its stated purpose. Original task/grant expiry never stretches. Preparation after the target's original dispatch deadline can recover recorded/observe-only or receipt-only if currently allowed; it cannot return prepared or remint. A successful command lookup does not imply retained bytes, current output read access or runtime admission. Current revocation/suppression that forbids the control receipt returns uniform denied with no receipt/source/target metadata; payload-only purge may yield receipt-only when the retention owner explicitly permits that retained control receipt. Current cancellation forbids a write session. None authorizes replacement execution.

### History and frontend lifetime

Retain existing run-local event sequence numbers and public cursor grammar. The proposed history anchor identifies the selected run, source run or null and its coverage. It is a closed tagged alternative: `unsubmitted` requires **sequenceBase:null**, because a reserved target has no durable sequence range before first submit; `retained` requires its actual durable base; `history-unavailable` has null unless the exact recorded base was separately authorized/read. Opening an unused target must not seal the predecessor range, fabricate base0 or infer one from current source events. Only existing prompt acceptance closes the source range and records the real target base.

Do not replace the run-local cursor with a conversation-wide integer. A conversation transcript is assembled only after authorized pages for each exact run, with closed prior ranges checked by existing sequence-range owner. Source gaps/purged or withheld segments are explicit `history-unavailable` coverage; never invent contiguous empty history or expose a hidden run selector. Previous/next retained run navigation is a further authorized read projection requiring owner receiver review; this minimal anchor does not silently provide it. Conversation-wide history projection itself still needs owner receiver/allocation review; this proposal does not claim current history supplies it.

Frontend must instantiate a fresh port/session lifetime on exact admitted replacement and unmount/remount view/action state using the canonical lifetime key. Stop the old observation without implicitly cancelling the durable run. Keep source and target submit journals, continuation command uncertainty and drafts in their original exact scopes. Do not mutate an existing SDK port's run, relax session hint equality, transfer the old prompt, or infer write permission from terminal state. Read-only sessions render an observing/history view with Send/Cancel unavailable. Current host's captured hints and one-run journal/port cannot be silently reused for this extension. Frontend separately owns a bounded reconnect-hint correction; no new source pin or qualification is claimed for its work in progress.

## Closed status grammar and acceptance

The design JSON enumerates page/selection-required/opened/prepared/recorded/pending/unknown/blocked/conflict/not-committed and error alternatives with forbidden cross-fields. Errors are `invalid-input`, `denied`, `cursor-invalid`, `cursor-stale`, `unavailable`, `deadline`. Distinguish denied native scope from dependency failure; exact conversation/run inaccessible or nonexistent uses the same `denied` response without an existence oracle. No arbitrary provider/backend error text is public. A mutation timeout is `unknown`, not a definitive failure/no-effect assertion. Recheck authority before returning any retained receipt, hash, source or target metadata.
