# Retrieval contract foundation 0.2.0

Status: additive R2 foundation, pending independent review. The [common](../packages/contracts/retrieval-0.2/common.schema.json) and [retrieval](../packages/contracts/retrieval-0.2/retrieval.schema.json) schemas establish request-context and response shapes. [validate.mjs](../packages/contracts/retrieval-0.2/validate.mjs) checks declared cross-field consistency. These checks do not authenticate, authorize, connect sources, implement retrieval or qualify a domain operation. REL-02 and REL-03 remain open.

The gateway binds Clerk identity, current authoritative user/membership and actual grants before resolving a requested subject. Model/UI requests contain requested client/entity identity, all-authorized active portfolio selection or personal scope; they cannot supply tenant/actor/grants. Ambiguous names, pronouns, denied IDs and unresolved entities require a trusted resolver and clarification rather than guessed identity. No resolver is implemented here. A server-resolved subject records canonical IDs, current tenant/actor, decision/policy revision, contributing scopes and a roster version for portfolios. A Meri portfolio is an authorized client roster; a Defense Research Portfolio or prospect is a distinct entity and does not gain new authority from its type name.

Every read, discovery/load/use, citation/read handle, replay/resume, publication and destination needs current authorization. Mailbox ownership, client walls, approved-memory lifecycle and private-user grants remain independent of tenant membership. Derived content inherits all contributing scopes; public evidence does not erase private lineage. Reusing the 0.1 Scope shape is not a new grant model. Protected resource/provider access stays disabled until source contracts and G2/G3 fixtures pass. [Source inventory](SOURCE-INVENTORY.md) and [integration boundary](INTEGRATION-BOUNDARY.md) retain the 22-domain discovery and missing-surface distinctions; availability is not assumed.

| Method | Contract meaning | Prohibited inference |
| --- | --- | --- |
| `candidate-search` | Bounded lexical/semantic/hybrid discovery results with record versions, snippets and required read handles | Top-k or an empty candidate page cannot establish total counts or absence |
| `exact` | A separately registered typed authoritative count/status/history/comparison operation | No arbitrary SQL, unrestricted tables or synthesis from candidate counts |
| `source-read` | Authorized full material source content with stable record/version/citation lineage | A snippet or opaque unread handle is not a completed decisive read |

The outer evidence envelope is closed and carries request/trace IDs, exact operation/version, server binding/subject, normalized window, validated argument digest and applied-filter digests. Those digests are audit metadata; they are not a generic filter execution language. Every source supplies authority (`authoritative`, `derived`, `approved-memory`), adapter/snapshot identity, checked/partial/unavailable/denied status, synchronization/as-of/retrieval timestamps and explicit fresh/stale/unknown state. Records carry immutable source/record versions, content hash, opaque citation ID, scopes and explicitly snippet/full-read/structured content. Citation and continuation strings are opaque identifiers, never preauthorized URLs or bearer credentials. Every returned record array enumerates distinct immutable `(sourceId, recordId, recordVersionId)` tuples, encoded without delimiter ambiguity. Citation IDs, content hashes, content and scopes do not create a new counted identity; multiple events sharing a version need a separately versioned event contract with an explicit counted unit. A record must correspond to a source state declared `checked` or `partial` and included in `sourcesChecked`; `denied` and `unavailable` sources cannot contribute returned records. Mixed-source partial responses may still return records from other eligible sources, with the denied/unavailable sources disclosed in coverage. These are consistency declarations, not authorization decisions.

Outcomes are `complete`, `partial`, `empty`, `unavailable`, `denied` or `error`, with stable reason and retryability. Failure outcomes carry no result/aggregate count or negative assertion. The local validator checks outcome/reason/retry consistency, source-set accounting, impossible timestamps, record lineage and returned counts. `returnedCount` counts returned result records; a scalar aggregate is one returned result, while `data.value` and `enumerableTotal` carry its exact count. Candidate results keep `enumerableTotal:null`; unknown counts remain null. Partial output and unavailable sources are explicit, never zero by default.

Coverage includes sources requested/checked/unavailable, enumeration completeness, known enumerable total, actual returned count, truncation, history support and limitations. Continuation includes an opaque cursor, required decisive reads and remaining sources. Complete enumeration cannot coexist with truncation, a next cursor, unavailable/partial sources, remaining sources or bounded/unsupported history. A complete response additionally requires fresh sources and no unresolved decisive reads. Empty is a result shape, not automatically a claim of exhaustive absence.

An explicit absence assertion is allowed only for an empty typed exact count/history result with a known zero enumerable total, complete relevant enumeration, all requested authoritative sources checked and fresh, no truncation/cursor/remaining sources or decisive reads, and an exact relevant-source set. Exact results require authoritative sources; complete history must bind its enumerable total to all returned history records. The gateway must verify those declarations against the source receipts/query/paging protocol; JSON declarations cannot prove real coverage. Tenant denial never becomes a factual negative. Source outages, stale data, capped searches and unsupported history require qualified partial/unavailable language. Cursor/read handles must bind actor, current revision, scopes, source snapshot, normalized query/window and continuation, and be reauthorized at use; no cursor implementation is provided.

Window requests distinguish calendar week/month/year, fixed relative duration, explicit interval, fiscal year and unbounded history. Bounded normalized results use UTC inclusive start/exclusive end plus the requested timezone. Calendar weeks explicitly select Monday/Sunday policy; the checker verifies local midnight and a seven-local-day span, including DST. Month/year boundaries and increasing bounds are checked. Relative `days` means exact 24-hour durations ending at the explicit anchor, distinct from a calendar week. Fiscal selection preserves calendar ID, year, funding stage and revision. Comparisons require an explicitly compatible revision/stage/unit basis; broader cross-version/domain semantics need their own typed operation.

`assertWindowResolution` rejects basis/timezone/explicit-bound/duration/week-policy/FY-stage-revision substitution. It does not select the correct `this`/`last` interval from a trusted current clock, implement fiscal calendars, resolve ambiguous text or qualify a source's revision semantics. Those deterministic resolver/domain fixtures remain REL-03 work. No silent 30-day default exists in this namespace. A previously supported 0.1 request/result is not silently widened or relabeled 0.2; adapters and in-flight compatibility require separate owner review.

The current fixtures establish closed structure and consistency only. Genuine source truth, policy walls/revocation, pagination/exact aggregates, decisive passage reads, full history, SDK/proxy discovery, traces and the real 75/200-case benchmark remain open. No real request is fabricated to fill that benchmark; optional Decisions/JEV remain disabled.

## First pending mail slice

The internal [mail schema](../packages/contracts/retrieval-0.2/mail.schema.json) and concrete [catalog](../packages/contracts/retrieval-0.2/catalog.json) add only `mail.read_thread@0.2.0`, with compatibility alias metadata `get_email_thread`. Its handler is null, availability unimplemented and qualification pending. Existing skill validation refuses it. The catalog retains all 139 original IDs, 96 selected and 43 deferred, with exact accepted boundaries; only this original has a typed replacement mapping. The other 95 selected operations remain pending/unmapped. This is not a freeze of the full selected catalog or a public 0.2 export.

`assertMailThreadInput` validates a closed external DTO and returns a new defaults-materialized object. `subject` reuses personal or explicit-client SubjectRequest; it cannot inject actor/tenant/mailbox authority. Required threadId and optional nullable messageId are UUIDs. Numeric fields are strict integers, with absent defaults below; strings, booleans and numeric null are rejected rather than reproducing legacy Number coercion. Accessors, nonfinite values and non-JSON objects are rejected before schema evaluation. Materialize defaults before computing the argument digest.

| Argument | Default | Inclusive range / meaning |
| --- | --- | --- |
| messageOffset | 0 | 0–10000, messages in the filtered collection |
| bodyOffset | 0 | 0–10000000, UTF-16 code units in each selected stored body |
| limit | 3 | 1–10; an exact messageId does not change the default |
| maxCharacters | 2000 | 1–6000, UTF-16 code units |

Positive bodyOffset requires exact messageId. Service order is sentAt ascending, then receivedAt ascending, then createdAt ascending, with **unspecified null ordering and tied-date order**. No effective-date/ID ordering or immutable snapshot is invented. UTF-16 offsets can split surrogate pairs; they are not Unicode-scalar or UTF-8-byte offsets. A requested offset beyond stored text returns an empty section whose actual start/end clamp to the known body length, while selection retains the requested offset. This is an explicit transport representation of the observed empty result. Declared next offsets can exceed the legacy request ceilings; adapters must disclose unsupported continuation rather than silently raise those ceilings.

`MailThreadSourcePage` is a separate incomplete transport DTO. It is never EvidenceEnvelope: evidenceReady is always false, negativeAssertion is always none and enumeration cannot be complete. `assertMailThreadSourcePage(page, input)` binds its selection and argument digest to the normalized request, reuses canonical resolved-subject/window/source accounting and checks message/mailbox/thread/scopes, authoritative source declarations, UTF-16 ranges, counts and continuation. Every returned message requires an unresolved opaque decisive-read handle, including a last or apparently full stored section. Unknown immutable record/snapshot identities remain null and require unknown enumeration; version1 legacy proof metadata is not an immutable version.

Mailbox connection status is reported as stored metadata, with no connected-only filter. Current trusted mailbox ownership/client authorization and nonremoved state still must be established by the future adapter at every read/use; JSON declarations do not authenticate those facts. A denied/unavailable source contributes no message; mixed-source partial output can retain eligible data with the other source disclosed. Thread messages cannot switch mailbox identity, and each message must carry its matching mailbox scope within the resolved subject lineage.

Body completeness is explicit full/preview/truncated/missing/unknown. Missing text is distinct from empty text; unknown size cannot claim no more body. Completing stored preview/truncated/unknown sections never upgrades upstream completeness. Hashes/citations may remain null and do not establish source truth. Known message totals count the optional messageId-filtered collection, not necessarily the whole thread; unknown totals stay null. Message and body continuation inventories are separate. This slice provides no cursor service, immutable snapshot store, assembly/conversion API, HTML normalizer, handler or policy decision. Only a later authorized adapter with actual complete same-version material and positively established source completeness may emit the unchanged full-read EvidenceEnvelope. Empty stored pages never prove that an email or commitment did not exist.

The catalog descriptor's input/output references identify exact definitions and SHA256 of raw mail-schema file bytes; `assertCatalog` rejects reference/hash drift. New schema versions need separate review. All original source-access, REL-02/REL-03, benchmarks and release/security gates remain open. [The implementation report](coordination/reports/CODEX-G1-REL02-MAIL-FIRST-CONTRACT.md) records local checks and preserved failures; the legacy evidence is behavioral metadata, not permission to port old handlers.
