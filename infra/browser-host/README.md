# D005 browser host source definitions

## Implementation outline

- `binding.mjs` validates exact, owner-supplied DATA for one tenant/conversation host generation and immutable source/image/network pins. It grants no authority.
- `network.mjs` describes the required separate proxy and browser/Bash network compartments, proxy-only tool traffic, public address denial and host firewall controls. Security groups are one layer, never the enforcement proof.
- `instance.mjs` describes non-root host/container, image and metadata constraints. `watchdog.mjs` records the existing managed-teardown source gap and the independent cleanup evidence required.
- `render.mjs` combines those DATA definitions into a **non-deployable** proposal with `runtimeEnabled:false`. It emits no CloudFormation resources, executable command or admission switch. The deployment owner must later review and implement an exact change set, obtain separate authorization, and qualify it on the real host.
- `template.mjs` compiles a reviewable CloudFormation **source specimen** with pinned AMI, private subnet, no public address or ingress, only the pinned private control security group on port 443, IMDSv2, encrypted delete-on-termination root, and an exact ECR repository pull role. Every resource is behind an unconditional literal-false condition. It has no parameter to enable launch, no host bootstrap, public web route, managed watchdog or deployment command. It cannot produce a live host as written; removing the guard requires a separately reviewed source and deployment change. The inert watchdog and missing positive root-volume-absence wire still block admission.
- Focused tests verify closed binding, exact run isolation, fixed topology and permanent refusal of deployment/activation claims. No AWS client, CDK, network, filesystem or process operation is imported or performed by these modules.

This proposal reuses `apps/worker/conversation/browser/{resolution,egress-control}.mjs`, `apps/worker/conversation/egress/proxy-server.mjs`, SDK sandbox readiness, and `infra/browser-{qualification,enforcement}` as source references. Their local fixtures do not qualify production. See `docs/coordination/handoffs/M8-BROWSER-BASH-SOURCE-DEPLOYMENT-20261018.md` for the owner handoff and activation sequence.

## Enabled closed-network source path (third checkpoint)

- `enabled-binding.mjs` validates one exact owner-supplied allocation, private network/endpoints, immutable AMI/image and literal user-data bytes, two distinct native helper SHA-256 pins, KMS keys, a pinned independent watchdog execution/provider, and a separate CloudFormation service role. It accepts only a 900-second lease, one `t3.large`, one 30 GiB root volume, a canonical user-data payload at most 16 KiB, and explicit `closed-qualification` mode. Inputs are configuration, never self-authenticating proof.
- `enabled-template.mjs` emits actual CloudFormation resources without a false condition: one private EC2 instance, one SG with inline egress to pinned private endpoints/S3 gateway, an exact ECR/log writer role, a seven-day encrypted log group, and a watchdog preflight Custom Resource. The instance has a hard `DependsOn` edge to the preflight. The template adds no Internet/NAT route or public-web rule. The reviewed template digest covers the deterministic template with its two self-referential digest fields normalized to zero. The EC2 role trusts only the `ec2.amazonaws.com` service principal and checks `aws:SourceAccount` if that key is present. AWS's [EC2 role trust example](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-service.html) uses that service principal without a SourceAccount requirement; [global-key availability](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html#condition-keys-sourceaccount) is integration-dependent, and [IfExists](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition_operators.html#Conditions_IfExists) permits the documented trust path when EC2 omits it. The deployment issuer must restrict `iam:PassRole` to this exact role/profile and qualify actual credential issuance.
- `launch-deadline-policy.mjs` emits the required **out-of-stack** inline Deny for the exact CloudFormation service role: EC2 launch/start actions at or after original C=t0+900s. `stack-update-policy.mjs` emits a one-use stack policy denying updates to stack resources. The stack must be created with both, the role policy installed beforehand, and IAM must prevent later role-policy removal or stack-policy override. The deployment issuer must also forbid adding resources to this stack: a stack policy protects resource updates but is not an authorization boundary for arbitrary new resources. These policies are separate from the guest's image/log role. The Deny blocks late API requests; it cannot prove that an earlier in-flight request finished provisioning before C.
- `watchdog-preflight-provider.mjs` defines a source handler with injected **read-only** Step Functions, CloudFormation, Lambda, IAM, EC2 and network inventory ports and an injected CloudFormation response sender. It permits a `Create` success only after reading back the actual stack template/digest, stack service role and exact inline deadline Deny, exact stack update policy, pinned active Standard state-machine version/definition, trusted independent qualification record, exact running execution input and original 900-second deadline, AMI/one-root mapping, and closed subnet/endpoints. Route readback accepts only active RFC1918 VPC-local routes and the exact S3 gateway route; any specific public IPv4, IPv6 or alternate target is refused. It rereads the execution and clock after the inventory calls. Update fails; Delete removes only the preflight resource. A failed/unknown read yields `FAILED`, so EC2 cannot be created through the dependency. A supplied service-token ARN or execution ARN alone is insufficient.
- This is an **enabled CloudFormation source definition**, not an approved launch packet. The provider's published Lambda version, IAM, read adapters, trusted watchdog qualification store and presigned-response transport are deployment-owner obligations. The read-only provider adapter must use `GetTemplate` Original, `DescribeStacks` with the exact stack ID, `GetStackPolicy`, `GetRolePolicy` (URL-decode its document), `DescribeStateMachine` on the exact version ARN, `DescribeExecution`, `GetFunctionConfiguration`, `DescribeImages`, and exact VPC/subnet/route/endpoint/SG/ENI inventory. The injected network port returns those raw rows as shown in the focused test. A fictional Boolean success receipt is insufficient.
- The existing managed watchdog workflow still refuses admission and lacks the positive root-volume absence wire. A real reviewed version must independently qualify exact instance/root/ENI absence, original-C cleanup, **and late CloudFormation/EC2 provisioning reconciliation**; a preflight response and the deadline Deny do not themselves prove physical absence at C. A request admitted just before C may become visible later; unknown or late evidence keeps the allocation quarantined. The endpoint inventory and role policy are point-in-time reads; the issuer must hold those bindings unchanged during provisioning and cleanup. The seven-day log retention bounds age, while ingestion volume requires a separately reviewed guest log quota. Guest bootstrap, helper binary, image scan, actual endpoint ingress/routing and non-root/browser/renderer/Bash probes remain separate gates. `proxy-web` mode is intentionally unsynthesizable until the network owner provides a reviewed proxy-only outbound topology and TLS-origin enforcement; browser activation remains held.

The enabled compiler requires `{proposal, privateNetwork, encryption, bootstrap, watchdog, launchGuard}` with no defaults. `proposal` is the exact existing binding. `bootstrap.userDataBase64` is literal reviewed EC2 user data whose decoded SHA-256 equals `proposal.source.bootstrapSha256`. `bootstrap.nativeHelperSha256` pins the SDK/browser pre-exec helper; `bootstrap.nativeHostRelayHelperSha256` separately pins the host-relay pre-exec helper. They must differ, and guest bootstrap must verify both installed binaries against these exact pins before any launcher use. The `/2` preflight and watchdog-input schemas carry both digests through template metadata, resource properties and the prearmed execution; the preflight refuses a missing or changed digest. `watchdog` includes a numeric Lambda provider version, numeric Standard state-machine version, unique running execution ARN, raw definition digest, independently issued qualification-evidence digest and original `t0Ms`. `launchGuard.serviceRoleArn` is exactly `arn:aws:iam::967807252336:role/MeriD005-<hostId>-g<generation>`. Its two digests are the canonical SHA-256 values of `launchDeadlinePolicy(leaseDeadlineMs)` and `closedHostStackPolicy()`. The deployment owner must compare the entire rendered template and stack/role policies before any separately authorized change set, create the stack with that service role and stack policy, and retain them until exact physical absence is verified. The prearmed execution input must equal canonical JSON of `expectedWatchdogInput(validatedInput, template.Metadata.templateReviewSha256)`.

### Live step: Control egress to the hosts (foundation stack; not executed by this change)

The Control security group has `allowAllOutbound: false`, so Control cannot reach a host's pinned listener (TCP 9444) until the foundation grants it. The live `meri-first-chat-foundation` stack has drifted from the committed source in both directions (it still holds the issuer resources the source removed, and differs elsewhere), so deploying the foundation from freshly synthesized source is NOT safe. Instead:

- The source now carries the rule: `browserHostSecurityGroupId` (optional, in `first-chat/foundation-binding.json`) makes `first-chat-foundation.mjs` add one standalone `AWS::EC2::SecurityGroupEgress` from the control group to the host group on the listener port, exactly like the existing egress to the endpoint group. Without the key the synthesis is unchanged.
- `first-chat/foundation-egress-patch.mjs` takes that one resource from the source synthesis and adds it to the LIVE template, asserting that the result differs from live by exactly one added resource (no removal, no modification, no other section).

Steps (release owner, one effect, read-backs between):

1. `aws cloudformation get-template --stack-name meri-first-chat-foundation --template-stage Original --query TemplateBody --output json > live.json`.
2. `node infra/product-preview/first-chat/foundation-egress-patch.mjs --live live.json --binding infra/product-preview/first-chat/foundation-binding.json --out patched.json`. Expected summary on the 2 November live template: `added` is exactly `ControlSgtoMeriFirstChatFoundationBrowserHostSg4770A6A39444C14D4ED1`, `removed` and `modified` empty, `sectionsChanged` empty, `inlineTemplateAllowed` true (24,715 bytes, below the 51,200 byte limit). Any other result: stop.
3. `aws cloudformation create-change-set --stack-name meri-first-chat-foundation --change-set-type UPDATE --template-body file://patched.json --capabilities CAPABILITY_IAM CAPABILITY_NAMED_IAM` (the stack has no parameters; its `meri=first-chat-preview` tag is kept when none is passed).
4. Read the change set back. It must list exactly one change: `Add`, `AWS::EC2::SecurityGroupEgress`, that logical id, no replacement. A Modify, a Remove or a second change means the live stack moved or the patch is wrong: delete the change set and stop.
5. Execute only with release authorization; wait for `UPDATE_COMPLETE`.
6. Read back the control group: its egress now also lists TCP 9444 to the host group, every earlier egress rule is unchanged, the 8080, 8082 and 8443 ingress rules are untouched (the change cannot reach ingress), and the control, worker and schedule services stay 1/1 with healthy targets.

Rollback: an UPDATE change set from `patched.json` back to the saved `live.json` shows exactly one Remove; or revoke the single rule.

Follow-ups recorded, not done here: reconcile the foundation source to live (or live to source) so a source-driven foundation deploy becomes safe; extract the roughly 100 lines `image-build.sh` of the browser host shares with `infra/product-preview/image-build.sh` into one helper. The `no inline ingress` tests added to the foundation and private-edge suites keep the standalone ingress rules that the listener and observer stacks add to those groups from being reconciled away.
