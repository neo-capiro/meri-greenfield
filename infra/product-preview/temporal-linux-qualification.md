# Temporal derivative Linux qualification packet — unrun

This is a review checklist for a **separately authorized** isolated Linux build and private Fargate smoke. It does not approve a build, credential, SQL action, AWS write or service start. The source at this pin keeps all five service counts zero and `MERI_TEMPORAL_ACTIVATION=disabled`.

## Freeze source and image bytes before the build

1. Name one approved Meri Git commit and require a clean exact checkout. Record `git rev-parse HEAD`, `git status --porcelain --untracked-files=all`, and SHA-256 for `temporal-launch.Dockerfile`, `.sh`, `-main.mjs`, `-render.mjs`, `-migration-plan.mjs`, `temporal-binding.mjs`, and `temporal-deployment.mjs`. Compare each blob to `git show <approved-commit>:<path>`. A 40-hex `LAUNCH_SOURCE_COMMIT` build arg alone only echoes a claim; it does not establish image provenance.
2. Independently approve a `node:24-alpine@sha256:<digest>` linux/amd64 image, the pinned `temporalio/server` linux/amd64 digest `sha256:2695f2564ec51aa84232bf3fa59b31e2cce99bec437a64f5bc487cbe21b2de0e`, the complete source context, and the public issuer CA SHA-256. Pass the CA only through the reviewed BuildKit secret mount. No private key, JWT, DB password or client material belongs in a build argument, layer, image label, source archive or build log.
3. Build the derivative only under a separate image-build authorization. Record the resulting image digest and scan/license disposition, then compare the ECR image digest in `serverImageUri` to that exact artifact. Inspect the final image user, entrypoint, source-commit environment, `/run/temporal` and `/tmp` VOLUME declarations, file modes, Node 24 executable and bundled musl loader/libraries. Preserve an immutable provenance receipt; do not infer content from an ECR tag.

## Isolated Linux container checks before any service count changes

1. With no runtime Secrets, run `/opt/meri/temporal-launch --help`: exit 0, fixed usage, no metadata/JWKS/database contact or secret output. An invalid role exits 64. A valid role with activation disabled exits 78 before network. Check the pinned `temporal-server --help`/CLI flag order and native executable compatibility on the actual derivative image.
2. With separately approved **synthetic** CA/leaf/JWKS/DB material in an isolated harness, verify the launcher parses one exact role, discovers its task ENI rather than loopback, writes owner-only files under `/run/temporal`, and renders a valid complete Temporal 1.32.1 config. Without a migrated PostgreSQL target and peer services, a child startup may fail at its dependency check; treat that bounded failure as a launcher/config-load observation, never as service-start proof. Verify cleanup on clean exit, signal, spawn failure and preflight failure with an isolated fake child. Keep fixture credentials ephemeral and outside Git/logs. Qualify `/run/temporal` ownership/mode 0700 and `/tmp` mode 01777 on the actual mounted volumes, not just the image. Inspect child stdout/stderr for config-derived sensitive material before allowing awslogs.
3. Parse the generated JSON/YAML with the exact Temporal 1.32.1 server. Check both `postgres12` stores, immutable 128 history shards, frontend `audience`/default mapper/authorizer, external versus internal frontend routes, five role ports, mTLS certificates/SAN/EKU/chain, hostname verification and disabled archival. Fail if a stock/default config silently overrides these values. Record the exact config hash without recording its credentials.

## Independently owned private infrastructure and identity gates

1. Existing Aurora is the selected direction: `capiro-dev-data-auroracluster23d869c0-ltmz40k47ewv`, writer endpoint and SG/VPC pinned in `TEMPORAL_EXISTING_DATABASE`, observed `aurora-postgresql` 16.11. Refresh nonsecret cluster readback and compare exact pins. Application schemas belong in existing database `capiro`; preserve its PUBLIC/database-wide privileges and unrelated schemas. Temporal's source-fixed `temporal`/`temporal_visibility` logical names still need catalog/exclusive allocation; no new database creation is authorized here. Qualify exact migration/grants source on an authorized isolated target, primary 1.19 then visibility 1.14, nonowner runtime roles, current catalog/engine compatibility and restore. The PostgreSQL 16.15 fixture is an isolated candidate, not the deployed Aurora version. No application/runtime task gets schema-admin credentials. Do not run SQL from this packet.
2. Collect current AWS Describe readbacks for the independent VPC, both task subnets and route tables, five named interface endpoints, S3 gateway/prefix list, issuer SG, migration SG and actual peer rules. Run `validateTemporalNetworkReadback` offline, then separately verify readback provenance, endpoint policies, private DNS resolution, SG ingress/egress, ECR layer pull, issuer reachability and no unintended public route. Prove the separate Meri-service-VPC to Aurora-VPC route/DNS/SG-reference path; the source adds only six exact 5432 ingress rules to the existing DB SG, not a peering/transit route. The product control/poller candidate also has no proved cross-VPC route to the Temporal frontend; `inspectTemporalProductJoin` remains HOLD until a reviewed route and client SG reference exist.
3. Allocate a real dedicated workload issuer with reviewed asymmetric key custody and mTLS identity. Require bounded `iat`/`nbf`/`exp`, unique key ID, exact `iss`, `aud=meri-temporal`, and separately named control/poller subjects with only `meri:write` for the bound namespace. Demonstrate allowed poll/complete/heartbeat and deny absent/foreign issuer, missing/expired `exp`, wrong audience, wrong namespace/role, revoked key and malformed JWKS. The stock default mapper does **not** establish exact issuer or mandatory `exp`; a reviewed ingress control or equivalent is required if those are hard enforcement requirements.
4. Compose an ongoing token issuer/writer in the product control and poller tasks, distinct from one-shot material init. Prove atomic owner-only token-file replacement on a task-local writable volume, read-only app mounts, expiry/read failure stop, refresh/restart/rotation, and no stale-token reuse. The existing `apps/runtime/temporal-authorization.mjs` is the reader; it does not mint tokens. Product-mode configuration must require authorization before enabling either service.
5. After an isolated PostgreSQL target has been migrated and its role grants/catalog read back, qualify successful startup of five roles one at a time in a private synthetic environment with explicit stop/rollback owner. Qualify the selected Aurora 16.11 compatibility separately, then two replicas across AZs, Cloud Map membership replacement, the existing cluster's failover/PITR policy, namespace registration, schedule/replay/Continue-as-New, JWT rotation, old-key retention and worker reconnect. Observe real resource cost and alarms. Do not infer HA or recovery from a single-process smoke. This template creates no RDS resource and does not change the existing cluster's backup, engine or failover settings.

## Activation condition

Source review and the focused Node tests allow **no** count increase. An activation change must name the selected existing Aurora pins and exact dedicated schema/role allocation, pinned SQL and image bytes, measured capacity/history-shard choice, network/route and issuer evidence, exact versioned Secrets and IAM policies, token writer, Linux/Fargate receipts, security/scan disposition, cost owner and stop/restore plan. It must separately change `enabled:false`/five `DesiredCount:0` and `MERI_TEMPORAL_ACTIVATION=disabled` under a reviewed deployment action. The present source cannot activate itself.
