# Static product material source and remaining delivery gates

The disabled product manifest now composes static control and Temporal-worker material only when both exact versioned bundle references and independently pinned envelopes are supplied. It refuses an `unmounted` material binding. Service counts remain zero. `apps/runtime/config.mjs` remains the canonical role configuration and secret-file reader. `apps/runtime/material-init-plan.mjs` owns the static control/poller inventory and Linux preflight; `infra/product-preview/material-delivery.mjs` re-exports it. `apps/runtime/material-init.mjs` owns validation, exclusive file writes and rollback. `apps/runtime/material-init-cli.mjs` is the packaged one-shot entrypoint. The existing Dockerfile `COPY apps` includes these modules. No credential is issued and no network or filesystem operation starts on import.

The init owner uses the existing role configuration validator, canonical SHA-256 and operation lifetime. It accepts only control or Temporal-worker material. Every credential/certificate is a direct child of `/run/meri`; configuration is exactly `/run/meri/control.json` or `/run/meri/worker.json`. The native/control capability alias is the sole allowed alias. Optional download-signing and Temporal-authorization files are present only when the canonical configuration declares them. Dynamic control capability storage must be an absolute separate directory outside `/run/meri`.

## Immutable static contract

`parseStaticProductMaterialExpected(expected)` accepts exactly:

```
{
  schemaVersion: 1,
  role: 'control' | 'temporal-worker' | 'temporal-issuer' | 'model-owner' | 'model-proxy',
  runtimeUser: '<nonroot numeric uid>:<nonroot numeric gid>',   // reader identity; see role-bound users below
  sourceCommit: '<40 lowercase hex>',
  imageDigest: 'sha256:<64 lowercase hex>',
  materialContractSha256: '<64 lowercase hex>',
  sha256ByPath: { '/run/meri/<exact file>': '<64 lowercase hex>', ... }
}
```

`materialContractSha256` is the repository's canonical SHA-256 of the other fields, omitting only `materialContractSha256` itself. This digest correlates the fixed deployment inputs; it is not an issuer signature. Expected file hashes must be supplied independently of the secret bundle in the reviewed task definition. A delivery echo, `authenticated:true`, browser input or ECS metadata does not create authority. Static material cannot contain the eventual task ARN. The deployment owner must verify the actual registered task definition and its secret references at action time; a self-reference to that definition's future ARN cannot be embedded in its own environment.

The closed bundle is `{files:[{path,base64},...]}`. It must contain exactly the independently pinned files, once each, with canonical base64 encoding, decoded sizes 1 through 32,768 bytes and a maximum serialized bundle size of 65,536 UTF-8 bytes. Configuration bytes must match their exact SHA before parsing, pass the canonical role validator and reproduce the complete pinned inventory. No material, parsed configuration or per-file digest map is returned in the startup receipt.

`validateStaticProductDelivery({expected,bundle})` performs pure offline validation. `materializeStaticProductMaterial({expected,delivery,now,signal,maxRequestMs})` obtains one bundle through the injected trusted `delivery.fetch` port within a bounded lifetime. It accepts no ambient credential or network fallback. It refuses outside Linux or with the wrong effective UID/GID before invoking delivery. The directory must be absent and createable or already empty, private, non-symlinked and owned by that same UID/GID. Files are created with `O_EXCL | O_NOFOLLOW`, mode `0600`, synced and checked by the existing read-only preflight. The directory is `0700` and its identity is rechecked around writes. A failure rolls back only the owned filesystem instance. Replacement files/directories or foreign entries refuse cleanup and report `STATIC_INIT_CLEANUP_FAILED` with a content-free original failure code. `releaseStaticProductMaterial(receipt)` performs explicit same-process rollback; the receipt cannot be forged or serialized into later authority. ECS owns final task-volume disposal after init exits.

## Model budget owner and model proxy roles

Two further fixed-inventory roles serve the product model-proxy pair. Their configuration validators run inside the plan, and every `{path,sha256}` or `*Sha256` reference a configuration makes to another delivered file must equal that file's independent pin (`STATIC_INIT_CONTENT_REFUSED` otherwise). `runtimeUser` is the **reader** identity and is role-bound: `model-owner` and `temporal-issuer` accept only `1000:1000`, `model-proxy` accepts only `10001:10001`, and no other role may use uid or gid `10001`. The envelope parser refuses a wrong pair before delivery.

| `model-owner` | `node apps/proxy/product/owner-entrypoint.mjs --config /run/meri/owner.json`, `MERI_PRODUCT_OWNER_REQUIRED=1`, `MERI_PRODUCT_OWNER_CONFIG_SHA256=<pin of owner.json>`, user `1000:1000` | `owner.json`; `control.json` (control's exact bytes); control's `database.connectionFile`; control's `nativeCandidate.identity.credentialFile`; owner `tls.caFile`, `certFile`, `keyFile` (7 files) | `validateProductOwnerConfiguration` plus `enabled:true`, `controlConfigurationFile` exactly `/run/meri/control.json`; the copy must compile as a static `control` plan, have `multiRun.dynamicInitialRuns:true` and the owner's `selectedClientId`. `controlConfigurationSha256` and `nativeCredentialFileSha256` must equal the delivered pins. |

The owner reads the database connection and identity credential at the absolute paths named inside `control.json`, so those paths must already be direct `/run/meri` children in control's own configuration; the owner task receives that same subset of control's material.

### model-proxy volume ownership

The proxy image has no Node, so `material-init` runs from the Node runtime image. A task-local ECS bind volume without an image `VOLUME` seed is `root:root` mode `0755` on Fargate; the Node image seeds `/run/meri` as `1000:1000 0700`, and which container's image seeds a shared volume is not something this source can prove. Neither state is writable by uid 10001. The `model-proxy` writer is therefore root (`writerUser` `0:0` in the plan) and needs only `CAP_CHOWN`:

1. Adopt the existing empty directory: `lchown` to `0:0`, open it `O_DIRECTORY|O_NOFOLLOW`, `fchmod 0700`, recheck dev/inode/owner/mode. A non-empty directory still refuses.
2. Write each file root-owned `0600` with `O_EXCL|O_NOFOLLOW`, then run the same read-only preflight as root.
3. Hand over: `lchown` each file, then the directory, to `10001:10001`, rechecking dev/inode, `0600`/`0700`, `nlink 1` and size.

After handover, root without `DAC_OVERRIDE` cannot read the files, so explicit same-process rollback refuses (`STATIC_INIT_CLEANUP_REFUSED`) and ECS disposes the volume. A failure during handover reports `STATIC_INIT_CLEANUP_FAILED`. The reader checks still hold in the proxy: `read_reviewed_file` accepts owner uid `0` or its euid, no group/other write and `&077 == 0` for keys.

ECS wiring for `meri-product-preview-proxy` (deviates from the shared init shape only in user and capabilities):

- volume `material` (task-local, no host path); `material-init` mounts it at `/run/meri` writable; container `model-proxy` mounts it at `/run/meri` with `readOnly: true` and `dependsOn [{containerName:'material-init',condition:'SUCCESS'}]`.
- `material-init`: Node runtime image, `user: "0:0"`, `essential: false`, `readonlyRootFilesystem: true`, no privileged mode. Fargate cannot add capabilities other than `SYS_PTRACE`, so keep `CHOWN` by dropping every other default instead of `drop: ['ALL']`: `drop: ['AUDIT_WRITE','DAC_OVERRIDE','FOWNER','FSETID','KILL','MKNOD','NET_BIND_SERVICE','NET_RAW','SETFCAP','SETGID','SETPCAP','SETUID','SYS_CHROOT']`.
- `MERI_STATIC_MATERIAL_EXPECTED` has `role:'model-proxy'`, `runtimeUser:'10001:10001'`; the init refuses to run as anything other than `0:0`.

`meri-product-preview-owner` uses the unchanged shape: Node image for both containers, init `user: "1000:1000"`, `drop: ['ALL']`, writable init mount, `readOnly: true` app mount, `SUCCESS` dependency, and `role:'model-owner'`, `runtimeUser:'1000:1000'`.

## Disabled ECS composition

The exact init command is `node apps/runtime/material-init-cli.mjs write`. It takes no material arguments. The fixed environment slots are:

- `MERI_STATIC_MATERIAL_EXPECTED`: nonsecret reviewed expected-envelope JSON, at most 8,192 UTF-8 bytes.
- `MERI_STATIC_MATERIAL_BUNDLE`: init-only Secrets Manager `SecretString` bundle JSON, at most 65,536 UTF-8 bytes. The CLI deletes this slot before validation and spawns no child. It does not pass material to app environment or output.

CLI exit codes are `0` for success/help, `64` for invalid arguments, `78` for missing/refused material and `1` for reported cleanup/internal failure. `--help` and empty arguments are inert. Success output contains only `ready`, `role` and `fileCount`; diagnostics contain only a fixed failure code. Node cannot securely erase immutable strings or the initial process environment, so the init container must have a separate process namespace and exit before the application starts.

The manifest emits the same digest-pinned product image, nonroot UID/GID, a nonessential init container, an init-only exact-version secret reference of the form `arn:aws:secretsmanager:<region>:<account>:secret:<name-suffix>:::<VersionId>`, one task-local ephemeral volume at `/run/meri`, a writable init mount, a read-only application mount and application `dependsOn: [{containerName:'material-init',condition:'SUCCESS'}]`. The control and Temporal-worker app containers receive neither the secret reference nor its value. No secret value belongs in a RunTask override, log or Git. The expected SHA map belongs in the independently reviewed task-definition environment. The ECS execution role retrieves the secret; task-role permissions are task-scoped, so the control init shares any control task role even though this source calls no AWS client. There is no per-container task-role exclusion.

An empty bind volume otherwise defaults to root ownership and `0755`. AWS documents customization by creating/chowning the image path and declaring an exactly matching Dockerfile `VOLUME`. The selected image source seeds `/run/meri` with numeric `1000:1000`, mode `0700`; both init and app must use that exact user and mount path. Init always checks the effective mounted ownership; an image declaration is not physical Fargate acceptance. See [AWS bind mounts](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html) and [the exact VOLUME/containerPath example](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mount-examples.html).

Exact-version secret injection requires Fargate Linux platform 1.4.0 or later, reviewed execution-role `secretsmanager:GetSecretValue` on that secret and `kms:Decrypt` on its customer-managed key when used, and a reachable Secrets Manager endpoint. A changed secret does not update an already running container; the deployment owner must register/verify a new exact revision and replace tasks for static rotation. See [AWS ECS secret injection and version selection](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html). The 65,536 byte ceiling follows [Secrets Manager SecretString limits](https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_CreateSecret.html). This source does not create any of these resources or permissions.

## Exact remaining ownership and activation gates

The missing provisioning inputs are one real immutable role-specific bundle Secret ARN and VersionId for control and poller, a protected independent SHA map and accepted source/image binding, and the execution role/KMS/network readback for those exact references. An exact source binding must include the reviewed source commit, digest-pinned image, and the complete hashes of every required `/run/meri` file. Their shipping owner must obtain existing approved database, native/control, identity, proxy and Temporal mTLS material from their actual authority; the init source does not invent them. Optional download keys require their existing signing-key owner. No secret value is committed or created here.

| Role | Source-required task-local material | Authority and version still to allocate or read back |
| --- | --- | --- |
| Control | `control.json`; database connection file; native/control capability (one allowed alias); identity, task, and model-proxy capability files; Temporal CA, client certificate and private key; router CA certificate when `taskRouter` is enabled; **distinct runner CA private signing key and control HTTPS CA certificate** when `taskRouter.poststart.enabled` is enabled; optional download-signing key and Temporal authorization token | The existing database, Core/native, proxy, Temporal and router trust owners must provide the values, issuer scope, exact bundle VersionId and independent file hashes. A named security owner must allocate the runner CA pair, separate control CA trust, key rotation and custody; the signing key stays only in the control bundle. Optional signing/token issuers and rotation also need named owners. |
| Temporal worker | `worker.json`; native capability; Temporal CA, client certificate and private key; Temporal authorization token when configured | The existing native and Temporal owners must provide the values, exact worker bundle VersionId and independent file hashes. Token renewal needs an ongoing owner. |
| Per-run conversation runner | Image/task-definition-pinned public control CA bytes/hash and fixed private control origin; then exact original's config, task capability and trusted control CA; task-generated private key and issuer-approved task-bound server certificate; exact candidate and ECS task metadata files | The pre-CLI source generates/obtains these **after** the admitted task is known; no original-specific bytes belong in either static bundle or RunTask override. The existing original-run issuance owner, control-side CA issuer, private ALB peer proof and Linux task-local material custody require real allocation/qualification. Candidate and metadata files are checked for consistency, not independent identity authority. |

The table lists required file classes, not allocated credentials or certificates. The current source supplies no values, version IDs, issuer keys or certificate authority.

Temporal authorization declares its existing runtime refresh reader, which fails closed on missing/expired/rejected tokens. This one-shot static writer supplies no ongoing issuer or rotation process. When token-file authorization is configured, the actual issuer, fresh-file rotation owner and ability to update the underlying task-local volume remain required before activation. A read-only app mount can read updated files but cannot perform that rotation. Dynamic per-run capability authority also needs its separately writable configured directory and durable issuer/grant ownership; it must not reuse the immutable static mount.

The runner HTTPS receiver source is mounted in the actual launch path: it validates owner-only CA, leaf, key, candidate and metadata files against the original before opening the TLS listener. Product CLI startup refuses a plaintext receiver. `apps/runtime/runner-bootstrap-files.mjs` materializes the exact original run's task capability, config and control CA; its expected envelope binds original run, task ARN/revision, expiry, versions, origin, SAN, capability/material references and CA hash. The manifest now starts `runner-poststart-cli.mjs start`, which reads ECS task metadata, generates the private key/CSR, makes a bounded direct TLS challenge/redeem exchange, writes owner-only `/run/meri/poststart` files, and passes the returned config/TLS plus pinned native fetch to the runtime CLI. It releases only its own material at exit. This is conditional source composition; no real CA/credential was generated or mounted and no Linux/Fargate positive run was performed.

The task router's poststart authority now checks the original allocation, current admission, fresh ECS task and ENI peer, single-use CSR possession and expiry before its named issuer signs a serverAuth leaf with the exact task DNS SAN. It repeats those checks before releasing the existing issuance owner's capability and material. No leaf/key is added to a pre-RunTask static bundle, no second capability issuer is installed, and the private task key never leaves the runner. Its use of the final ALB-appended XFF hop requires an independently proven private ALB listener/SG and header configuration; source validation cannot establish that live boundary.

Focused Windows Node 24 checks cover pure plans, exact delivery bytes/inventory/configuration, optional files, fail-closed platform/port behavior, poststart owner/CSR/CLI and cleanup fixtures. Positive Linux directory ownership, write rollback, cancellation during writes, replacement refusal and actual Fargate image/mount/secret/dependency behavior are unverified gates. Keep service counts zero until the exact real references, image binding, CA/issuer ownership, private peer proof, rotation, cleanup and physical qualification are independently accepted.
