## PostgreSQL row locks and immutable custody

PostgreSQL 16 requires UPDATE privilege on at least one column of every table locked with `SELECT ... FOR UPDATE`, in addition to SELECT. A privilege on an otherwise unused column still permits a direct SQL UPDATE unless the database rejects it. This behavior is documented in [PostgreSQL 16 SELECT](https://www.postgresql.org/docs/16/sql-select.html).

Migration 0017 already rejects UPDATE/DELETE/TRUNCATE for `initial_run_bindings`; grant only `UPDATE(record_sha256)` for row locking. The other locks in that journal need `runs UPDATE(sequence_base)`, `initial_inputs UPDATE(allocation_sha256)` and `next_runs UPDATE(reservation_sha256)`. Their existing triggers preserve those values; ordinary source state updates retain their real columns. The `runs` guard permits a same-value assignment, while a changed sequence base is rejected. No lock-only privilege grants the ability to alter a binding.

The budget migration 0001 has no equivalent guards for several tables locked by admission/currentness. Granting a dummy identity column alone would weaken custody. The SQL packet therefore proposes statement-level triggers rejecting any UPDATE **OF the single lock-only column**, including a no-op, before granting that column. They do not reject legitimate updates to other columns:

| Table | Lock-only column whose UPDATE is refused | Legitimate mutable columns preserved |
| --- | --- | --- |
| `meri_conversations.conversations` | `projection_sha256` | None used by the traced store; this proposal leaves any separately reviewed columns untouched |
| `meri_conversations.selected_outputs` | `preparation_sha256` | None used by the traced retention adapter |
| `meri_product_budget.budget` | `id` | Model owner may advance `consumed_micro_usd`/`quarantined`; control receives only the guarded lock privilege |
| `meri_product_budget.runs` | `policy_revision` | `attempt`, `worker_arn`, `fence` remain outside the new guard, for separately authorized owner rollover |
| `meri_product_budget.grants` | `capability_sha256` | `state` activation/revocation remains available only to control; expiry/identity updates are not granted by this packet |
| `meri_product_budget.tool_run_allocations` | `allocation_sha256` | No additional write privilege granted |
| `meri_product_budget.tool_grant_bindings` | `facts` | No additional write privilege granted |
| `meri_product_budget.tenant_budgets` | `tenant_id` | Operator-managed caps remain outside the new guard and runtime grants |

These guards are **unallocated source proposals**. They are not a migration, and no migration filename/ID is invented. The central owner must allocate exact ordered migration source and prove the guards in isolated PostgreSQL before granting these lock-only privileges. Existing INSERT ON CONFLICT and grant state changes are preserved. Runtime roles must not own the schema/table/function or have rights to disable triggers. Existing trigger functions need no new runtime EXECUTE grant merely to fire; explicit callable routines remain separately scoped.
