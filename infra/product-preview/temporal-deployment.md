# Disabled Temporal deployment source outline

`temporal-binding.mjs` validates the exact reviewed inputs; `temporal-deployment.mjs` owns only the reviewable infrastructure boundary for the self-hosted Temporal **design candidate**. The existing `apps/control/qualification-temporal` fixture owns the server/SDK/schema pins and five-role authorization decisions; runtime control and poller configuration remains in `apps/runtime`. This source synthesizes a dedicated encrypted Multi-AZ PostgreSQL 16 instance, a private Cloud Map namespace with five A-record services, six security groups (one per server role and one database group), five role task definitions and five stopped services. The primary database is created by RDS; a separate ordered migration owner must create and migrate the visibility database. Neither a migration nor a namespace registration is executed by synthesis. The separate Meri application Aurora store is outside this candidate; this template does not reuse it. An explicit architecture/placement decision is still needed before deployment.

Its sole synthesis export is `synthesizeTemporalPreview(binding)`. It accepts only `enabled:false` and exact, reviewable account, independently reviewed Meri VPC, two-AZ subnets, cluster, digest-pinned **derivative** server image, upstream 1.32.1 amd64 digest, launcher source/renderer hash, certificate and password Secret **version** references, workload issuer/JWKS/CA hash, namespace/queue, IAM role, KMS, and network peers. The observed shared `capiro-dev` VPC is explicitly refused. It derives immutable Temporal 1.32.1, `postgres12`, shard, per-role sizing/DB connection ceilings, and role defaults from the exact-hash pinned candidate fixture. The fixed CloudFormation names cannot adopt another service by label. Missing or ambiguous material refuses before CDK constructs are created. The template has no API client, deployment entrypoint, lookup, credentials, model call or server-start side effect. `enabled:false` gates ECS desired counts only: deploying this template would still create billable RDS, Cloud Map and network resources. The task environment separately fixes `MERI_TEMPORAL_ACTIVATION=disabled`, which the launcher refuses even if someone raises desired count.

Runtime certificate, RDS CA and DB material is injected only into the corresponding stopped task definition as exact-version ECS Secrets; only the frontend task receives frontend private-key and client-CA Secret fields. The values are absent from the source and template. The execution role must be granted the selected ECR digest, exact secret base ARNs/KMS keys, and log stream delivery; five distinct task roles remain independent and receive no blanket AWS policy from this template. The DB master password is an exact-version CloudFormation dynamic reference, not an invented password or managed-secret side effect. Secret rotation requires a reviewed new version/task revision; ECS environment injection does not update running tasks automatically. The migration principal is separate from server task roles.

The outputs give the nonsecret composition join: `TemporalFrontendAddress = frontend.<privateDnsName>:7233`, the bound namespace, task queue, and RDS endpoint. Only the two supplied trusted **application** SGs can ingress the frontend gRPC port; Temporal internode role SGs also ingress that port. No application SG ingresses the internal frontend. The five Temporal role SGs admit role-specific gRPC/membership ports from other Temporal role SGs and egress only to those role ports, dedicated RDS 5432, reviewed endpoint SGs 443, and the dedicated issuer SG 443 for JWKS refresh. The database SG accepts only Temporal roles and the separately supplied migration SG. Tasks use supplied subnet IDs, no public IP, Fargate 1.4.0, and desired count zero. Private route-table and endpoint ownership must be proven from AWS readback before deployment; an ID and AZ label alone do not prove a subnet is private. DNS resolution, endpoint/network routing, cert SANs and actual ENI discovery still require live checks.

**Image/launcher integration seam:** `temporal-launch-render.mjs` now generates a complete JSON document (YAML 1.2 syntax) with nonempty `global.authorization.audience`, the default mapper/authorizer, private frontend DNS instead of upstream loopback, separate stores, disabled archival, mTLS trust roots and actual task ENI membership address. `temporal-launch-main.mjs` checks the renderer digest, issuer/RDS CA hashes, certificate/key pairs, exact single role, metadata-v4 one-container ENI, and a nonempty HTTPS JWKS before writing owner-only task-local files and starting `/usr/local/bin/temporal-server --config-file <file> start --service <role>`. The renderer receives no credentials from source; exact-version ECS Secrets arrive only at runtime. The task root is read-only; `/run/temporal` and `/tmp` are the declared writable ephemeral mounts. `temporal-launch.Dockerfile` pins the accepted Alpine/musl Temporal amd64 image and requires a separately pinned `node:24-alpine` image; it copies that image's musl loader and Node libraries as a set, and runs a build-time executable check before accepting an image. It also requires an exact source commit and supplied public issuer CA. The derivative image is **not built, scanned or Linux-run** here. The upstream default mapper does not itself require an issuer string or exp claim, so dedicated minting/expiry and ingress behavior must be checked live. [Tagged upstream config template](https://github.com/temporalio/temporal/blob/v1.32.1/docker/config_template.yaml), [Temporal authorization configuration](https://docs.temporal.io/references/service-configuration#authorization), [ECS exact-version Secret behavior](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html).

The image declares `/run/temporal` and `/tmp` as Docker volumes after assigning the former to the `temporal` user at mode 0700 and the latter mode 01777. ECS bind mounts may then inherit the image directory permissions; verify both mounted directories' actual owner/mode and task-local writes on Fargate before activation. The launcher refuses a nonowner or group/other-writable `/run/temporal`. Its JWKS preflight imports each public signing key and checks algorithm, key size/curve and unique key IDs; actual issuer token acceptance, rotation and expiry remain live gates. [ECS bind mount ownership](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html).

The launcher CLI accepts exactly one Temporal role. `--help` prints usage without reading configuration or contacting a service. Exit 0 means help or a clean server exit; 64 means invalid role arguments; 78 means binding, image, metadata/JWKS preflight, server-start or cleanup refusal. Launcher-owned refusals are fixed strings and do not echo injected material. The child Temporal server inherits stdout/stderr, so its Linux startup logs need a separate secret-redaction inspection before activation. A future source review must change both `enabled:false`/zero services and the independent `MERI_TEMPORAL_ACTIVATION=disabled` gate to permit a rollout; this source cannot silently activate.

**Ordered data/identity gates:** create the distinct `temporal_visibility` logical database and separate least-privilege primary/visibility roles, then apply pinned `postgres12` primary 1.19 and visibility 1.14 migrations with an isolated migration principal. An exact migration plan hash is a binding only; it does not execute SQL or prove catalog state. After schema checks, register the bound namespace and task queue using restricted administrative identity and verify `namespace:write` on the actual control/poller issuer. A real private HTTPS JWKS issuer/service, certificate issuance/rotation and bridge from its JWT to the runtime token-file refresh reader remain provisioning/source work; the issuer is a supplied SG/URL binding, **not** fabricated by this template. The private VPC, subnets, endpoints, cluster, log group, IAM roles and Secrets are reviewed inputs rather than resources secretly adopted by name.

The actual derivative image, Node binary compatibility, Temporal YAML parser, CLI startup, config values and certificate SAN/EKU behavior must be qualified on Linux before activation. Cloud Map/membership startup, RDS TLS hostname verification, default authorizer issuer limitation, JWKS rotation/retained-key behavior, TLS/secret rotation, exact SQL migration, namespace registration, and application-worker `namespace:write` issuance remain live gates. This source cannot satisfy them by itself. Every ECS service remains at desired count zero. Approval of a future change set must name the RDS/KMS cost and restore owner, image/scan status, VPC ownership, six SG peers, role/secret scopes, issuer, migration principal and SQL hash, maximum service count, old-pin rollback and physical stop owner. No AWS build, write, SQL or credential creation occurred.

This is a synthesis-capable disabled CloudFormation source plus a source-only launcher recipe, not a ready-to-run deployment packet: the derivative image, issuer, independent network, exact Secrets, IAM policies, ordered migration and live qualification are unallocated/unrun inputs. A synthesized output cannot certify their existence or authority.

Focused verification: Node 24 CDK synthesis, resource/network shape assertions, negative binding mutations and exact fixture-hash drift checks; separate Node 24 launcher tests inspect the rendered config and reject activation, role, issuer, SQL, secret-scope, metadata and JWKS contradictions. These checks do not verify actual subnet routes, a built image, Temporal's YAML parser or issuer behavior. No install, SQL, AWS write, build, or deploy.
