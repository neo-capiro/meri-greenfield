# Disabled Meri product preview manifest

`synthesizeProductPreview(binding)` is a pure, offline CDK template builder. It does not query AWS, create resources, read files, or deploy. The binding must name exact reviewed resources in account `967807252336`, region `us-east-1`; there are no default cluster, image, network, role, log, or ingress values. Synthetic binding values appear only in `manifest.test.mjs`.

The builder checks account, region, resource type and immutable image syntax. It does not treat a resource name as permission to reuse it or a reason to replace an otherwise qualified resource. The deployment owner must independently read back actual CloudFormation ownership, VPC/subnet and security-group isolation, IAM trust and actions, log permissions, image provenance, and target-group routing for the exact input identifiers before any stack action. The observed qualification and legacy Capiro resources have not passed that product binding review.

The template contains three digest-pinned Linux Fargate task definitions, two ECS services with `DesiredCount: 0`, and no other resources. Control listens on port 8080, the Temporal worker on 8081, and the fresh conversation runner on private port 8080. The runner has one container named `worker`, matching the existing native candidate's `taskRequest` container binding, and no service. The services use an existing cluster, one supplied subnet and role-specific existing security groups with public IP disabled. Distinct reviewed public and private control target groups may be named explicitly; both attach to the same stopped control container on port 8080. No target group, ALB, DNS name or listener rule is inferred or created. No task can be started by synthesis. `enabled` must be `false` and `materialDelivery` must be `unmounted`.

The two target groups provide separate routing references, **not path isolation**. The proposed shared port exposes the same control HTTP router to both target groups. Public isolation depends on an independently reviewed HTTPS listener rule that forwards only the exact public Meri paths and has an earlier same-host fixed-denial catch-all; it must be proved again on the actual listener before any service starts. The private listener also needs a path allowlist and a default denial. See `CAPIRO-DEV-CHANGE-SET-20261016.md`. No listener rule is created here.

Task families and service names are fixed as `meri-product-preview-{control,temporal-worker,runner}` so a reviewed change set has stable, distinct ownership of this new three-role deployment and cannot silently target the qualification or legacy Meri service. This template always registers new task definitions and defines new zero-count control/worker services; it cannot adopt an otherwise qualified existing task definition or service with a different name. An existing cluster, ECR repository, roles, logs, network or target group may still be supplied after its actual owner and permissions are reviewed. Reusing an existing task definition or service would require a separately reviewed source change, not a name-based rejection of other qualified resources.

The role commands match the image's `node apps/runtime/cli.mjs` entrypoint:

The builder requires these non-secret binding fields: `account`, `region`, `clusterArn`, digest-pinned `imageUri`, `logGroupName`, `executionRoleArn`, `controlTaskRoleArn`, verified non-root `runtimeUser`, `runnerSha256`, role-specific Fargate `sizing`, and `network` with `privateSubnetId`, `controlSecurityGroupId`, `workerSecurityGroupId`, and one to five `runnerSecurityGroupIds`. `controlTargetGroupArn` and `controlPrivateTargetGroupArn` are optional, distinct reviewed references. It emits runner task ARN, cluster, subnet and security-group outputs for later comparison with the existing `task-allocator.mjs` request; these outputs are not admission authority. The builder checks reference format and account/region, but cannot prove a subnet is private, a role is least-privileged, either target group is routed safely, or a digest contains the reviewed runtime. Deployment review must read those actual resources back.

**Activation remains blocked.** The image reads role-specific configuration and credential files as owner-only, regular, non-symlink files. ECS environment and Secrets injection do not satisfy this contract. The tested `runner-bootstrap-files.mjs` materializer has no production caller, and the CLI loads its config before running. No task definition here mounts or manufactures material. Review and compose a bounded file-delivery owner for control, worker, and each task before changing the zero service counts or invoking RunTask. The runner must receive only its admitted per-run task capability; it has no task role in this template. The Temporal worker likewise has no task role. The control task uses only a separately reviewed existing role reference.

The current generic control `/health/ready` remains unavailable while product owners are uncomposed. ECS liveness checks use `/health/live`; they are process checks, not permission to route traffic. Review an existing private/public ingress and an actual target-group health path before attaching any control target group. Current read-only inventory has no named product target group or product image repository, so these bindings are pending. Also verify the exact Core origin, approved database schema/application role, Temporal namespace/TLS, model proxy and budget, current identity/client pins, runtime image/executable measurement, old-pin rollback, and one-run physical-stop custody.
