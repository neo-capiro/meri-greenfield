# First-chat runner route: bounded source design

This is a disabled route proposal. `task-route.mjs` checks a fresh ECS task and EC2 ENI readback against one original after its caller separately proves durable admission; it does not start a router, issue a certificate, or make an AWS call.

## Why a static target group is insufficient

`nativeCandidate.taskOrigin` is a single HTTPS origin frozen in issued run facts before `RunTask`. The control client and the runner's SDK process client both POST `/v1/native-task/*` to that origin with the original in the JSON body. The path and headers do not identify the target task. `task-allocator.mjs` retains task ARN and admission but only verifies the attached subnet; it does not retain or route by ENI/IP. `remote-task-http.mjs` checks the exact original and capability after a request reaches a task. `http-server.mjs` currently opens plain HTTP, not TLS, on runner port 8080. An ALB with multiple runner IP targets can deliver a request to a different run before those checks and cannot prove where a credential was sent.

## Selected minimum route without per-run DNS writes

Keep the issued static `taskOrigin`, but make it a **private, stable HTTPS router origin** served by the control workload through a dedicated internal ALB and control target group. The same private HTTPS origin can serve the existing authenticated `/v1/*` native provider and the new `/v1/native-task/*` router on control port 8080; path dispatch remains separate in source. A private DNS record and server certificate must name that exact origin. The existing control and task capabilities remain the only application credentials. No runner task role is added.

This deliberately selects the same control port 8080 for the public and private target groups. Target-group separation alone supplies **no path boundary**: a live public HTTPS listener must forward only the exact reviewed public paths and return fixed 404 for every other request on the Meri host before any broader rule can match. The private listener needs its own protected path allowlist and default denial. The application currently has no independent host-boundary proof; listener-rule readback and route probes are required before enabling either service. A separate private application port would need an explicit control server/config and task-definition change; it is not implied by the current manifest.

For each request, the router must authenticate the credential against the exact original and allowed operation, then read the immutable issuance and admitted `native_allocations` row. It must compare `original.executionKey`, binding hash, task ARN, task definition, expiry and worker fence. It must read that task afresh with `DescribeTasks` and its one attached ENI with `DescribeNetworkInterfaces`, call `observeOriginalTaskNetworkCandidate`, and refuse missing, duplicate, stopped, changed or public-interface evidence. It may connect only to the returned private IP on runner port 8080. The router must recheck the durable current owner and task evidence around forwarding; a task stop or uncertain read ends the route. POST body, authorization header and response remain bounded, uncached, unredirected and unlogged. The receiving task still verifies the original and capability, so router selection does not replace its authority.

The internal hop should also be TLS. Deliver a short-lived **per-task** server leaf and key to the owner-only runner filesystem after the exact task ARN and ENI are known; its SAN identifies that task (for example the task ID under a private runner zone). The router dials the verified ENI IP with that task-specific SNI and a pinned CA and checks the leaf's task identity and expiry before sending a bearer. DNS need not resolve each task name because the router already has the ENI IP; task-specific SNI/certificate verification must be implemented in its connector. The runner must independently compare its ECS task metadata identity with its admitted bootstrap before opening the TLS listener. The currently tested runner bootstrap delivers a CA file, but no production caller or runner server leaf/key; `http-server.mjs` has no HTTPS listener. This TLS and file-delivery source is required before any service count or `RunTask` is enabled. Reusing one wildcard private key across runners would lose per-task identity.

The post-start delivery protocol is **unselected**. A shipping owner must first define an authenticated, task-bound CSR or equivalent handshake that binds the exact admitted run, ECS task ARN, ENI and expiring certificate before a key is delivered to that task. The current task definition has no such receiver or certificate issuer. Issuing a certificate after `RunTask` without a proved receiver would leave the runner unable to listen; passing a private key in a task override would expose it to the wrong boundary. This is an activation blocker, not a step performed by the offline route observer.

## Exact network and service actions to review

- In the selected `capiro-dev` VPC `vpc-0ac26cfac7ed972be`, use an approved private subnet for the task and **new dedicated** control, worker and runner security groups, plus an internal ALB security group. Do not treat the existing broad `ServiceSg` as a runner boundary. Runner ingress: TCP 8080 only from the control SG. Control ingress: TCP 8080 only from the existing public ALB SG and the new internal ALB SG. Control egress: TCP 8080 only to the runner SG and TCP 443 to the internal ALB SG, with separate exact DB/Core/Temporal/S3/proxy peers. Worker and runner egress to the internal ALB SG on TCP 443 and other exact approved provider peers; worker has no ingress. Internal ALB ingress: TCP 443 only from control, worker and runner SGs; its target hop is TCP 8080 only to the control SG. Poller 8081 is a container-local health check, not runner ingress.
- Create one internal TLS listener and dedicated control IP target group on TCP 8080 for the protected native/router origin, with a private DNS A/alias record and certificate SAN matching that origin. The public control TG is separate and must never route `/v1/*` or `/internal/*`. No per-run Route 53 record, ELB target registration or runner service is required. The router's task lookup uses `ecs:DescribeTasks` on the selected cluster and `ec2:DescribeNetworkInterfaces` with **one admitted ENI ID**; [AWS states](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/iam-policies-ec2-console.html) that EC2 Describe actions cannot use resource-level permissions, so the extra read action requires a separately reviewed `Resource:"*"` grant and strict client-side ID/VPC checks. It needs no Route 53 or ELB mutation permission beyond the control role's separately approved lifecycle rights.
- Add a bounded `/v1/native-task/*` forwarding owner to the control composition, and TLS serving to the single `worker` runner container. Preserve the one-container Fargate task, exact original/capability checks, and stop-only path. Wire the checked ENI candidate from this module only after the durable admission and issuer joins are in place. Add focused wrong-task, stale ENI/IP, stopped/replaced task, TLS wrong SAN/CA, token nonforwarding, expiry and stop-race tests. Route failure must keep physical-stop reconciliation available through ECS even when HTTP is unavailable.

The code today has none of that routing, TLS listener, private DNS, dedicated SG or certificate delivery. This proposal is a source plan, not a claim that first-chat can be reached.
