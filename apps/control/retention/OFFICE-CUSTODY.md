# Office disposal and uncertain remote writes

Core owns private Office draft rows and their existing seven-day lifetime. Meri's existing retention owner remains the sole authority for suppression, policy eligibility, purge plans, UNKNOWN outcomes and restore recovery. Office custody is owner-managed in the data-class registry; it adds no second configurable retention policy or local copy of private bytes.

Production retention composition supplies the existing service-authenticated Core Office client to the purge executor and reconciler. Before local row/object deletion, the executor records effects started in its existing ledger, asks Core to retire at most 100 matching drafts, and requires a current counts-only read with zero active rows/bytes and a durable disposal marker. Partial batches and unavailable responses remain UNKNOWN. A lost response is reconciled by a fresh read; successful disposal is not replayed. Recovery performs reads only, verifies Core even when there are no local targets, and withdraws completion if bytes return or its disposal marker disappears.

Core's forward migration adds a content-free disposal marker in the existing Office custody owner. It is a permanent erasure exclusion, not a suppression decision, active access grant or second retention ledger. All native Office reads and mutations take shared transaction locks on the conversation and artifact before the private draft lock. Retirement takes the exclusive subject lock, inserts the marker and removes bytes in the same transaction. A remotely running Save commits before retirement obtains the lock; a delayed Open or Save arriving later sees the marker and is refused. Deleting expired draft rows cannot remove the marker. Ordinary actors can read only their tenant's markers and cannot create or remove them.

The fixed internal wire is `meri.office-draft-retention.v2`; Core migration/source and this consumer must be released together. Normal chat Trash/member/client access cleanup remains with its existing Core owner. Immutable artifacts are still erased only by the existing Meri object/row owners. No runtime credentials, browser content or editor tokens enter the retention ledger.

Author responsibility assessment: the existing executor still owns one purge state machine and its canonical plan/ledger. The extra Core effect is sequenced through its existing begin/UNKNOWN/reconciliation transitions. The reconciler remains read-only and consults the same external custody owner. Extracting a second Office purge state machine would duplicate those responsibilities. This assessment is not an independent review.

Verification includes ordinary-role PostgreSQL races (already-running Save, delayed Open, empty subject, expired row identities, cross-tenant/RLS denial), native-client response validation, lost acknowledgement, bounded partial retirement, unavailable Core, restored bytes/marker and existing purge/recovery/production composition tests. The migration is applied only to isolated synthetic databases. Builds, deployment, live CODE/Office qualification and independent review remain held.
