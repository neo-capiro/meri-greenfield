# Conversation requests and durable events

The product control owner accepts an authenticated request, commits immutable prompt/window/skill pins and a queued Run/UIEvent, then starts the existing Temporal service with an exact workflow ID. Retrying the exact request recovers a lost start acknowledgement without a second stored request. PostgreSQL serializes request creation and event allocation per conversation. Events use existing public contracts, ordered sequence cursors and immutable event-ID replay. Current session context controls history, cancellation and worker publication; every access uses the existing opaque session owner again. Cancellation persists a terminal state before sending Temporal cancellation, fencing late publication.

`createPostgresConversationStore({pool})` borrows an already-configured finite-timeout pg-compatible pool. The centrally allocated product migration is `migrations/0001_conversations.sql`; it does not alter qualification state or native-owner pins. `createConversationService({sessions,store,dispatcher,versions,fiscalCalendars})` composes existing session/current-context ports. `createTemporalConversationDispatcher({client,taskQueue})` borrows an upstream Temporal Client. The deterministic `meriConversationWorkflow` dispatches one activity, with automatic activity retries disabled; it contains no model or tool loop.

`createConversationApplication({service})` retains POST `/api/conversations/submit`, `/history` and `/cancel`. Submit body is `{requestId,prompt,windowRequest?,skill?:{skillId,skillVersion}}`, history is `{after?,limit?}`, and cancel is `{}`. Additive public package0.1.3 admits closed receiving requests and exact responses through `/conversation-application`; previous action/document/root/browser generated exports and public wire0.1.0 are unchanged.

POST `/api/conversations/events` publicly accepts `{command:{conversationId,intent:'view.subscribe'}}`. The selector must equal authenticated `history.run.binding.conversationId` before stream release; it never selects tenant/run/actor/scopes or substitutes authority. GET `/api/conversations/events/{conversationId}/stream` matches upstream AI SDK7.0.137 DefaultChatTransport reconnect (`api:'/api/conversations/events'`, `chatId:conversationId`). Optional `x-meri-resume-sequence` is a canonical nonnegative safe decimal integer, default0. Query/Last-Event-ID cursors, conflicting POST cursor headers, GET bodies/content-type/encoding/nonzero content-length and foreign selectors are refused. Legacy POST events `{after?,limit?}` remains a distinct compatibility shape; public command cannot be combined with it.

Every subscription uses the same existing current-session checks and event source; no second lifecycle is introduced. SSE uses existing transient `data-meri-event` AI SDK transport, with no-store/nosniff headers and reader cancellation cleanup. Client stream end/abort does not invoke durable cancel and is not run completion. Frontend integration remains separately owned, and native/runtime acceptance remains separate.

Calendar normalization calls the actual trusted window resolver. Selected skills load exact immutable assets and invoke the existing canonical manifest availability check; all production operations remain unavailable, so those requests currently fail before persistence/dispatch. Ordinary questions remain lightweight. Worker publication is limited to run status and public text; source/tool/artifact receipts keep their existing owners and require subsequent authorized integration.

`loadForExecution`/`publish` are trusted-control methods, not browser routes. A worker proxy can expose those methods under its task-bound capability while this host keeps the native authority credential. No worker receives a database or account credential. The loopback tests compose the real session owner, store, service, Fetch mount, AI SDK producer and worker adapter with synthetic SQL/native-identity/SDK-message ports. They prove source behavior, not native PostgreSQL, Temporal server, model proxy or worker execution.

This first usable-request slice supplies creation, durable event history/reconnect, cancellation and one SDK activity. Multi-run conversation listing, authenticated steering/fork, verified checkpoint/workspace resume, approval-wait integration, current native identity/worker activation, actual isolated worker launch/retirement, UI consumption and native migrations remain open. No runtime worker is launched by import or this mount. Live qualification must wire the exact product source/image to the independently accepted native owner and persistence; qualification fixtures are not promoted.

Run `npm ci --ignore-scripts --prefix apps/control/conversations` and the analogous worker/window package installs, build `packages/ui-stream`, then `npm run check --prefix apps/control/conversations` and `npm test --prefix apps/worker/conversation`. Pools/Temporal clients/sessions are borrowed and remain caller-owned. A subscription owns its abort controller and closes it; the activity owns and closes its SDK Query, deadline and heartbeat timer. Unknown COMMIT/start acknowledgements remain visible and recover through exact persisted IDs.

Exact request replay compares the original user window specification and immutable skill/prompt while returning the saved normalized window, so crossing a civil week boundary cannot silently repoint the request. Worker publication compares current scopes with stored scopes inside the locked transaction before inserting anything. Redundant event sequence/ID columns must agree with the hashed event JSON before replay/release.

The canonical store's read-only `findRequest` selects an already-pinned request before calendar resolution. Reconstruction therefore replays a fiscal request even when the current fiscal configuration is absent, after current authority, scopes, runtime versions and exact input/pins agree. New requests still require trusted resolution. Cancellation uses the same locked expected-scope check as worker publication.

Terminal settlement and recovery. The worker's terminal publication waits a bounded acknowledgement per attempt and replays the same event ID once, so a lost acknowledgement reads back the committed write. A run whose original never acknowledged a terminal write is settled by `createRunReconciler({store,retirement})` (`run-reconciler.mjs`): after the native stop owner has recorded the original RETIRED (physical stop proven, grants revoked) in the allocation journal, it records `failed/ATTEMPT_LOST`, or the verified `HOLD_CHECKPOINT_FAILED` exit for an unapplied hold; an unproven stop writes nothing. The prepared kickoff's stop composes it, and both workflows schedule the `reconcileConversation` activity (the same stop) after their single attempt fails or is lost; nothing is redispatched. After a hard control restart the kickoff's stop also reaches a stop-only original retirement rebuilt from the exact durable allocation facts (it revokes, contains and records RETIRED; it never allocates); every later stop, reconcile activity or operator `apps/runtime/reconcile-run.mjs` call is a fresh bounded attempt over durable state, and an uncertain stop stays UNKNOWN. A failed or cancelled latest run admits one explicit next prompt through the next-run owner once its original is retired and revoked, or, when it turned terminal while still queued and never claimed an allocation, on the store's no-authority evidence: the `FORECLOSED` allocation row written in that same terminal transaction, which also refuses any later claim. A missing allocation row is never accepted. The successor starts a fresh SDK session and never resumes a checkpoint: earlier turns' model context is not restored (the durable conversation history continues; that is a different claim).
