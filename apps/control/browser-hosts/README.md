# Physical browser allocation and routing

The existing `meri_host_control.host_allocations` proposal is implemented by `migrations/0001_host_allocations.sql`. This is the single physical host registry shared by host currentness and viewer routing. It stores immutable allocation and native boot identity, original run binding, viewer owner identity, private endpoint and public certificate pins. It stores no private key, session credential, document, browser profile or image. The canonical conversation journal continues to own paused custody, successor admission, user scope and current run authority.

The trusted provisioning owner calls `createPostgresHostAllocationWriter.admit` after verifying its existing native allocation. Actual issued public certificates determine the fingerprints and expiry. Repeating the exact admission returns its original allocation; changed metadata, reused certificates or a second unterminated host for the conversation refuse. Revocation is one-way. Its `recordTeardown` consumes the existing trusted native teardown owner's VERIFIED result and atomically persists that exact receipt with `terminated`. The forward `0002` migration makes a terminal state without a receipt invalid; receipts remain immutable. Replaying the same receipt recovers an unknown commit without running teardown again. A revocation or timeout alone cannot make an allocation replaceable. Certificate rotation is not provided inside one bounded generation. It expires rather than silently broadening the original lease.

`meri_host_allocator` and `meri_host_currentness` are NOLOGIN roles with no automatically granted membership. The latter has SELECT and nonce INSERT only. Fixed definer functions retain a `FOR SHARE` lock on the selected allocation inside the caller's transaction, avoiding an UPDATE grant merely to obtain PostgreSQL row locks. Public execution is revoked. The same-transaction `readCanonicalRun` supplied by the existing run/custody owner must independently derive current browser admission, fresh Core scope and the logical binding; the physical row is never sufficient authority.

`createBrowserHostRouter` resolves that row before every private mTLS operation and again before releasing the reply. The destination cannot come from a viewer request. It constructs a bounded client for one exact allocation and closes it after the operation. Unknown device effects do not retry. Existing runtime TLS credentials are supplied at composition, never minted by the router.

`createBrowserCustodyCurrentness` joins retained custody to the existing Core client and native credential owner. It uses the allocation reader's same transaction and the canonical lifecycle `currentHost` chain. `readHost` preserves the original physical binding for native browser currentness; `readRoute` permits only the latest logical binding, checking exact custody when supplied. It borrows that logical run's credential, requires a fresh matching Core receipt, checks that the credential did not change during the read, and clips expiry to all existing cutoffs. It never grants SDK or Bash authority to the retired source. Do not supply the higher-level `transitionAuthority` as its Core client: that wrapper reacquires conversation locks on another connection. Use the existing Core authority HTTP client's `readCurrent` directly.

This custody adapter handles an already established, canonically held browser and its successors. Initial active-host policy/admission and native provisioning must be composed through their existing owners; there is no active fallback or caller-supplied positive. Native successor attachment, verified teardown and runtime registration remain required before live activation. This source does not allocate an EC2 host, apply a product migration, open the browser activation record or deploy a service.

The existing central migration catalog appends ordinals 72–75 after its unchanged 71-entry prefix: installer-created NOLOGIN roles, allocation schema, verified teardown extension, and readonly currentness grants to the existing Control role. The migration owner stays NOCREATEROLE. The native provisioning writer's production service/login/credential binding remains unselected; no allocator privilege is granted to Control and no login or password is created. Release/DB own the bounded apply packet; this is not authorization to replay bootstrap or passwords.

Qualification: `MERI_HOST_ALLOCATIONS_PG_ATTEST=isolated-local node --test scripts/qualification/browser-host-allocations-postgres.mjs` uses the existing Windows PostgreSQL 16 fixture on loopback port 55487. It installs only this new schema when absent and two isolated ordinary fixture logins; it never resets, deletes or stops existing data or services. Actual PostgreSQL checks cover exact replay, immutable metadata, separated roles, serialized revocation, unknown COMMIT recovery, nonce replay and withholding a reply after revocation. Core and native-host decisions in this allocation-specific qualification are synthetic; they do not establish end-to-end browser or deployment acceptance. Exit 0 means the assertions passed; nonzero means missing explicit fixture attestation or failure.

Then run `MERI_HOST_ALLOCATIONS_PG_ATTEST=isolated-local node --test scripts/qualification/browser-custody-routing-postgres.mjs`. It grants the local fixture reader the already existing canonical conversation role, seeds only a new synthetic tenant's configured model budget, and exercises real custody/continuation journals and route resolution with that ordinary role. It checks stale source, wrong custody, denied/foreign/stale Core observations, changed credentials and cancelled successors. Core, SDK and native host effects remain scripted. Existing fixture data and services are retained.
