The fixed private Fetch routes are POST `/v1/runner/session/{register,load,append,list-subkeys}`. ## First-run compiled join

`createNativeFirstRunPorts({identity,admission,native?,registration?,enabled:false,now,limits})` provides `{identityContext,sdkSessionOwner}` for `assembleControl({...,productPorts})`. `identity` contains only the canonical authority `origin`, server-prebound `commandContext` and trusted `fetchImpl`; `limits` is `{maxRequestMs,maxFactBytes}`. The same borrowed `admission` supplies `currentRun` and `withCurrentAllocation`. Construction performs no IO, migration, credential lookup or allocation. Activation remains an explicit trusted-server decision, separate from source activation or output approval.

`createNativeTaskAuthority` forwards exact task capability/binding/operation/input SHA to the existing native `worker/authorize` owner and validates its canonical fresh receipt. It is a transport/correlation adapter, not a signature, task launch or native policy implementation. Existing private worker routes reuse it. Missing verifier/observer, booleans, malformed/foreign/expired receipts and current-policy drift refuse. The native verifier must not reacquire the same Meri allocation lock during lease refresh.

`registration` is the independently observing native owner's compiled `.read` port, captured with its original receiver. The existing durable owner validates exact SDK init/main-key provenance, observation identity/hash and original expiry. No worker publish endpoint, callback boolean, UUID, grant hash or qualification observer replaces it. The native worker verifier and native registration reader still need externally approved implementations/bindings; the local synthetic loopback PostgreSQL and SDK package checks do not supply them. The frontend's newer three read-only backend routes are a separate receiving plan and do not replace application-authority context or task/session verification.
