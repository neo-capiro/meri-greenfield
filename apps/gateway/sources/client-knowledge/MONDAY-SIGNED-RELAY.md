# Monday retained read relay outline

`read_monday_client_boards@0.2.0` uses a Monday-only signed handler and HTTP adapter. The existing client-knowledge request context remains the canonical input, current authority and output validator. The memory adapter and eligibility callback are unchanged. The older passive adapter retains its separate `monday-mapping.mjs` receipt check.

The handler requires a trusted post-reservation invocation ID. The adapter emits exact `JSON.stringify({input,metadata})` bytes to `POST /api/clio/tools/read_monday_client_boards`, asks the existing credential broker for a single-use `CapiroMeriRead` token bound to that target and the canonical four-field correlation, and verifies the echoed credential pins before Fetch. The gateway still owns reservation, current policy checks, deadlines, output bytes and release. A missing signed token, current authority or deadline closes the call.

The signed-native source contract relies on Core `138c04373b18bb730b1ad0f8f9338342f628b8c6`, `apps/api/src/meri/retained-source-v02/monday-current-source.ts` (`readWithCurrentMondayMapping`) and `documents-monday.ts` (`prepareMondayRead`, `projectMondayRead`). Core reads the managed mapping for the actual tenant/user/client before and after the same canonical source read, rejects mapping-version/board-set changes, and verifies every row against the current board set and source actor. `boardContext` is only a selector inside that mapping. Core returns the unchanged canonical Monday result; neither its token reply nor result body exports a `managedBoardMapping` receipt. The signed adapter therefore requires no fabricated mapping receipt. It validates the canonical result plus every row's selected client and actual actor; exact signed target/body/correlation pins remain mandatory. HTTP denial and unavailable states stay failures, and canonical unavailable/partial coverage stays unchanged.

This is an intentional boundary correction from an unproducible external mapping receipt to the existing authoritative Core receiver. Activating a Core successor requires preserving that producer contract; source inspection does not qualify its deployment.

Focused verification uses synthetic signed wire and refusal cases, the unchanged memory adapter checks, and the general-read family composition once shared dispatch propagates the trusted invocation ID. Production enablement requires a configured Core endpoint, composed credential broker, Core listener, deployed source/image/config pins and live readback by the shipping owner.
