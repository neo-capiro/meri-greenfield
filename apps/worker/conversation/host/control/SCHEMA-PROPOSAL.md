# Host control persistence — implemented source, deployment unapplied

The canonical physical allocation migration and its role grants now live in [browser-hosts](../../../../control/browser-hosts/README.md), at `apps/control/browser-hosts/migrations/0001_host_allocations.sql`. That source replaces the earlier proposed SQL in this document. Do not create a second host table from an older copy.

The allocation stores one immutable native host generation, original run binding, stable browser owner, private endpoint and actual public certificate fingerprints. Routing and currentness use that same row. Currentness obtains its transaction-held row lock through the fixed `lock_allocation` function and needs no allocation UPDATE grant. Nonces remain unique for the generation. Revocation cannot reactivate a host or permit replacement before verified teardown. Credentials expire within the bounded allocation; in-place certificate rotation is not implemented.

The canonical conversation journal retains all run, pause and successor authority. Its existing `browserCustody.currentHost` reads held custody and exact successor lineage on the same PostgreSQL client. The control composition must also supply current Core authority and independently derived policy admission; allocation metadata never grants SDK, Bash or browser use by itself. A retained browser successor must leave its retired source SDK and Bash denied.

Actual isolated PostgreSQL qualification covers immutable allocation replay, separated ordinary roles, locked revocation, nonce replay and lost COMMIT acknowledgement. Core/native decisions in that allocation qualification are scripted. The native provisioning/currentness composition, verified teardown and deployed browser acceptance remain open. The source does not apply a production migration or change activation.
